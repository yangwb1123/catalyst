# 架构分析：ForgeOS 方向分析文档体系的元架构审查

## 1. 架构评估

### 1.1 当前分析体系架构的观察

我审查的不是那五个方向本身（方向验证文档的代码级质量扎实），而是**产出这些分析的元架构**——一个 118,319 行、~200 个文档的文件体系。

**现有架构的优势：**
- **低摩擦入口**：任何人（Agent 或人）可以随时写入一个新的分析文档，无审批门槛
- **代码级实证文化**：每个方向强制绑定 `file:line` 引用，防止纯推测
- **审验闭环**：每个 `.md` 有对应的 `.out.md` 验证输出，形成可追溯的审计轨迹

**现有架构的局限性（远大于优势）：**

| 维度 | 当前状态 | 架构债务等级 |
|------|---------|------------|
| **信息密度** | 118K 行文档，有效新颖方向数远低于文档数 | 🔴 P0 |
| **检索成本** | 平面目录，无索引、无标签、无交叉引用 | 🔴 P0 |
| **重复率** | 交叉验证发现方向二、四完全重复，方向三、五部分重复 | 🟡 P1 |
| **元冗余** | 验证文档本身（`.out.md`）成为噪音源，而非信号增强器 | 🟡 P1 |
| **饱和效应** | 随着分析轮次增加，新颖方向发现率趋近于零 | 🔴 P0 |
| **决策通道** | 「分析→验证」循环与「工程实施」脱节——分析不转化为 ACTION | 🟡 P1 |

### 1.2 关键的架构债务点

**债务一：平面文件系统作为状态管理**

`docs/requirements/` 被用作唯一的状态存储——没有数据库、没有索引、没有分层。一个典型的搜索场景（"哪个文档讨论了 spine workflow 数据契约？"）需要 `grep -r` 遍历全部 ~200 个文件。这不可扩展。

**债务二：验证反模式（Validation Loop Amplification）**

每次分析触发一次验证，验证产出本身（`.out.md`）再进入文件体系——但验证输出**不抑制原分析的重复**。这意味着：
- 方向二被第 N 个文档覆盖 → 验证指出重复 → 原文档保留 → 第 N+1 个分析仍可能重新发现
- 验证只做**检测**（告警），不做**抑制**（阻止冗余进入系统）

**债务三：新颖性声明的可信度衰减**

每个文档的开头都声明「交叉审阅最新 10 篇确认无重复」。但交叉验证文档**自身**指出这个声明不成立——它漏掉了同一天 18:05 创建的文件。这表明：
- 审阅窗口（最新 10 篇）太窄
- 审阅方法缺乏全局去重哈希（如 MinHash/LSH 做近似文本匹配）
- 声明的可信度随时间递减

## 2. 扩展方向（5 个高价值架构方向）

以上是对「分析体系本身」的架构评估。以下我给出 5 个**真正新颖**的扩展方向——不是 ForgeOS 运行时的扩展，而是 **ForgeOS 认知/分析/治理体系**的架构扩展。

### 方向一 ⭐ P0 · 分析知识图谱与去重管道

**为什么需要**：118K 行中保守估计 40-60% 是重复或部分重叠内容。每次新分析前的手工去重不可靠（如交叉验证所证实）。需要系统级去重。

**核心挑战：**
- 近似文本匹配（而非精确匹配）——方向二在不同文档中措辞不同但核心论点相同
- 跨文档的论点去重而非全文去重——方向三的「空审批文件」在文档 A 中作为子论点、在文档 B 中作为独立方向
- 语义级而非 token 级相似度检测

**预期架构变更：**
- 引入 `docs/requirements/INDEX.json` 作为轻量级索引
- 每个文档提交时计算内容特征的 MinHash 签名
- 新增 `harness/novelty-scan.mjs` 作为 check.py 同等地位的闸门——新分析必须通过新颖性检查才能入库
- 新增 `docs/knowledge-graph/` 层：不重复存储，只存交叉引用和差异

**对现有系统的影响**：低。完全不触及 forge-core 运行时，只改变分析产出流程。新增一个 harness 级别的检查闸门。

### 方向二 ⭐ P0 · 从「方向仓库」到「方向生命周期」——分析→决策→实施→关闭

**为什么需要**：当前每个方向分析都停留在「已分析、已验证」的终结状态，从不转化为 ACTION。仓库中 ~200 个文档真正被转化为 sprint item 的比例极低。

**核心挑战：**
- 分析文档和工程 backlog 之间的桥梁缺失
- 没有优先级采纳/拒绝决策记录
- 分析推荐的方向在 3 个月后是否已被解决？无从知晓

**预期架构变更：**
- 在 `.agent/` 中新增 `insights/` 目录，结构化为 `PENDING | ADOPTED | REJECTED | SUPERSEDED` 四态
- 每个方向分析必须包含「建议工程动作」章节（不编写代码，但指定受影响的包/文件/接口）
- 新增 `harness/backlog-bridge.mjs`：定期扫描 `PENDING` 方向，与 `CURRENT_SPRINT.md` 交叉验证，标记已覆盖的方向为 `ADOPTED`
- 方向进入 `REJECTED` 时必须记录理由（如「已覆盖见文档 X」或「当前阶段不优先」）

**对现有系统的影响**：中。不改变运行时，但改变 .agent 结构，引入新的治理检查。需修改 `check.py` 或新增检查。

### 方向三 ⭐ P1 · 方向分析的饱和曲线——何时停止「发现」开始「建造」

**为什么需要**：从数据看，7月10-11日两天内产生了 ~170 个分析文档，但有效新方向发现率急剧下降。交叉验证确认 5 个方向中仅 1 个真正新颖。这是**分析生产率的饱和曲线**——继续投入分析产出的边际价值趋近于零。

**核心挑战：**
- 需要量化「饱和度」指标：给定 N 个文档，下一个文档的预期新颖概率
- 需要触发机制：当饱和度超过阈值时，自动关闭「方向发现」阶段，强制转向「实施」阶段
- 反向激励：当前系统激励「产出更多文档」（文档数量被用作工作量证明）

**预期架构变更：**
- 新增 `docs/requirements/SATURATION.md` 或 `docs/SATURATION.md`：每日更新新颖方向发现率曲线
- 在 `harness/acceptance.mjs` 或 `check.py` 中引入饱和度检查：如果连续 3 次分析没有发现新颖方向（新颖方向率 < 20%），闸门拒绝新的分析文档，要求先实施已有方向
- 新增 `docs/requirements/CLOSURE.md`（或合并到 `CURRENT_SPRINT.md`）：记录「分析阶段关停」决策，列出所有未实施但已分析的方向，指明何时重新开放

**对现有系统的影响**：中。新增检查闸门，可能改变工作流。需要审慎设计阈值——太早关闭错过真实盲区，太晚关闭延续当前冗余。

### 方向四 ⭐ P1 · 代码级验证本身的架构债务——`file:line` 引用的漂移

**为什么需要**：交叉验证文档中代码引用的偏差是 4 行（`main.go:395` 实际在 `main.go:399`），这已是较好情况。随着代码迭代，所有 `file:line` 引用都会漂移。当前分析文档中的引用是**一次性快照**，不会随代码更新。

**核心挑战：**
- 漂移率：每个 sprint 有多少行号引用变得不准确？
- 如何验证引用当前是否仍然准确？每次方向被提及时需要重验证
- 引用漂移导致分析文档的可信度随年龄衰减

**预期架构变更：**
- 代码引用格式从纯文本 `file:line` 升级为结构化格式：`file:line:function:content-hash`
  - 例如 `engine_build.go:458:execEngine:sha256partial`
  - 引用验证时可以检查 content-hash 是否匹配，不匹配则标记为「可能漂移」
- 新增 `harness/reference-staleness.mjs`：定期扫描所有分析文档中结构化引用，报告漂移率
- 引入引用半衰期指标——当一个文档超过 30% 的引用已漂移，标记为 STALE

**对现有系统的影响**：低。只改变分析文档的引用格式和新增一个验证 harness 工具。

### 方向五 ⭐ P2 · 跨文档论点合并与重构管道

**为什么需要**：交叉验证发现方向二在 `genuinely-unexplored-extensions.md` 方向三中已被完全覆盖。两个文档的同一论点分散在不同上下文中，各自有独立的边缘场景分析和代码引用。合并它们可以产生更完整的分析。

**核心挑战：**
- 跨文档的论点识别：同一论点可能分布在 N 个文档中，每个贡献不同的子分析
- 合并语义冲突：两个分析对同一方向提出不同的修复方向，需要仲裁
- 自动合并 vs 人工复审：论点合并到哪里？

**预期架构变更：**
- 新增 `docs/requirements/MERGED/` 目录——存放经过合并的精炼方向文档
- 每个合并文档记录源头文档列表（如 `source: [doc-A.md, doc-B.md]`）
- 新增 `harness/merge-proposal.mjs`：当新颖性检测发现 ≥60% 匹配时，自动生成合并提案而非拒绝
- 合并提案包含差异高亮（doc-A 独有的边缘场景、doc-B 独有的代码引用），供人决策

**对现有系统的影响**：低至中。需新增工具和流程，但不影响运行时。

## 3. 接口设计建议

### 3.1 分析体系的核心接口

当前分析体系缺少四个关键接口：

| 接口 | 现有 | 建议 | 原则 |
|------|------|------|------|
| **进入接口** | 直接写 `docs/requirements/` 目录 | 通过 `harness/ingest.mjs` 管道——自动检测新颖性、格式验证、索引更新 | 先验证再入库 |
| **查询接口** | `grep -r` | `docs/requirements/INDEX.json` + `docs/requirements/TAG_INDEX.md` 两级索引 | 元数据先于全文 |
| **决策接口** | 无 | `.agent/insights/` 四态目录 + 状态变迁规则 | 决策绑定理由 |
| **过期接口** | 无 | 引用半衰期 + STALE 标记 | 知识有半衰期 |

### 3.2 是否引入新抽象层

**需要引入一个「分析管道」抽象层**，位于分析者（Agent/人）和存储之间：

```
分析者 → [新颖性检查] → [格式验证] → [索引注册] → [入库]
           ↑              ↑              ↑
       MinHash签名   引用结构化    INDEX.json 更新
```

这个管道不触及 forge-core 运行时一丝一毫，是纯治理层的工具链扩展。

### 3.3 向后兼容性

所有已有文档保持原样。新管道只对新入库的文档执行检查。已有文档可以按需迁移（通过 `harness/migrate-refs.mjs` 升级引用格式）。

关键原则：**读路径（已有文档的阅读）不变，写路径（新文档的写入）增强**。

## 4. 技术选型

### 4.1 是否需要引入新的技术栈

**审慎：尽量不引入外部依赖。**

对比方案：

| 功能 | 自建（推荐） | 引入外部库 | 理由 |
|------|------------|-----------|------|
| **文本相似度** | MinHash 自实现（~50 行 Python/JS） | `textdistance`（Python）/ `string-similarity`（JS） | 自建成本极低，零依赖，无锁定风险 |
| **文档索引** | `INDEX.json` + `find`/`grep` 回退 | SQLite / Elasticsearch | 平面文件索引足够支持 ~200-1000 文档规模 |
| **引用哈希** | SHA256 截断（Go `crypto/sha256` 已有） | 无 | forge-core 已内置 |
| **CM 风格合并** | diff3 算法自实现或调用系统 `diff3` | 无 | POSIX 工具链即可 |

**评估标准**：
1. **零外部依赖**（与 forge-core 保持一致）
2. **可被 harness 直接调用**（Node 或 Python，无需额外运行时）
3. **文件系统原生**（不需要数据库服务）

### 4.2 自建 vs 采购决策

不是「采购」场景——这些都是工具链改进。决策树：

- **核心功能**（新颖性检查、引用验证、索引）→ 自建，嵌入 harness
- **辅助功能**（合并提案的 diff 展示）→ 调用系统工具（`diff3`、`git merge-tree`）
- **可视化**（饱和曲线、方向分布）→ 可选项，可移植到 Web UI（第三地平线）

## 总结：真正的问题不是那五个方向

交叉验证文档揭示的真正架构问题是：

1. **分析体系本身的熵增**——118K 行零结构平面文件是不可持续的
2. **缺乏饱和感知**——继续「发现」的边际价值趋近于零，但系统没有停止信号
3. **分析→决策→实施的断裂**——方向分析不转化为工程动作，仓库变成分析墓地

我建议将交叉验证文档本身转化为一个**方向零**（P0）：不要继续在五个方向的细节上迭代，而是解决让这五个方向得以产生但又无法被有效管理的**元架构问题**。

最紧急的动作不是修复 `execEngine` 的 exit code（那是工程任务），而是：
1. 停止「更多分析文档」的生产——在饱和曲线见底后每篇新文档的边际贡献接近零
2. 建立分析知识图谱索引
3. 将已验证且有价值的方向（方向一为起点）正式转化为 sprint action items
