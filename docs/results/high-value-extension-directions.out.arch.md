# 架构分析报告：AI 编码助手使用限制错误

## 1. 架构评估

### 当前架构推断

从错误信息 `GoUsageLimitError` + `5-hour usage limit reached` + 退出码 1，可以推断当前的工作流存在对外部 AI 编码助手服务的**硬依赖调用**，且该调用是**同步阻塞**在关键路径上的。

### 优势

- **简单直接**：将 AI 编码助手嵌入工作流后，功能上能快速落地
- **低成本启动**：利用托管服务（opencode.ai），无需自建推理基础设施

### 局限性

| 问题 | 风险等级 | 说明 |
|------|---------|------|
| **硬依赖外部第三方 API** | 🔴 P0 | 调用失败直接导致整个任务失败（exit=1） |
| **无重试/降级机制** | 🔴 P0 | 一次 429 就彻底中断流程，没有缓冲 |
| **无配额感知** | 🟡 P1 | 代码未检查配额状态，等到被限才失败 |
| **无异步/队列化** | 🟡 P1 | 2.1s 耗时说明是同步阻塞调用，浪费等待时间 |

### 架构债务

1. **可靠性债务**：外部服务的可用性（SLA 通常为 99.9%）直接决定了整个流程的可用性，这在架构上没有隔离层
2. **弹性债务**：面对速率限制（rate limit）没有指数退避、预检查、或用备用提供商的降级策略
3. **可观测性债务**：仅看到「退出码 1 + stderr」，缺乏调用延迟、配额剩余量、重试次数等可观测指标

## 2. 扩展方向

### 方向一：引入断路器 + 降级层

**为什么需要**：防止单次 AI 服务不可用导致整个 CI/CD 管道崩溃。

- **业务价值**：提高流水线可用性，避免因配额耗尽阻塞开发流程
- **技术价值**：通用化熔断模式，可复用于其他外部依赖

**核心挑战**：
- 如何定义「降级行为」？是跳过 AI 检查、使用缓存结果、还是回退到传统规则引擎？
- 断路器状态（closed/open/half-open）需要在多实例间同步（如果 CI 是分布式执行）

**预期的架构变更**：
```
┌─────────────┐     ┌──────────────┐     ┌───────────────┐
│ 工作流引擎   │ ──→ │ 断路器代理   │ ──→ │ AI 编码助手   │
│             │     │ (降级策略)   │     │ (opencode.ai) │
└─────────────┘     └──────┬───────┘     └───────────────┘
                           │
                    ┌──────▼───────┐
                    │ 缓存层 /     │
                    │ 回退规则引擎  │
                    └──────────────┘
```

**对现有系统的影响**：需在调用链中插入代理层，原本的直接调用改为通过抽象接口调用。中低影响，重构范围可控。

---

### 方向二：异步队列化 + 配额感知调度器

**为什么需要**：配额是时间窗口内的总量，将高并发请求打散到配额窗口内，避免触发限制。

- **业务价值**：在有限配额下最大化吞吐量；不再因「恰好多个任务同时执行」而失败
- **技术价值**：通用的配额感知调度模型可复用于其他 API（GitHub API、OpenAI API 等）

**核心挑战**：
- 需要精确跟踪配额消耗速率，提前预测何时接近阈值
- 队列的优先级：配置变更触发的 AI 检查 vs PR 的 AI review 谁优先？
- 跨进程/跨主机的配额状态同步

**选项对比**：

| 方案 | 优势 | 劣势 |
|------|------|------|
| **本地令牌桶 + 预估算** | 简单，无需外部存储 | 多实例不同步，可能超限 |
| **Redis 集中计数器** | 精确同步，支持分布式 | 引入 Redis 依赖 |
| **预测窗口自适应** | 可动态调整，适应不同模型 | 实现复杂度高 |

---

### 方向三：多供应商抽象（Multi-Provider Abstraction）

**为什么需要**：绑定单一 AI 提供商是单点故障，不同模型各有优劣。

- **业务价值**：不因一家配额受限而停摆；可根据任务特性选最佳模型
- **技术价值**：建立 Provider 抽象层后，换模型/加模型不改调用方代码

**核心挑战**：
- 不同提供商的 API 格式、能力边界、定价模型差异大
- 如何保证不同模型在同任务上的结果质量和一致性？
- 成本控制：自动 fallback 到更贵模型可能导致预算超支

**预期的架构变更**：

```
┌────────────┐
│ 调用方代码  │ — 面向接口编程
└─────┬──────┘
      │
┌─────▼──────────┐
│ AIProvider     │ ← 抽象接口
│   · Generate() │
│   · Analyze()  │
│   · Review()   │
└─────┬─────┬────┘
      │     │
┌─────▼┐ ┌─▼──────┐ ┌─▼──────┐
│Genie │ │Claude  │ │GitHub  │
│(open│ │ (API)  │ │Copilot │
│code) │ │        │ │        │
└──────┘ └────────┘ └────────┘
```

**对现有系统的影响**：中等。引入抽象层需要重构所有直接调用，但这是健康架构的必要投资。

---

### 方向四：可观测性与告警体系

**为什么需要**：当前完全无观察性，失败即失败。

- **业务价值**：开发者和运维能在配额耗尽前收到预警
- **技术价值**：构建完整的 Metrics → Dashboard → Alert 链路

**关键指标**：
- `ai_provider.quota_remaining` — 当前配额剩余
- `ai_provider.quota_reset_time` — 配额重置时间
- `ai_provider.latency_p99` — 调用延迟
- `ai_provider.retry_count` — 重试次数统计
- `workflow.blocked_by_quota` — 因配额阻塞的任务数

---

### 方向五：结果缓存与增量分析

**为什么需要**：对相同输入的重复 AI 分析是浪费配额。

- **业务价值**：节省配额，加快 CI 速度
- **技术价值**：缓存命中可缩短到毫秒级，用户体验提升大

**核心挑战**：
- Cache key 设计（按文件内容 hash？按 diff 范围？）
- 缓存失效策略（文件变更后自动失效）
- 对于 AI review，同一段代码如果上下文变了，结果可能不同

---

## 3. 接口设计建议

### 关键模块抽象层

建议引入以下接口（伪代码级描述，不涉及实现）：

```
Provider 接口：
  - generate(Req): Res          — 通用生成
  - analyze(CodeCtx): Review    — 代码分析
  - quota_status(): QuotaInfo   — 配额状态查询
  - provider_meta(): Meta       — 提供商元数据

断路器抽象：
  - call(Provider.method): Result
      内部处理：配额检查 → 熔断判断 → 调用 → 错误重试 → 降级

调度器抽象：
  - enqueue(Task): TaskHandle
      内部处理：配额调度 → 排队 → 提交 → 回调通知
```

### 向后兼容策略

1. **包装而非替换**：新增抽象层作为包装器，原有直接调用路径保留一个版本（标记 `@deprecated`）
2. **渐进式迁移**：用 feature flag 控制是否启用断路器/降级，默认关闭
3. **兼容性测试套件**：对抽象后的 Provider 实现和原始调用做 diff，确保行为一致

### 是否需要新抽象层

**是**，强烈建议引入：

| 抽象层 | 必要性 | 优先级 |
|--------|--------|--------|
| Provider 接口 | 必要——解除服务绑定 | P0 |
| 带重试的调用包装 | 必要——当前无任何容错 | P0 |
| 配额调度器 | 推荐——最大化配额利用率 | P1 |
| 断路器 | 推荐——防止级联故障 | P1 |

## 4. 技术选型

### 当前约束评估

- **不引入外部依赖**（已有约束：forge-core 零依赖）
- **Node/Python 可以轻量使用**（已有约束：harness 零外部依赖）
- 需要**轻量、可控、适合嵌入式场景**的解决方案

### 推荐方案

| 组件 | 选型建议 | 理由 |
|------|---------|------|
| **令牌桶算法** | 手写（~50 行） | 零依赖，完全自控 |
| **断路器** | 手写（~80 行） | 核心逻辑简单，无需框架 |
| **Provider 抽象** | 接口 + 注册表模式 | 内建多态支持，运行时动态选择 |
| **缓存** | LRU 内存缓存（手写） | 无外部存储，适合 CI 场景 |
| **配额告警** | stdout 日志 + exit code | 零依赖，后续可对接任意告警平台 |

### 自建 vs 采购

| 决策 | 推荐 | 理由 |
|------|------|------|
| AI Provider 抽象 | **自建** | 核心架构有需求，代码量小（<200行），完全可控 |
| 令牌桶/断路器 | **自建** | 经典算法，成熟可预测 |
| 可观测性后端 | **复用现有** | 如果已有 ELK/Grafana，直接对接 |
| AI 模型推理 | **采购/托管** | 自建 GPU 推理成本远高于托管 API，且非本系统核心能力 |

### 第三方依赖评估标准

对于任何新引入的依赖，按此标准评估：

1. **必要性**：是否能用 50 行手写代码替代？
2. **稳定**：是否 1.0+，有长期维护记录？
3. **体积**：tree-shaking 后是否 < 50KB？
4. **许可**：MIT/Apache-2.0？是否与项目兼容？
5. **审计**：无已知 CVE，无敏感网络请求

## 5. 实施路线图

### 优先级矩阵

```
高影响
  │
  │   P0: Provider 抽象        P1: 配额感知调度
  │   P0: 重试+断路器          P1: 多供应商支持
  │   P0: 基础可观测性
  │
  └───────────────────────────────→ 低努力
  │   P2: 缓存层
  │   P2: 高级告警
  │
  低影响
```

### 阶段划分

#### 阶段 1 — 止血（1-2 天）

| 任务 | 说明 | 产出 |
|------|------|------|
| P0 | 在 AI 调用点插入重试逻辑（指数退避） | 429 不再直接致命 |
| P0 | 添加预配额检查（读取响应头中的 `X-RateLimit-Remaining`） | 在超限前主动等待 |
| P0 | 记录基础 metrics（调用次数、耗时、错误类型）到结构化日志 | 可观察失败模式 |

**里程碑**：即使遇到配额限制，不掉 exit code 1。

#### 阶段 2 — 架构加固（1 周）

| 任务 | 说明 | 产出 |
|------|------|------|
| P0 | 定义 `AIProvider` 接口，重构所有调用点 | 解除对单一提供商的绑定 |
| P1 | 实现令牌桶调度器，按配额窗口排期 | 消除突发超限 |
| P1 | 实现断路器状态机（3 状态） | 隔离故障提供者 |

**里程碑**：可运行时切换供应商，配额用尽时自动排队而非失败。

#### 阶段 3 — 智能化（2-3 周）

| 任务 | 说明 | 产出 |
|------|------|------|
| P1 | 接入第二个 Provider（如通过 Claude API） | 实际故障切换能力 |
| P2 | 实现结果缓存（按文件 hash） | 节省配额 |
| P2 | 构建配额使用仪表板 | 可视化管理 |

**里程碑**：多供应商自动 failover + 配额利用率提升 50%+。

### 风险点与缓解策略

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| Provider 抽象过度设计 | 🟡 中 | 🟡 中 | 先做最小可行接口（3 个方法），后续按需扩展 |
| 缓存导致 AI review 结果过时 | 🟢 低 | 🔴 高 | 缓存 TTL 短（5min），显式缓存失效策略 |
| 断路器误判导致功能降级 | 🟡 中 | 🟡 中 | 稳定期（cooldown）可配置，支持手动复位 |
| 多 Provider 结果不一致 | 🔴 高 | 🟡 中 | 对关键任务（代码审查）使用主 Provider + 不一致时告警 |

---

## 总结

当前系统对外部 AI 编码助手的**硬依赖**和**无容错设计**是核心架构短板。这次 `GoUsageLimitError` 暴露了架构中缺乏的三个关键能力：

1. **弹性**（Resilience）—— 无断路器、无降级、无重试
2. **抽象**（Abstraction）—— 直接绑定具体供应商 API
3. **可观测**（Observability）—— 完全透明，无法诊断和预警

建议从 **阶段 1（止血）** 开始，用最少改动在最短时间内使系统对配额限制有韧性，再逐步推进到多供应商架构。核心原则是：**不把 AI 变成关键路径上的单点故障**。
