# 架构分析报告：ForgeOS 四项基础设施债深度评估

## 1. 架构评估

### 当前架构优势

**ForgeOS 的架构设计展现了几个突出的工程质量特征：**

1. **载重墙（Load-Bearing Wall）设计清晰**。项目最精妙的设计决策是将「带外执法层」确立为真相之源，host hook 仅为加速器。这个选择从根本上解耦了治理逻辑与执行宿主——无论下游采用 Claude Code、Codex 还是 Gemini CLI，治理纪律不受侵蚀。这是 Kubernetes 式控制面/数据面分离的务实下沉，避免了与具体 CLI 版本绑定的风险。

2. **中枢旋钮（mode × lifecycle）是模式级杠杆**。单个设置同时驱动 Router 档位、Harness 严格度和 Workflow 深度，避免了 N 个独立配置项间的组合爆炸。这种「一个杠杆调三处」的设计比分散的 feature flag 治理更安全，因为减少了「忘记同步配置」导致的安全漏洞面。

3. **诚实（honesty）文化已制度化**。从代码注释到 sprint 回顾，N/A 不伪造、gap 不掩盖、延迟声明附有引用。这在工程层面转化为可观察的架构收益：每个适配器（lint/coverage/SCA）都遵循「探测 → 可配可用 → 降级 N/A」三态模式，避免了 false-pass 风险。这不是文化口号，是架构模式。

4. **增量交付纪律落地扎实**。north-star 存在但不被用作 excuse 来镀金 day-1 微服务；每版有独立验证条件，先拆分再继续是硬闸门。

### 局限性

1. **资源可观测性的结构缺口**——这是我评估中最值得关注的架构债务。`trace.Event` 只有延迟/cost，没有 CPU/内存/IO。这意味着 forge-core 对一个子进程的「健康/异常」判断只能基于 exit code 和延迟，而非资源消耗画像。这不是「加个字段」的问题：它意味着系统无法区分「进程因逻辑错误退出」和「进程因 OOM 被 kill」，两者都只是 `exit code != 0`。当 agent 在用户预算下运行时，没有资源画像就无法做容量规划或异常检测。

2. **配置面安全没有纵深防御**。`--approved` 是纯 bool flag，`FORGE_AGENT_DEPTH` 靠信任环境变量，`projectYAMLValue` 用行扫描而非结构化解析。这暴露出一个架构层面的问题：**配置信任边界没有建模**。当前架构隐含假设「配置源（project.yml、环境变量、CLI 参数）在同一个信任域内」，但这个假设在 agent 自治场景下的合理性随时间递减——agent 可以写文件、设环境变量、调 CLI。

3. **Go 层与 Python harness 层的桥接没有契约测试**。`yaml2json.py` 的输出格式变化会直接导致 Go 侧 `json.Unmarshal` 静默失败。这不是「加个测试」的问题，而是两套运行时（Go + Python）之间的接口定义没有显式 schema——共享的只有运行时行为。当 YAML 转码由 Python shim 完成而消费端是 Go 编写者时，缺失的是**一个跨进程的接口契约**。

4. **「示例即 dogfood」的策略缺少自动化护栏**。`examples/` 下有端到端真实应用（url-shortener、go-taskd）但 CI 从不运行它们。这意味着治理层（ForgeOS 自己）的回归可能破坏被治理层（示例）的构建/测试，而直到有人手动运行示例时才会发现。这不是示例本身的测试覆盖率问题（它们有测试），而是**回归检测的覆盖范围问题**。

### 关键设计决策评估

| 决策 | 评价 |
|------|------|
| 「带外执法为真相之源」 | **优秀**。唯一能在异构宿主间保持一致的策略。 |
| 「纯标准库零依赖」 | **合理但有代价**。避免了 supply-chain 风险，但 YAML 解析依赖 Python shim 引入的桥接复杂度是权衡结果。当前选择「保持零依赖」优于「加 Go YAML 库」，因为 bridge 的稳性可以通过契约测试解决。 |
| 「trace.Event 只有延迟/cost」 | **可理解的 v1 剪裁，但有遗留成本**。v1 的焦点是流程可观测性（执行了什么、花了多久），而不是资源可观测性（消耗了多少）。当系统进入自治运行后，资源视角变得必要。 |
| 「配置以文件为中心（project.yml）」 | **合适但缺少完整性保护**。文件作为声明式配置源是正确的，但配置消费链缺少哈希/签名校验或至少意外的 key 检测。 |
| 「先拆分再继续」 | **优秀**。直接防止了当前 sprint 中多个文件超过 500 行 LIMIT 的情况。 |

## 2. 扩展方向

### 方向 A：资源级可观测性子系统（P1）

**为什么需要**：当前 `trace.Event` 只记录延迟和成本，缺少 CPU/内存/IO 维度。在 agent 自治场景下越早异常检测越有价值——资源泄漏（内存/文件描述符）比逻辑错误更隐蔽也更昂贵。同时，资源画像对成本归属和容量规划至关重要。

**核心挑战**：
- 跨平台资源采集接口不统一（Linux `rusage`、macOS `task_info`、BSD `getrusage`），需要抽象层
- 子进程已结束时采集（`Wait4`）的信息更准确但失去了时序
- 无侵入采集 vs 性能开销的权衡

**预期的架构变更**：
- `command_executor.go` 中新增 `ResourceMonitor` 接口，在 `setupProcessGroup` 时启动带外采集 goroutine（使用 `/proc/[pid]/stat` 或 `rusage` 轮询）
- `trace.Event` 新增 `omitempty` 资源字段（`CPUMs`、`PeakMemoryKB`、`MaxOpenFDs`、`IOBytesRead/Write`）
- `scorecard` 新增资源维度（p95_cpu_ms、avg_memory_kb）
- 诚实地降级：平台不支持时 omit 不编 0

**对现有系统的影响**：影响在增量层。新增资源字段在 trace JSONL 中约 120 字节额外开销（最坏情况），对现有消费者（scorecard、telemetry）向后兼容。`CommandExecutor` 的 `Observe` 回调签名不改变——资源信息作为可选补充通过 `trace.Event` 传播。

### 方向 B：配置信任边界建模（P1）

**为什么需要**：验证报告确认了四个配置面攻击向量（`FORGE_REPO_ROOT` 环境变量覆写、`--approved` 无认证、`projectYAMLValue` 注释中提取值、`FORGE_AGENT_DEPTH` 可伪造）。当前架构隐含假设「所有配置源来自可信系统管理员」，但在 agent 自治场景下不是这样——agent 可以写 project.yml、可以设环境变量、可以调 CLI 参数。需要明确的信任边界。

**核心挑战**：
- 配置源有多种（文件、环境变量、CLI 参数、子进程继承），各自的可信度不同
- 一个配置源的覆盖不应自动信任来自不同源的配置
- 向后兼容：现有用户不配置任何安全措施也能工作

**预期的架构变更**：
- 新增 `config/trust.go` 层，明确定义配置源的**可信度等级**：hardcoded > CLI flag > env var > 文件 > 继承环境
- `main.go` 的变量绑定改为通过信任层，而非直接 `os.Getenv` + `flag.BoolVar`
- `--approved` 改为需要签名或至少 `[approved_by: <identity>]` 格式（简单启用，无 PKI 负担）
- `projectYAMLValue` 改为结构化 YAML 解析（Go 标准库无 YAML，可通过 python shim 或等 v2 依赖决策在 go-zero-dep 阶段后引入 YAML 库）
- 敏感配置项（`FORGE_AGENT_DEPTH`、`FORGE_REPO_ROOT`）在跨进程边界时被 `command_executor.go` 的 `childEnv` 显式清理或覆写，而非从父进程静默继承

**对现有系统的影响**：高影响——涉及核心配置路径。但可通过渐进方式部署：第一阶段加信任注释和跨进程 env 清理（安全加固，不改变行为），第二阶段加配置源跟踪和告警（预警不阻断），第三阶段加签名/校验（安全阻断，可降级）。

### 方向 C：跨语言桥接契约测试框架（P2）

**为什么需要**：Go（forge-core）和 Python（harness/yaml2json、check.py）之间的桥接没有显式契约。`yaml2json.py` 输出格式变化可以导致 Go 侧静默失败——这已经在 Sprint 27 的 block-scalar bug 中真实发生过。Python→Go 桥在 v2 架构中会持续存在一段时间（Go 标准库无 YAML，零依赖策略不引入），所以需要一个系统性的防护。

**核心挑战**：
- 契约定义在哪个层：Go struct（现有）、JSON schema、protobuf、还是简单 fixture？
- 如果不引入外部依赖（保持 zero-dep），契约只能是 fixture-based 或 Go struct-based
- 多个 Python shim（yaml2json.py、check.py、mode_gating_check.py）需要覆盖

**预期的架构变更**：
- 为每个 Python→Go 桥创建**契约 fixture 集**：已知输入 → 预期 JSON 输出（以 `.golden.json` 文件形式存储）
- 在 Go 侧，每包添加一个 `contract_test.go`，调用 Python shim 并将输出与 golden file 对比（类似 `yaml2json_test.go` 的 `TestToJSON_MatchesPythonShim` 但修复了其曾用 `t.Logf` 而非 `t.Errorf` 的问题）
- 在 CI 中，每次 `pip install` 或 `go generate` 触发契约测试
- 桥接接口定义在共享文档（如 `docs/interfaces/yaml2json.md`）中描述输入输出格式

**对现有系统的影响**：影响小。契约测试是新增文件，不修改现有代码路径。Golden file 是静态资产，测试是自包含的。

### 方向 D：示例回归检测自动化（P2）

**为什么需要**：项目有两个真实 dogfood 示例（url-shortener、go-taskd），CI 从不运行。这意味着治理层回归（如 go.mod 改变 Go 版本、新 harness 规则）可能破坏示例而不被发现。示例是项目可信度的核心——如果项目自己的示例不能通过自己的治理流程，治理的可信度就降低了。

**核心挑战**：
- 示例可能依赖外部资源（如 Go 编译器、Node 运行时、网络访问）
- CI 运行时间会随着示例数量线性增长
- 需要区分「示例回归」和「环境配置差异」

**预期的架构变更**：
- 在 CI YAML（`.github/workflows/forge.yml`）新增示例验证步骤，与主治理步骤并行（非串行）以减少延迟影响
- 轻量校验：对每个示例运行 `go build`（或 `npm test`），不运行完整的 `forge accept`（除非示例有自己的 gate）
- 对示例目录添加 `examples/.ci-skip` 支持，允许临时跳过已知环境问题（如更新失败）但标记为 CI 弱点

**对现有系统的影响**：非常低。仅 CI 配置变化，不涉及 forge-core 代码。

### 方向 E：成本/延迟的预测性治理（P3）

**为什么需要**：当前成本治理是反应式的（设置预算上限，超限熔断）。验证报告中的 sprint 历史展示了真实的成本溢出：Sprint 25 烧穿 budget，Sprint 26 才补齐 telemetry。预测性治理——基于历史数据估算每次 agent 调用的预期成本范围，超出范围时告警或降级——可以在熔断发生前提供更细腻的控制。

**核心挑战**：
- 成本预测需要足够的历史数据（cold-start 问题）
- 延迟分布可能是多模态的（不同阶段的 agent 调用成本差异大）
- 过度预测控制可能错误地拒绝合法的高成本调用（如复杂架构评审）

**预期的架构变更**：
- 新增 `internal/budget` 或扩展 `internal/risk` 包，从 scorecard 的成本历史数据计算运行均值和标准差
- 在 `engine_build.go` 的 `checkAgentBudget` 前增加**预期范围检查**：若当前调用的预测成本显著偏离历史分布（如 > 3σ），发出 advisory 级别警告而非阻断
- 支持 `--budget-forecast` flag 来启用预测检查（默认 off，保持向后兼容）
- 预测不准确时诚实降级：模型数据太少时跳过预测检查

**对现有系统的影响**：低。新增模块，不影响现有熔断路径。预测检查默认关闭。

## 3. 接口设计建议

### 关键模块接口原则

1. **`trace.Event` 扩展原则**：所有新字段应使用 `omitempty` 标记，保持 JSON 向后兼容。资源字段（`CPUMs`、`PeakMemoryKB` 等）应作为可选扩展而非必填字段。这允许 Observable 层渐进部署，不要求全部 executor 同时升级。

2. **配置信任层的引入原则**：可信度等级应该是**显式的叠加**而非隐式的优先级。建议一个 `ConfigKey` 类型携带来源注释：

   ```
   ConfigKey("FORGE_AGENT_DEPTH") → Source(CLI) > Source(Env) > Source(Inherited)
   ```

   而不是在 `main.go` 分散的 `os.Getenv` 调用中隐含这个顺序。

3. **桥接契约的接口原则**：每个 Python→Go 桥接点应有一个**单一职责的接口定义**，并在 Go 侧拥有可执行的契约测试（golden file 对比）。建议：

   - 同步操作（目前 yaml2json）：返回 `([]byte, error)` + 契约测试
   - 异步操作（check.py 调用）：返回 `(exitCode, stdout string, error)` + 契约测试

4. **可观测性接口的隔离原则**：资源采集应通过接口注入而非直接在 `CommandExecutor` 中内联实现：

   ```
   type ResourceCollector interface {
       Start(pid int) error
       Snapshot() (*ResourceSample, error)
       Close() (*ResourceSample, error) // 最终样本
   }
   ```

   这样可以在不支持资源采集的平台`返回 nil`（诚实降级），或为测试提供 mock。

### 是否需要引入新的抽象层

**需要，但范围有限：**

1. **配置信任层**是一个合理的抽象——当前配置消费分布在 `main.go`、`command_executor.go`、`gate.go`、`converge.go` 中，每个都独立读取 `os.Getenv` 和 flag。新增安全层面而不抽配置层会导致逻辑复制在 5+ 个文件中。但要注意不要造一个「配置框架」——泛化后的配置框架会与当前零依赖策略冲突，且会给 YAML 解析死灰复燃提供借口。建议只抽最小层：**tsafe（taint-safe）包**，提供值的读取和覆写/清理。

2. **资源采集层**是一个合理的抽象——不同平台、不同采集粒度、不同 overhead 需要接口隔离。但不要范式化到「可插拔资源采集框架」，保持一个接口 + 一个 goroutine 循环就够了。

3. **不要引入**新的跨语言 IDL（protobuf/thrift）。当前桥接点数量少（2-3 个）、复杂度低（JSON over stdin/out），protobuf 带来的 schema 强度收益不足以 justify 其引入成本。Golden file 契约测试 + 文档接口定义足够。

### 向后兼容策略

| 变更 | 兼容策略 |
|------|---------|
| trace.Event 加资源字段 | `omitempty`，旧 JSON 解析器忽略新字段 |
| 配置信任层 | 默认行为与当前一致（`trustAll` 模式），通过标志（`--config-trust-mode`）逐步收紧 |
| 契约测试 | 新增文件，不变更现有代码路径 |
| 示例 CI | 新增并行步骤，不阻塞现有 CI 路径 |
| 预测性成本治理 | 默认关闭（`--budget-forecast` flag），不影响现有熔断逻辑 |

## 4. 技术选型

### 是否需要引入新的技术栈或框架

**原则上不引入**。遵循项目「零外部依赖」的纪律。

具体分析：

| 候选技术 | 评估 | 结论 |
|---------|------|------|
| **Go YAML 库（如 go-yaml/v2）** | 消除 Python shim，简化桥接，但引入外部依赖，与零依赖策略冲突 | **与策略冲突，否决**。Python shim 的稳性可通过契约测试提升，不必要引入依赖。 |
| **eBPF / rusage 系统调用** | 资源采集的自然选择，`rusage` 是 POSIX 标准，不需要外部依赖，可在 Go 标准库 `os.Wait4` 或 `syscall.Wait4` 中获取 | **推荐**（零外部依赖）。Go 标准库 `os` 包没有直接暴露 `rusage`，但 `syscall.Wait4` 可用。Linux `/proc/[pid]/stat` 可作为轮询补充（文件读取，无需外部依赖）。 |
| **OpenTelemetry** | 可观测性标准，但引入外部依赖和配置复杂度 | **否决**，与零依赖策略冲突。当前 JSONL trace 文件 + scorecard 的轻量方案够用。 |
| **JSON Schema** | 用于跨语言契约定义，但需要 schema 验证库 | **不引入**。Golden file 对比 + 文档够用。 |
| **testcontainers / docker** | 用于隔离示例测试但增加 CI 依赖 | **否决**，过度复杂。当前简单编译/测试验证够用。 |

**结论**：所有四个方向的实现都可以在**现有 Go 标准库 + Node/Python 无额外依赖**的约束下完成。不需要引入任何新的外部依赖。

### 第三方依赖评估标准（为未来决策参考）

如果将来考虑引入依赖，应使用以下标准：

1. **许可证兼容**（MIT/Apache 2.0/BSD，不引入 GPL）
2. **零传递依赖**（或传递依赖可管理）
3. **Go 标准库替代评估**——引入前必须穷举「标准库能实现吗」
4. **最小可用 API surface**——不要引入像框架一样大的库
5. **权威治理层接触面**——依赖不应进入配置信任或执行路径的 critical path

### 自建 vs 采购

当前所有方案都是自建，且应该保持自建。理由：

1. **治理面是核心差异**——ForgeOS 的护城河是其治理模型，而不是使用的具体技术。配置信任、资源采集、桥接契约是治理面核心能力，外包给第三方会侵蚀差异。
2. **外部依赖会增加 supply-chain 风险**——对于一个旨在治理其他项目的元框架，自身依赖的安全性是一个额外的可信度负担。
3. **当前方案够用**——rusage 是 POSIX 标准，golden file 是零依赖的测试方法，配置信任层可以用 Go 标准库实现。

唯二适合采购的是已经明确列出的：Firecracker（沙箱隔离）、Temporal（长时 workflow 引擎）、LiteLLM（跨厂商模型路由）——这些属于基础设施面，不是治理面。

## 5. 实施路线图

### 优先级排序

| 方向 | 优先级 | 为什么 | 价值/风险比 |
|------|--------|--------|-------------|
| **B: 配置信任边界建模** | **P1** | 当前有可被利用的模式，安全缺口真实存在 | 高（减少攻击面）/低（可渐进） |
| **A: 资源级可观测性** | **P1** | OOM/kill 退出的区分对自治场景关键，trace 数据现在就有缺口 | 高（运维必要）/低（std lib 可用） |
| **C: 桥接契约测试** | **P2** | 已有 block-scalar bug 先例；触发概率中等但触发时后果严重 | 中（防止退化）/低（测试开销小） |
| **D: 示例回归检测** | **P2** | CI 从不跑示例，但示例数量少（2个），并行步骤开销可忽略 | 中（回归保护）/极低（CI 配置变更） |
| **E: 预测性成本治理** | **P3** | 增值功能，不是安全性或可观测性必备 | 中（成本控制更细腻）/中（需设计） |

### 阶段划分

```
阶段一：安全基建（Sprint N + 1 sprint）
  目标：消除可被利用的配置安全缺口
  - 配置信任层最小实现：跨进程 env 清理 + 配置源跟踪
  - FORGE_AGENT_DEPTH 跨进程显式覆写
  - projectYAMLValue 改为结构化解析（通过现有 python shim）
  - --approved 改为标记格式校验
  可交付：安全基线加固完成，现有测试全绿

阶段二：可观测扩展（Sprint N + 2~3 sprint）
  目标：为自治运行时补充资源级可见性
  - ResourceCollector 接口定义
  - Linux 实现（rusage + /proc/stat 轮询）
  - trace.Event 可选扩展字段
  - scorecard 资源维度
  - 桥接契约测试框架（并行推进）
  可交付：CPU/内存/IO 精度可用，跨语言契约保护就位

阶段三：回归检测自动化（Sprint N + 4 sprint）
  目标：CI 覆盖示例，防止治理层回归
  - CI 并行示例构建/测试步骤
  - 示例 .ci-skip 优雅降级机制
  - 合并前自动验证
  可交付：示例回归检测集成到 CI

阶段四：预测治理（Sprint N + 5 sprint，可跳过）
  目标：从反应式熔断升级为预测性成本控制
  - 历史成本分布模型
  - 预期范围检查
  - --budget-forecast flag
  可交付：预测性成本治理可用但默认关闭
```

### 风险和缓解策略

| 风险 | 影响 | 可能性 | 缓解策略 |
|------|------|--------|----------|
| 配置信任层过度工程化 | 膨胀代码库，增加复杂度 | 中 | **保持最小层**。只抽取 taint-safe 包，不做配置框架。设定明确的「不做清单」（不引入 YAML 解析、不做 PKI、不做配置编排）。 |
| 资源采集的平台差异 | 功能退化或性能问题 | 中 | **诚实降级**。不支持的平台 omit 不编 0。平台检测在 `init()` 执行，不是运行时。 |
| 桥接契约测试的 fixture 漂移 | 测试与接口不一致 | 低 | **golden file 作为唯一契约源**。接口变更必须先更新 golden file，CI 检查文件一致性。 |
| 示例 CI 步骤影响主 CI 稳定性 | 开发者体验退化 | 中 | **示例测试与主治理并行，独立失败**。示例 CI 步骤失败不阻塞核心 CI 判定。 |
| 预测治理误告警导致信任损失 | 运维者忽略预测告警 | 中 | **默认关闭，advisory 模式先于 warning**。历史数据少于 10 个样本时不发出预测。 |

### 总风险暴露

四个方向的风险都在可控范围内。最值得注意的架构风险是**方向 B 和方向 C 的交叉影响**：配置信任层（B）会改变 `main.go` 的配置消费方式，而方向 C 的契约测试对 `main.go` 的 Python shim 调用路径加测试。两方向在 `main.go` 有代码路径冲突风险。缓解方式：**阶段一（B）优先完成，阶段二（C）在已变更的代码上叠加契约测试**——不尝试并行修改同一模块。

---

## 结论

这份基础设施债分析是一次**扎实的架构审查**。四个方向都对应真实的代码级证据，优先级分级合理。从架构角度，最重要的洞察是：

1. **配置信任边界建模（方向 B）** 是当前安全性最值得关注的问题——不是因为系统被攻破了，而是因为系统设计隐含的信任域假设在 agent 自治场景下不再成立。
2. **资源级可观测性（方向 A）** 是 v1→v2 的关键架构缺口——当前 trace 可以回答「跑了多久、花了多少」，但回答不了「是不是内存泄漏了」。
3. **桥接契约测试（方向 C）** 和示例回归（方向 D）是保护治理层自身可信度的工程投资，不是功能特性。
4. **预测性成本治理（方向 E）** 是增值方向，不是当前瓶颈。

所有方向都可以在项目现有「零外部依赖/诚实降级/增量交付」的纪律下实施，不需要范式转移或引入新框架。
