# 架构分析报告：LLM API 限流故障引发的系统韧性设计

## 1. 架构评估

### 当前架构推断（基于 429 错误特征）

从错误信息推断，系统有以下结构特征：

| 特征项 | 推断 |
|--------|------|
| **编排方式** | 存在一个长时间运行的任务（elapsed=37.2s）调用外部 AI API，很可能是批处理/工作流式编排 |
| **依赖模型** | 硬编码使用单一模型（`Go`），无 fallback |
| **错误处理** | 异常未被优雅捕获，以 `exit=1` 直接失败，无重试或降级 |
| **配额管理** | 无本地用量追踪，依赖 API 返回 429 后才被动感知 |
| **超时控制** | 37.2s 的任务耗时说明不是毫秒级短请求，可能是多轮对话/链式调用 |

### 优势

- **简洁直接**：对单一 API 的直接调用模式降低了初始开发复杂度。
- **快速迭代**：没有引入复杂的重试/降级抽象层，早期产品验证速度快。

### 局限性

- **脆性关联（Brittle Coupling）**：系统与单一外部 LLM API 之间形成了紧耦合。API 的任何故障（限流、超时、模型下线）都直接导致业务流程完全中断。
- **零容错设计**：没有重试策略（尤其是带指数退避）、没有熔断器、没有降级路径。在 37.2 秒的任务中，一旦遭遇 429 即全盘失败，浪费了此前所有计算资源。
- **无可见性**：没有在调用前检查配额状态，说明缺乏对基础设施健康度的主动监控。
- **无成本控制机制**：5 小时用量配额消耗完毕才暴露问题，说明缺乏用量预警和软限制。

### 架构债务与技术债

1. **错误处理债务**：`exit=1` 是最原始的失败模式。需要建立结构化错误体系（可重试 vs 不可重试、客户端 vs 服务端）。
2. **配置债务**：模型名称、API endpoint、配额阈值硬编码在业务逻辑中，缺乏集中配置管理。
3. **观测性债务**：缺失调用计数、延迟分布、错误率、配额水位等关键指标。
4. **测试债务**：无法轻松地在不消耗真实配额的条件下对限流场景进行测试。

## 2. 扩展方向

### 方向 1：引入多模型路由与智能降级

- **为什么需要**：解决本次故障的直接原因——单一模型不可用时系统瘫痪。业务价值在于提高 SLA 和任务完成率。
- **核心挑战**：
  - 不同模型的输出质量、成本、延迟差异大，需要路由策略来平衡。
  - 降级时应能无损恢复上下文，而不是从零开始。
  - 需要评估哪些任务可以安全降级到次优模型，哪些不允许。
- **预期架构变更**：
  - 引入 `ModelRouter` 抽象层。
  - 每个请求携带 `ModelRequirements`（最低能力标签、最大延迟 SLA、最大成本预算）。
  - 路由策略支持：primary → fallback chain 直连、基于历史成功率概率路由、基于配额余量动态切换。
- **对现有系统的影响**：
  - 中高。需要重构所有直接调用 API 的代码改为通过 `ModelRouter`。
  - 需要引入模型能力评估体系（benchmark 基准测试）。
  - 可能会改变 response 格式的一致性（不同模型 output 格式差异需对齐）。

### 方向 2：构建本地配额管理与渐进式背压

- **为什么需要**：避免 429 完全突袭，在配额耗尽前就能做出调整。技术价值在于将外部错误转化为内部可控策略。
- **核心挑战**：
  - 配额信息通常没有实时 API 可查询，只能通过历史消耗和限流响应反向推算。
  - 多线程/多任务并行时的配额记账需要线程安全且高性能。
  - 需要区分"配额定额耗尽"和"瞬时并发限流"，处理策略不同。
- **预期架构变更**：
  - 引入 `QuotaTracker` 组件，本地维护一个 `token bucket` 或 `sliding window` 计数器。
  - 请求发出前先检查本地配额预估，预估不足时自动排队或降级。
  - 每次 API 响应中提取 `X-RateLimit-Remaining` / `Retry-After` 头来校准本地计数器。
- **对现有系统的影响**：
  - 低到中。如果设计为装饰器/中间件模式，现有业务代码改动量很小。
  - 需要增加配置项：配额上限、预警阈值、硬限制。

### 方向 3：引入异步任务编排与可恢复工作流

- **为什么需要**：37.2 秒的长时间任务表明这是一个多步骤工作流。当前在任意步骤失败就全丢弃是极大的浪费。业务价值在于提高任务完成率和资源利用率。
- **核心挑战**：
  - 工作流步骤的状态持久化：中间结果该存哪里？如何序列化？
  - 部分可恢复：如果第 3/5 步失败，是重做第 3 步还是回退到第 1 步？
  - 幂等性保证：重入执行时不能产生重复副作用（如日志、计费）。
- **预期架构变更**：
  - 引入 `WorkflowEngine` 或基于状态机的工作流抽象。
  - 每个步骤输出持久化到 DB 或对象存储。
  - 失败时自动标记步骤为 `FAILED`，根据重试策略决定：`RETRY_SAME` / `FALLBACK_DIFFERENT` / `ABORT_AND_NOTIFY`。
- **对现有系统的影响**：
  - 高。从同步阻塞调用改为异步持久化工作流是根本性架构变化。
  - 需要引入任务队列（如 Bull、Celery、Temporal）和持久化存储。
  - 引入了最终一致性复杂度。

### 方向 4：构建成本与用量观测面板

- **为什么需要**：5 小时配额用完才被发现，说明缺乏主动监控。业务价值在于成本可预测、可控制。
- **核心挑战**：
  - 配额的计量口径可能和 API 返回不一致（计费 token vs 显示 token）。
  - 需要关联到业务维度（哪个项目/哪个用户/哪个模型消耗了多少）。
- **预期架构变更**：
  - 新增 `UsageCollector` 作为一个切面/中间件，记录每次调用的元数据（时间、模型、输入/输出 token 数、成本估算、慢速/快速、成功/失败）。
  - 将数据输出到时序数据库（如 Prometheus + Grafana，或 CloudWatch）。
  - 设置按严重级别递增的警报：WARN@70% → CRITICAL@90% → BLOCK@100%。
- **对现有系统的影响**：
  - 低。通过中间件模式或 AOP 无侵入插入，业务代码不需改动。

### 方向 5：实现从失败上下文中自动恢复的机制

- **为什么需要**：当前 task 运行 37.2s 后失败，这 37.2s 的上下文完全丢失。如果能捕获并在配额恢复后恢复，能显著提升效率。
- **核心挑战**：
  - 大量上下文（完整对话历史、中间推理结果）的序列化与存储。
  - 自动恢复后是否需要人工 Review 还是完全自动提交。
  - 配额恢复时间不固定（45min），需要一个等待/轮询机制。
- **预期架构变更**：
  - 将当前 task 状态保存为 `Checkpoint`（进程级快照）。
  - 捕获 `QuotaExhaustedException` 时，不退出，而是进入 `WAITING_FOR_QUOTA` 状态。
  - 后台定时检查配额状态（或监听 webhook），恢复后从 Checkpoint 继续。
- **对现有系统的影响**：
  - 中。Checkpoint 的序列化/反序列化增加了复杂度。
  - 需要考虑 checkpoint 过期策略和存储增长问题。

## 3. 接口设计建议

### 关键模块接口设计原则

**原则 1：面向失败设计（Design for Failure）**

所有外部 API 调用应当默认失败是常态。接口签名应当显式表达这一点：

```
推荐（隐式故障）：
  function callLLM(prompt: String) -> Response

不推荐（显式封装故障域）：
  function callLLM(prompt: String, options: CallOptions) -> Result<Response, LLMError>
```

其中 `LLMError` 是一个 tagged union/sealed class，明确区分：
- `QuotaExhausted`（可恢复，等待后重试）
- `RateLimited`（可重试，带 backoff）
- `ModelUnavailable`（可降级到其他模型）
- `InvalidRequest`（不可重试，客户端错误）
- `InternalError`（不可重试，服务端错误）

**原则 2：依赖倒置 —— 依赖于抽象，不依赖于具体 API**

```
现状：     Analyzer → OpenCodeAI.Go  (直接依赖具体模型)
目标：     Analyzer → ModelInterface  (依赖抽象)
                       ↑
              OpenCodeAIModel.implements(ModelInterface)
              LocalModel.implements(ModelInterface)
              MockModel.implements(ModelInterface)
```

**原则 3：显式契约（Explicit Contract）**

每个模型的接口应当声明其能力特征：

```typescript
interface ModelCapabilities {
  maxTokens: number;
  supportsFunctionCalling: boolean;
  supportsVision: boolean;
  avgLatencyP50: Duration;
  costPer1KTokens: Money;
}
```

调用方根据任务需求声明需求，由路由器匹配。

### 是否需要引入新的抽象层

**需要。推荐引入以下三个新抽象层：**

| 抽象层 | 职责 | 是否可选 |
|--------|------|----------|
| `LLMGateway` | 统一接入点：路由、重试、限流适配 | **必需** — 解决本次故障的核心 |
| `QuotaManager` | 本地配额跟踪、预检、预警 | 强烈推荐 |
| `WorkflowOrchestrator` | 多步骤任务的持久化编排与恢复 | 视任务复杂度而定 |

### 如何保持向后兼容性

1. **Facade 模式**：新抽象的默认行为与旧代码完全一致（`usePrimaryModelOnly`），通过配置开关逐步启用新特性。
2. **渐进式迁移**：
   - 阶段 1：所有调用保持原逻辑 + 新增 `LLMGateway` 作为可选包装器。
   - 阶段 2：默认路由改为 `LLMGateway`，但 `fallback=false, retry=0`，行为不变。
   - 阶段 3：逐步开启重试、降级、配额管理。
3. **特征开关（Feature Flag）**：每个新功能都有独立开关，可灰度发布。
4. **Deprecation 周期**：旧直接调用 API 的方式标记 deprecated，预留一个 major 版本的过渡期。

## 4. 技术选型

### 是否需要引入新技术栈或框架

基于务实的"最少增量"原则，我不主张引入大型分布式框架。以下是成本效益权衡：

| 技术需求 | 推荐方案 | 替代方案 | 选择理由 |
|---------|---------|---------|---------|
| 重试与熔断 | 内置中间件（10-20 行核心逻辑） | Resilience4j / Polly / Failsafe | 零依赖，刚好够用 |
| 任务持久化 | 已有 DB + JSON column | Temporal / Airflow / Celery | 当前规模下自维护状态机更轻量；若工作流节点 > 10 个或跨进程，再考虑专用引擎 |
| 观测指标 | Prometheus client + 自定义 metrics | Datadog / NewRelic agent | 开源免费，本地存储，不产生额外 API 成本 |
| 配额跟踪 | 自建 token bucket（内存 + 可选 Redis） | AWS AppConfig / LaunchDarkly | 需求非常特定，通用 feature flag 系统反而冗余 |

### 第三方依赖评估标准

所有候选依赖应通过以下评估矩阵（权重从左到右递减）：

```
1. 安全审计通过（CVE 扫描）           → 否决项
2. 零外部传递依赖（transitive deps）  → 加分项
3. 兼容当前 Node/Python 主版本        → 否决项
4. 最近 6 个月内有活跃提交            → 必要条件
5. 周下载量 > 10,000（Node）/ > 100,000（Python）→ 参考
6. Apache 2.0 / MIT 许可证            → 必要条件
7. 类型定义（TypeScript / type stubs）→ 加分项
```

### 自建 vs 采购的决策依据

| 决策 | 自建 | 采购/开源 | 我们的选择 |
|------|------|-----------|-----------|
| 模型路由 | 核心业务逻辑，差异化竞争力 | 通用网关（如 OpenRouter） | **自建核心**；可考虑套 OpenRouter 作为 fallback provider |
| 配额管理 | 业务特定规则，通用方案往往不匹配 | No | **自建** |
| 工作流编排 | 若复杂度低 | Temporal / Airflow | 当前 **自建简化版**；复杂度超阈值时迁移到 Temporal |
| API 代理/网关 | 非核心 | Kong / APISIX / Envoy | **采购开源**，专注于业务层 |

**自建 vs 采购的核心决策规则**：
- **如果是核心差异化竞争力，自建。**（模型路由策略直接影响输出质量和成本）
- **如果是基础设施管道，采购/复用开源。**（API 网关、监控、消息队列）
- **如果采购成本 > 自建成本 × 3 年，且团队有能力维护，自建。**

## 5. 实施路线图

### 优先级排序

| 优先级 | 项 | 理由 |
|--------|----|------|
| **P0** | 重试 + 指数退避 + 有限降级 | 最直接的止损方案；可在不改变架构的前提下实现 |
| **P0** | 错误类型结构化区分 | 所有后续改进的前提 |
| **P1** | 本地配额跟踪 + 本地预检 | 主动防御，避免 429 突袭 |
| **P1** | 观测指标（调用计数/错误率/延迟） | 获得 Visibility 才能谈优化 |
| **P1** | 多模型路由抽象层 | 核心架构改进，但改动量较大 |
| **P2** | 工作流持久化与 Checkpoint 恢复 | 需要较大的存储和状态管理设计 |
| **P2** | 成本控制面板与用量预警 | 非功能需求，可后续完善 |

### 阶段划分和里程碑

```
阶段 1 — 止血（预计 1-2 天）
├── 为所有外部 LLM 调用添加 retry + exponential backoff
├── 捕获 429 后自动等待 Retry-After 头重置时间
└── 里程碑：同类 429 故障不再导致任务失败，而是自动恢复

阶段 2 — 防御（预计 1 周）
├── 引入 ErrorHierarchy 结构化异常体系
├── 实现 QuotaTracker（内存版 token bucket）
├── 在调用前检查预估配额，不足时主动排队/降级
├── 实现简单的 Primary → Fallback 模型路由
└── 里程碑：单一模型配额耗尽时自动切换到备用模型继续工作

阶段 3 — 可观测（预计 3-5 天）
├── 添加调用计数器、延迟直方图、错误率仪表盘
├── 添加配额水位监控面板
├── 设置多级用量警报（70% / 90% / 100%）
└── 里程碑：成本用量实时可视化，预先收到配额预警

阶段 4 — 韧性提升（预计 2-3 周）
├── 完整的 ModelRouter 抽象层开发
├── 工作流 Checkpoint 持久化
├── 状态恢复机制（从 WAITING 恢复到 RUNNING）
├── 多 provider 支持（不止 OpenCode AI）
└── 里程碑：任意单点 LLM 服务不可用不影响业务流程完成
```

### 风险点和缓解策略

| 风险 | 概率 | 影响 | 缓解策略 |
|------|------|------|----------|
| 引入重试后导致 API 成本激增 | 中 | 高 | 重试次数上限（max 3）、退避时间硬限制、仅重试已知可恢复错误 |
| 降级到备用模型后输出质量下降 | 高 | 中 | 按任务类型分类：核心任务不允许降级（必须等待）、辅助任务允许降级 |
| 多模型抽象过度设计（YAGNI） | 中 | 中 | 阶段 2 不做完整抽象，只做 if-else fallback；阶段 4 才抽象，基于实际数据驱动 |
| 配额本地跟踪和实际 API 不一致 | 高 | 低 | 本地跟踪只是"预估"；以 API 响应头为最终校准来源；不一致时丢弃本地状态 |
| 工作流 Checkpoint 恢复导致状态不一致 | 中 | 高 | 恢复前做完整性检查；恢复失败时回退到"从初始重试"而非恢复 |

## 总结

本次 `429 GoUsageLimitError` 故障不是偶然的运维事故，而是系统架构中 **缺少容错层、缺少抽象层、缺少观测层** 这些结构性缺陷的必然暴露。

修复建议的核心思路可以概括为一句话：

> **不要信任外部服务的可用性，通过抽象层将外部失败转化为内部可控策略。**

优先级上，P0 项（重试 + 错误类型结构化）可以在 1 天内完成且不需要架构决策，建议立即执行。完整的架构演进则应在 4 周内分阶段完成，每个阶段都有可验证的里程碑。
