# 架构师分析：ForgeOS 扩展方向全景评估

## 1. 当前分析体系评估

已存在的 ~100 份分析文档覆盖了从引擎补齐、执行语义、生产可靠性到多仓治理、安全纵深等几乎所有维度。这是极其详尽的工作，但有一个核心问题：**广度远大于深度，且缺乏交叉验证**。

### 优势
- 每份文档都附有代码级证据（行号、函数名、文件路径），分析可信度很高
- 方向覆盖全面，从成本治理到运行时观测再到多仓治理，不存在明显的「空白大陆」
- 大部分分析诚实地标注了「差异化证明」，避免重复发明轮子
- 优先级分级（P0/P1/P2）提供了基本的决策框架

### 现有分析的局限性

| 问题 | 表现 | 风险 |
|------|------|------|
| **缺乏交叉验证** | 代码行证据来自 grep 而非运行时观察，某些推断可能是错的 | 决策建立在未经验证的假设上 |
| **方向重叠** | Event Gateway、Daemon、Webhook 在至少 5 份文档中分别提出，但未合并 | 重复工作、力量分散 |
| **优先级缺乏外部输入** | 优先级判断完全基于架构视角，没有用户/市场验证 | 可能做了正确但没人要的功能 |
| **忽略迁移路径** | 每个方向只描述「目标态」，极少讨论从当前到目标的增量步骤 | 团队不知道从何入手 |
| **Edge case 深度不足** | 跨领域 Edge Cases 只列出 5 个，实际远不止 | 上线后踩坑 |

## 3. 关键设计决策评审

### 决策一：Event Gateway 的时机

**分析文档主张**：P0，因为「没有事件驱动能力，ForgeOS 在 CI 管线中永远是手动步骤」。

**我的挑战**：这个判断假设了 ForgeOS 已经有外部用户想要 CI 集成。但根据 `.agent/CURRENT_SPRINT.md`，当前阶段的核心目标是**让核心引擎成熟**，而非拓展用户触达。Event Gateway 是销售功能，不是生存功能。没有它系统照样跑，没有多仓治理和预算引擎，企业用户不会碰。

**选项对比**：

| 选项 | 理由 | 风险 |
|------|------|------|
| **A: 保持 P0**（如原分析） | 品牌定义，「软件工厂」不能是手动的 | 分散有限工程资源，核心能力未稳前做集成层 |
| **B: 降为 P1**（推荐） | 先做多仓治理和预算引擎，待有真实外部需求时再启动 | 如果有人急需 CI 集成，需临时加急 |
| **C: 拆为两段** | Phase 1 只做 daemon mode（最小可行），Phase 2 再做 webhook | 需要额外的架构管理成本 |

**我的推荐**：**选项 B**。Event Gateway 的价值在 ForgeOS 有外部采用者之前是未被验证的假设。相反，多仓治理（方向三）是「元框架」承诺的兑现，预算治理（方向四）是企业采用的硬性前提。

### 决策二：预算治理引擎 vs. 简单 CLI 扩展

**分析文档主张**：引入声明式 `budget.yml` 策略文件，沿用 `mode.Policy` 的 YAML + Go 条件匹配模式。

**我的挑战**：这个设计方向正确，但需要回答一个前提问题——**当前有谁在为成本问题睡不着觉？** Sprint 26 显示单个 agent phase 约 $0.18，完整 build 迭代约 $1，24h evolve 跑 50 迭代约 $50+。这个成本水平对个人开发者是舒适的，对中小企业是可接受的，只有大企业才会紧张。

**建议**：
- 预算治理引擎的设计方向正确，但目前的实现时机应该与**真实用户采用**挂钩
- 先做一个轻量级方案：扩展 CLI flag 为 `--budget-policy` 指向 YAML 文件，解析器用 50 行 Go 代码实现条件匹配。不需要引入 `internal/budget/` 包，先在 `cmd/forge/` 层做
- 只有当用户反馈「需要更复杂的策略」时，才将其下沉为独立的 `internal/budget/` 包

**决策矩阵**：

| 标准 | 轻量 CLI 扩展 | 独立 budget 包 |
|------|--------------|---------------|
| 实现时间 | ~2 天 | ~1 sprint |
| 向后兼容 | ✅ 天然 | 需注意 |
| 灵活度 | 足够覆盖 90% 场景 | 可扩展至任意复杂策略 |
| 过度设计风险 | 低 | 高（如果策略需求从不出现） |

### 决策三：可观测性的优先级

**分析文档主张**：P2，因为「没有它依然能跑」。

**我的挑战**：我同意 P2 的分级，但要补充一个**颠覆条件**：如果 ForgeOS 要进行 daemon mode（Event Gateway 的 Phase 1），那么健康检查和结构化日志就从 P2 升为 P1。因为 daemon mode 意味着进程 24h 在后台运行，operator 需要知道它是否还活着。

**条件升级规则**：
- **If** daemon mode 启动 **then** `/healthz` 和 `forge stats` 的优先级提升至 P1
- **If** 外部用户接入 **then** Prometheus metrics 端点提升至 P1
- **If** 团队规模 > 3 人 **then** span 追踪提升至 P1

## 4. 优先级修正建议

基于代码走查验证和决策评审，我对优先级提出以下修正：

| 方向 | 原优先级 | 建议优先级 | 修正理由 |
|------|---------|-----------|---------|
| **多仓治理** (原方向三) | P0 | **P0** → 维持 | 这是 ForgeOS「元框架」承诺的兑现，分析准确 |
| **预算治理** (原方向四) | P1 | **P0** | 企业采用的硬性前提，比 Event Gateway 更关键；且可与多仓治理并行开发 |
| **运行时观测** (原方向五) | P2 | **P2** → 维持，但有条件升级 | 见上述条件升级规则 |
| **知识引擎** (原方向二) | P1 | **P2** | Learning loop 的数据积累需要先有足够的 run 才能提炼知识；目前 run count 还不够 |
| **Event Gateway** (原方向一) | P0 | **P1** | 价值取决于外部采用者的存在，当前阶段应优先核心能力 |
| **声明式输出验证** (边界盲点 方向二) | P2 | **P2** → 维持 | 重要但不紧迫 |
| **跨会话一致性** (边界盲点 方向三) | P1 | **P1** → 维持 | 多 session evolve 是真实场景 |
| **并发相位资源争用** (边界盲点 方向五) | P2 | **P2** → 维持 | 在 forge-core 确认存在并发 phase 前不应启动 |
| **SCA 复用** (文档中提及) | 未明确 | **P0** | 这涉及供应链安全，是合规硬性门禁 |

## 5. 技术选型建议

### 自建 vs 复用评估框架

对于分析中提出的每个新组件，我建议采用以下决策矩阵：

| 维度 | 评估标准 |
|------|---------|
| **核心差异化** | 该组件是 ForgeOS 的核心价值主张吗？是 → 自建 |
| **现有依赖约束** | 引入外部依赖是否违反「零外部依赖」红线？是 → 自建 |
| **领域复杂度** | 该领域的实现复杂度是否在 Go 标准库能力内？是 → 自建 |
| **生态成熟度** | 是否存在成熟、轻量、可嵌入的 Go 库？是 → 复用 |

### 具体评估

| 组件 | 评估 | 决策 |
|------|------|------|
| 预算策略解析 | 条件匹配逻辑简单，沿用 `mode.Policy` 模式 | **自建**（~50 行 Go） |
| OpenTelemetry 导出 | 不引入 vendor SDK，只用标准 `expvar` 或 `/metrics` 端点 | **自建**（Go `net/http` + `expvar`） |
| Webhook 解析 | 标准 `net/http`，无外部依赖 | **自建** |
| Git submodule 同步 | 标准 `os/exec` 调用 git，无外部依赖 | **自建** |
| YAML 解析 | 已在使用 `gopkg.in/yaml.v3` | **维持现有依赖** |
| SCA (软件组成分析) | 当前 `sca.mjs` 调用 OSV API；可考虑换为 `govulncheck` | **保持为 Node 脚本**，不引入 Go 依赖 |
| 向量检索/embedding | 排除，TF-IDF 足够 | **不自建**（明确 deferred） |

## 6. 风险矩阵

| 风险 | 概率 | 影响 | 缓解策略 |
|------|------|------|---------|
| 方向分散导致核心引擎不稳定 | 中 | 高 | 每次 Sprint 锁定 1 个方向，其余方向只在 ROADMAP 中保留 |
| 外部采用者需求与架构预判不匹配 | 低 | 高 | 在有外部用户前，所有 P1 方向保持增量可逆设计 |
| 多仓治理设计过度（Submodule + 双层覆盖） | 中 | 中 | Phase A 只做 `forge upgrade` diff-aware 合并，Submodule 延迟至至少 2 个项目接入后 |
| 预算策略过于简单导致后续重构 | 中 | 低 | 用 CLI flag → YAML file → 独立包的渐进路径，每次升级向后兼容 |
| 并发 phase 引入竞态条件 | 低 | 高 | 在明确需要并发执行之前，所有 phase 保持顺序执行 |
