# 架构分析报告

## 关于输入文档的说明

首先需要指出：**输入的所谓"分析文档"并非分析文档**，而是一条任务执行失败的 stderr 输出——一个 **HTTP 429 (Rate Limit)** 错误，来自 `opencode.ai` 的 Go 模型服务（`GoUsageLimitError`，5 小时用量上限触发，距重置还有 45 分钟）。

因此，以下分析不是针对一个架构文档的评审，而是**从这条错误本身推断系统架构中存在的设计问题**，并以此为切入点给出架构建议。

---

## 1. 架构评估

### 当前暴露的问题

| 问题 | 严重程度 | 说明 |
|------|----------|------|
| **外部 API 硬依赖** | 高 | 任务因第三方 API 限流而完全失败（exit=1），没有降级或重试机制 |
| **缺乏限流自治** | 高 | 系统自己没有用量管理，完全依赖上游的 "5-hour usage limit" 硬边界 |
| **错误信息透出混乱** | 中 | stderr 直接暴露了上游 JSON 错误体的内部结构（`GoUsageLimitError`），说明错误包装/抽象层缺失 |
| **没有熔断/退避** | 中 | 1.3s 内就失败了，没有指数退避重试 |

### 关键设计决策评估

这个错误的根源是一个**架构决策**：将对 `opencode.ai` Go 模型的 API 调用设计为同步阻塞的关键路径，且没有引入：
1. **用量配额代理层**（Proxy/Agent）—— 在客户端做速率限制和配额管理
2. **多模型故障转移**（Failover）—— 当 Go 模型限流时自动切换到替代模型
3. **优雅降级策略**（Graceful Degradation）—— 返回缓存结果或提供有限功能而非崩溃

### 架构债务

- **耦合债务**：任务执行器直接耦合到具体模型供应商的单一路径
- **弹性债务**：没有熔断器（Circuit Breaker）、重试+退避、超时控制等经典弹性模式
- **可观测性债务**：从输出看，失败信息没有被结构化地采集到 metrics/logging 系统

## 2. 扩展方向

### 方向 1：引入统一的 AI Provider 抽象层

**为什么需要**：当前系统硬编码了对 `opencode.ai` Go 模型的依赖。一个 Provider 抽象层可以让系统接入多个 LLM 提供商（OpenAI、Anthropic、本地模型等），实现故障转移和成本优化。

**核心挑战**：
- 不同提供商的 API 语义（streaming、tools、structured output）差异很大，抽象接口需要精心设计
- 某些模型能力不同（如是否支持 function calling），需要能力声明机制
- 需要统一的 token 计数和成本跟踪

**预期的架构变更**：
```
┌─────────────────┐     ┌──────────────────┐     ┌─────────────────┐
│   Task Executor  │────▶│  AI Provider     │────▶│  opencode.ai    │
│   (无感知)       │     │  Abstraction     │     │  OpenAI         │
└─────────────────┘     │  (路由/重试/      │     │  Anthropic      │
                        │   限流/降级)      │     │  Local (Ollama) │
                        └──────────────────┘     └─────────────────┘
```

**对现有系统的影响**：
- 需要重构所有直接调用 AI API 的代码点，改为通过抽象层
- 现有配置格式（如模型名称/endpoint）需要扩展
- 影响中等，可通过适配器模式逐步迁移

### 方向 2：本地用量配额与限流引擎

**为什么需要**：避免被上游 429 打个措手不及。系统应该在本地维护用量计费，在到达上游硬限制之前主动限流或切换。

**核心挑战**：
- 需要跟踪分钟级/小时级/日级的 token 消耗
- 多进程/多实例场景下的配额同步（Redis 或共享文件）
- 配额耗尽时的策略配置（降级 vs 队列 vs 拒绝）

**预期的架构变更**：
- 新增 `QuotaManager` 组件，位于 Provider 抽象层内部
- 支持配置化的限流规则（如 "Go 模型每小时不超过 100 次调用"）
- 与 Provider 路由逻辑结合，配额耗尽时自动 failover

**对现有系统的影响**：
- 低影响，作为 Provider 抽象层的内部组件，对外透明
- 需要新增配置项，但无需改业务逻辑

### 方向 3：增量化重试与熔断模式

**为什么需要**：从失败信息看（elapsed=1.3s），系统没有做任何重试就直接失败了。引入重试+熔断可以大幅提升任务成功率。

**核心挑战**：
- 需要区分可重试错误（429、5xx）和不可重试错误（4xx 非 429、认证错误）
- 指数退避的初始间隔和最大间隔需要调优
- 熔断后的半开探测（Half-Open）逻辑

**预期的架构变更**：
- 在 Provider 抽象层内部集成重试中间件
- 引入熔断器状态管理（CLOSED / OPEN / HALF-OPEN）
- 熔断状态应暴露给运维（metrics / health check）

**对现有系统的影响**：
- 低影响，属于 Provider 抽象层的内部实现细节
- 原有的调用方无需修改

### 方向 4：任务结果缓存层

**为什么需要**：对于相同或相似的请求（如代码审查同一段代码），缓存可以显著减少 API 调用量，同时降级时也能返回缓存结果。

**核心挑战**：
- 缓存 key 的设计（prompt + 参数 + 模型版本）——需要平衡命中率和正确性
- 缓存失效策略（TTL、LRU、主动失效）
- 语义相似性缓存（高级选项，使用 embedding 做相似度匹配）

**预期的架构变更**：
- 新增 `CacheLayer`，可以在 Provider 抽象层外部或内部
- 可选持久化缓存（SQLite / Redis）以跨会话复用

**对现有系统的影响**：
- 中低影响，通过装饰器模式透明接入
- 需要存储，引入一个轻量级依赖（如 SQLite）

### 方向 5：结构化可观测性（Observability）

**为什么需要**：从错误输出看，当前只有原始 stderr。没有 structured logging、metrics、tracing，导致故障定位困难。

**核心挑战**：
- 确定合适的观测维度（provider、model、latency p50/p95/p99、error rate、quota usage）
- 如何在不影响性能的情况下采集数据
- 是否需要引入 OpenTelemetry

**预期的架构变更**：
- 在所有 AI 调用路径上加入 instrumented 中间件
- 输出到结构化日志（JSON lines）、metrics 端点（Prometheus）
- 可选：分布式追踪（OpenTelemetry）

**对现有系统的影响**：
- 低影响，通过中间件/装饰器模式添加
- 无外部依赖即可先做结构化日志

## 3. 接口设计建议

### AI Provider 抽象接口原则

```go
// 核心原则：面向能力而非面向供应商
type Provider interface {
    // 模型基本信息
    Name() string
    Models() []ModelInfo       // 可用模型列表
    Supports(Capability) bool  // 能力声明

    // 核心推理
    Complete(ctx Context, req CompletionRequest) (*CompletionResponse, error)
    CompleteStream(ctx Context, req CompletionRequest) (<-chan CompletionChunk, error)

    // 健康与状态
    Health() ProviderHealth
    Usage() ProviderUsage
}
```

**设计原则**：
1. **失败模式作为接口的一部分**：返回明确的错误类型（`RateLimitedError`、`ContextLengthExceededError`），而不是原始 API 错误
2. **上下文感知**：`Context` 包含请求 ID、超时、重试策略等元信息
3. **分页/Streaming 统一**：所有可能返回大量数据的调用都支持流式
4. **可组合中间件**：重试、限流、熔断、缓存、日志都作为 `Middleware` 组合

### 是否引入新抽象层

**需要**。当前的硬编码架构缺少以下抽象层：

| 抽象层 | 必要性 | 优先级 |
|--------|--------|--------|
| Provider 接口 | **P0** — 否则无法解决当前问题 | 最高 |
| 限流/配额管理层 | **P0** — 直接对应 429 问题 | 最高 |
| 错误标准化层 | **P1** — 避免上游错误类型泄露 | 高 |
| 缓存层 | **P2** — 性能优化，非必须 | 中 |

### 向后兼容策略

1. **适配器模式**：保留原有的直接调用路径作为默认实现，新增 Provider 抽象层通过适配器接入
2. **特性门控（Feature Flag）**：新架构通过配置开关启用，默认关闭
3. **两阶段迁移**：Phase 1 在新抽象层背后包装旧代码；Phase 2 将旧调用方迁移到新接口

## 4. 技术选型

### 是否需要引入新技术栈

| 技术 | 推荐 | 理由 |
|------|------|------|
| 重试/熔断库 | ✅ 引入 | 自己实现 bug 多，用成熟的如 `cenkalti/backoff` + `sony/gobreaker` |
| OpenTelemetry | ✅ 引入 | 标准化观测，但可以先从结构化日志开始 |
| Redis / SQLite | ⚠️ 按需 | 配额管理和缓存需要时再引入，初期可用内存+文件 |
| 消息队列 | ❌ 暂不需要 | 当前场景同步调用即可，引入 MQ 过度设计 |

### 第三方依赖评估标准

```
[必要性] 是否能直接解决一个明确的问题？
[成熟度] 是否在 GitHub 上有 1000+ star，维护活跃？
[侵入性] 是否强制改变已有代码结构？
[替代性] 能否用 <100 行代码自实现且不丢失功能？
[licensing] 是否兼容当前项目的开源协议？
```

**核心原则**：对于基础设施类能力（重试、熔断、限流），优先用成熟库；对于业务逻辑（路由策略、配额算法），在项目内部实现以保持控制。

### 自建 vs 采购

当前场景没有明显的"采购"选项，但有一个类似的权衡：

- **自建 Provider 抽象层** → ✅ 推荐。这是核心竞争力，需要完全掌控
- **使用第三方 LLM Gateway**（如 Helicone、Portkey、LiteLLM） → 可评估。如果团队资源紧张，可考虑用开源版 LiteLLM 作为 Provider 代理，但损失了定制灵活性

## 5. 实施路线图

### 优先级定义

| 级别 | 含义 |
|------|------|
| **P0** | 立即需要，阻塞系统正常运行 |
| **P1** | 重要，但不是阻塞性 |
| **P2** | 有长期价值，但可暂缓 |

### 阶段划分

#### Phase 1 — 止血（P0，1-2 天）

| 任务 | 描述 |
|------|------|
| 1.1 引入重试+退避 | 对 429 错误自动重试，指数退避初始 1s，最大 60s |
| 1.2 错误封装 | 将上游原始错误包装为内部错误类型，stderr 不泄露内部结构 |
| 1.3 单实例简单限流 | 在内存中维护调用计数器，在接近上游限制前主动节流 |

**风险**：重试可能加剧上游限流压力（thundering herd）—— 需加上随机 jitter。

#### Phase 2 — 抽象层（P0～P1，1 周）

| 任务 | 描述 |
|------|------|
| 2.1 定义 Provider 接口 | 根据 3.1 节的原则定义核心接口 |
| 2.2 接入现有调用方 | 将现有的 opencode.ai 调用包装为第一个 Provider 实现 |
| 2.3 配置化模型选择 | 支持通过配置指定模型，为 failover 做准备 |

**风险**：接口设计可能过度抽象或抽象不足 —— 建议先只实现一种 Provider，再根据第二个 Provider 的接入经验迭代接口。

#### Phase 3 — 弹性增强（P1，1-2 周）

| 任务 | 描述 |
|------|------|
| 3.1 熔断器集成 | 在 Provider 抽象层中集成熔断模式 |
| 3.2 多 Provider failover | 支持配置备选 provider，主 provider 限流/熔断时自动切换 |
| 3.3 配置化配额管理 | 可配置的分钟/小时/日配额，支持持久化 |

#### Phase 4 — 深度优化（P2，2-4 周）

| 任务 | 描述 |
|------|------|
| 4.1 缓存层 | 支持结果缓存，可选 SQLite 持久化 |
| 4.2 可观测性 | 结构化日志 → metrics → 可选 tracing |
| 4.3 性能优化 | 连接池、请求合并、预取等 |

### 里程碑

| 里程碑 | 时间 | 验收标准 |
|--------|------|----------|
| M1: 止血完成 | Day 2 | 429 错误不再导致任务直接失败，自动重试恢复 |
| M2: 抽象层上线 | Week 2 | 至少一个调用方通过 Provider 接口完成调用 |
| M3: 弹性增强 | Week 4 | 熔断器切换和 Provider failover 测试通过 |
| M4: 生产就绪 | Week 6 | 缓存+观测上线，可以展示 SLA 仪表盘 |

### 关键风险与缓解策略

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| 重试导致上游负载放大 | 中 | 高 | 随机 jitter（±50%），熔断器快速熔断 |
| Provider 接口过度设计 | 高 | 中 | YAGNI 原则，只实现第一个 Provider 后再迭代 |
| 引入过多依赖 | 中 | 低 | 每个依赖加入前必须通过评估标准 |
| 缓存导致结果过时 | 低 | 中 | 清晰的 TTL 配置，默认不缓存关键任务 |
| 团队对新抽象层学习曲线 | 中 | 低 | 提供迁移指南和示例代码 |

## 总结

本次"分析"的输入虽然只是一个 429 错误，但它揭示了一个更深层的架构问题：**系统对上游 AI API 的调用缺少任何弹性模式**。这不仅是运维问题，更是架构设计缺失的体现。

核心建议：
1. **立即做**（P0）：重试+退避，成本最低，收益最大
2. **本周做**（P0～P1）：Provider 抽象层 + 错误标准化
3. **本月做**（P1～P2）：熔断、failover、缓存、观测

从错误中学习架构问题，本身就是架构师的重要能力。如果你有实际的分析文档需要评审，欢迎提供。
