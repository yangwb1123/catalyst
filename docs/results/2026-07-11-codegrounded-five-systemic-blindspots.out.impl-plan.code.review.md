## 代码质量深度分析

### 1. 组织 — ✅ 良好

代码库具有出色的关注点分离设计：
- 明确的六边形架构：`domain` → `service` → `store` → `httpapi`
- `internal/` 子包按领域划分（`gate`、`mode`、`memory`、`trace`、`risk`、`routing`）
- 无循环依赖（经 `arch-check` 验证）
- 依赖关系单向向内（`cmd/forge` → `internal/` 包，不反向依赖）

**缺点：** `cmd/forge` 包过大，包含太多业务逻辑。此包应仅为 CLI 调度器，将提示构建、成本核算和检测提取到 `internal/` 子包。

### 2. 命名与文档 — ✅ 优秀

这是代码库的优势：
- 每份文件均以全面的包级 doc 注释开头，说明设计意图、honesty 范围和关联
- 命名清晰且表达意思：`GatesGreen`、`ResolveGate`、`CommandExecutor`、`runBudget`
- 锁顺序契约在 `parallel.go` 中文档化 — 极佳的实践
- 常量被恰当命名和注释

**需改进：** 少数内部函数缺失文档（如 `pluck`、`normStatus` 等工具函数）。

### 3. 错误处理 — ⚠️ 良好但可改进

积极方面：
- Go 1.13+ 风格的错误包装广泛使用 `%w`
- `nil` 具有可处理性 — 以安全默认值处理缺失文件（缺失文件 ≠ 错误）
- 仅 1 个 `os.Exit`（在 `main.go`）和仅 1 个 `panic`（在 `MustParse`）— 优于行业标准

需改进：
- 混合模式：部分函数返回错误，同时部分向 stderr 写入（`gatherSignals` 写入 `os.Stderr` 并返回信号）
- `MustParse` 是导出的 panic 路径 — 应当是内部函数或返回错误

### 4. 日志 — ⚠️ 功能足够但原始

`fmt.Fprintf` 至 stderr 单一方法：
- 无日志级别（`INFO` / `WARN` / `ERROR`）— 无法过滤
- 无时间戳 — 无法关联事件序列
- 无结构化数据 — 无法编写告警查询
- Go 1.21 的 `log/slog` 可在零依赖条件下提供此能力

### 5. 测试实践 — ✅ 良好，有改进空间

积极方面：
- 77 个测试文件对应 63 个源文件 — 良好的覆盖比例
- `t.Helper()` 在测试辅助函数中一致使用
- Fuzz 测试已添加（`internal/routing/routing_test.go` 中的 `FuzzTierForScore`）
- 基准测试存在（`memory_bench_test.go`、`asset_bench_test.go`）

需改进：
- 表格驱动测试利用率约 30%，而非更优
- 无共享 `testutil` 包，导致重复定义
- 覆盖率未测量，也无门槛值

### 6. 值得称赞的做法

| 实践 | 示例 |
|--------|---------|
| **Honesty 优先设计** | 每份包文档均清晰说明范围和限制。"这不是 ADR 引擎，它是薄马歇尔器" |
| **零依赖纪律** | 纯 Go 标准库 — 无一依赖 |
| **显式锁顺序** | `parallel.go` 中的锁顺序契约可防止死锁 |
| **反脆弱性** | 缺失数据 = 风险暴露而非有缺口；N/A 不被视为绿色 |
| **真空绿色防护** | `GatesGreen` 要求 ≥1 个真实 PASS，以防零检查通过 |
| **防御性解析** | `parseID` 拒绝尾随斜杠和嵌套路径 |
| **DoS 防护** | `maxBody`、`MaxOutputBytes`、`recoverMiddleware` |
| **回退链** | YAML 解析回退：Go → Python shim → 错误 |

## 结论

**总体代码质量：良好**

这是精心设计的代码库，具有出色的工程纪律。`forge-core` 以干净的架构、零外部依赖和广泛的内置文档运行。

**生产前必须修复：**
1. **P0** — 拆分 `ai-dev/pi-batch.py`（917 行）。闸门已将此项标记为 BLOCKED。
2. **P0** — 将 `cmd/forge` 中的关键业务逻辑提取到 `internal/` 子包（7,500+ 行需要精简）。

**可维护性关注：**
- 无结构化日志使生产可观测性成为未来痛处
- 无可测量覆盖率的空 `coverage.out` 意味着"覆盖率"闸门形同虚设
- `context.Context` 缺失意味着超时永远无法向上传播

**快速致胜（小型改进）：**
1. 对仍悬停于 499 行的 6 个文件各添加一个空行进行拆分（缓解，非修复）
2. 将 `MustParse` 设置为包私有（`mustParse`）或返回错误
3. 向 CI 添加 `go test -coverprofile=coverage.out ./...`
4. 使用 Go 1.21 的标准库 `log/slog` 引入结构化日志

**关于您的问题：** 关于选择哪组文档进行实现，我推荐 **`v38-extension-analysis`（P0）**，因为它具有最高的覆盖范围和最细粒度的任务分解。但也请注意，工作树中有 57 个已修改文件（+4,750/-2,060 行）尚未提交，这表明当前实现与文档之间可能存在偏差。我建议在开始新的实现工作之前先提交或暂存当前未提交的代码。
