# ADR-0099: Durable Scheduled Whole-Graph Controller v1

## Context
The scheduled Graph path already separates three safety boundaries. Progress reconcile observes one exact serial schedule and lets pinned Core select the first non-completed node. Ready release reconstructs that selected initial or successor source without granting execution. The effectful one-node step then requires fresh request-scoped consent, atomically claims the current source and global Project lane, polls at most one provider request, and preserves no-resend lifecycle evidence.

Repeatedly calling that step from process-local code is not a whole-Graph controller. A crash would lose the intended cursor and loop budget, while a retry could not distinguish failure before claim from a provider effect whose local terminal commit is missing. A durable controller must remember orchestration progress without replacing the lifecycle transaction that is already the provider-send fence.

The safe first controller remains serial and caller-driven. It may passively materialize and prepare the one Core-selected node, and after a completed node it may prepare the next selected successor, but it must stop before every new external request. Claimed, quarantined, adjudicated, failed, uncertain or incompatible evidence must remain visible rather than being converted into availability through retry.

## Decision
Add scheduled whole-Graph controller protocol version 1 and SQLite schema v29. Exactly one controller belongs to one Graph Run. Its append-only journal is independent from the existing Graph Run seed journal and does not change the meaning of that journal.

### Immutable controller envelope
The controller header binds the Graph Run, exact schedule identity and digest, schedule and progress protocol versions, node count, exact pinned Core binary digest, one execution profile, creation time, maximum effectful steps and maximum total micro-USD reservation. The execution profile binds the registered HTTPS endpoint, model, token, event, byte, timeout, per-node maximum cost, pricing snapshot and result bounds. The header, profile and every event use strict canonical JSON plus domain-separated SHA-256 identities.

Version 1 accepts only schedule-v1 serial, maximum-one-in-flight, contiguous-prefix, exactly-one-attempt and fail-fast policies. The effectful-step budget is positive, no greater than the scheduled node count or 32, and total cost is bounded by the number of steps times the profile's per-node maximum. The journal is bounded to 512 events, 64 KiB per header or event and 4 MiB in aggregate.

Every Core-using re-entry must present the same executable digest and pass the exact existing handshakes. The digest proves copied byte identity and the handshake proves wire compatibility only. Core remains operator-trusted same-user code without publisher, function, filesystem, network or syscall attestation.

### Explicit commands and passive progression
`controller start` creates or exactly replays the immutable controller after observing one atomic progress snapshot and validating the schedule policy. `controller show` only reconstructs the bounded journal. `controller advance` performs no provider poll; it re-enters planned passive work, reconciles current durable state and drives the selected node only as far as fresh consent. `controller step` first performs the same recovery and passive drive, then may consume one current request-scoped consent set and delegate exactly once to the existing one-node step.

Passive drive materializes only the ordinal and node selected by the current reconcile decision. It uses deterministic controller-and-ordinal idempotency keys rather than the multi-ready wave admission surface. It then prepares the exact provider request and reruns ready release for current authorization bindings. Existing valid candidate or request records are replayed only after complete validation. The call stops at `AwaitingFreshConsent`, which binds the exact ordinal, node, request, authorization, progress snapshot, decision and whether predecessor content is included.

After one node is durably completed, the same public call may reconcile, materialize and prepare its one selected successor. It still returns at the successor's consent boundary. No command recursively calls another step, polls a second provider request or executes a concurrent node.

### Planned and observed journal protocol
The event chain starts with `Started`. Before materialization, preparation or provider dispatch, the controller appends the corresponding `MaterializePlanned`, `PreparePlanned` or `DispatchPlanned` event through compare-and-append against the exact previous event digest. The external or fallible call runs outside the journal transaction. A successful observation is then appended as `MaterializeObserved`, `PrepareObserved`, `NodeCompleted`, `RetryablePreclaimFailure`, `Stopped` or `Completed` as applicable.

Materialization and preparation are passive, deterministic and idempotency-keyed, so a dangling planned event may be re-entered and its durable result revalidated. Their observed events record identifiers and digests, not Prompt, predecessor output, request body or model result. Controller CAS orders cooperating journal writers, but it is not provider execution authority.

Immediately before a possible provider effect, `controller step` requires fresh off-machine consent for the exact current request and, only when predecessor content is included, separate fresh content consent. It appends `DispatchPlanned` before invoking the one-node step. That event consumes the next effectful-step reservation and the full per-node maximum-cost reservation and records the exact current anchors plus consent-observed facts. Reservations are never automatically refunded, even when no lifecycle is later found or a preclaim dependency fails. A stored consent observation is audit metadata and can never authorize a later invocation.

The existing ready-node snapshot-to-lifecycle claim and cross-family Project-lane transaction remain the sole provider-send fence. Only its winning non-clone authority may poll the request. Thus a controller-head race, process overlap or repeated dispatch plan cannot grant a second send; losing or stale one-node invocations poll nothing.

### Crash re-entry and stops
Re-entry from a dangling `DispatchPlanned` inspects the exact any-family scheduled lifecycle before credential or provider construction. A completed receipt repairs the controller with `NodeCompleted` and permits passive preparation of the next selected ordinal. A currently claimed lifecycle appends terminal `Stopped(claimed_unknown)` and never resends. Quarantined or adjudicated evidence appends the corresponding terminal manual stop. Failed and failed-uncertain terminal receipts, incompatible progress or schedule, and exhausted step or cost budget also stop the controller.

If no lifecycle exists for a bare dangling `DispatchPlanned`, the consumed reservation remains charged and the controller appends terminal `Stopped(claimed_unknown)`; absence is not proof that a prior process cannot still claim. Only a specifically classified credential, provider-construction or owner-evidence failure may first append `RetryablePreclaimFailure` and return to `AwaitingFreshConsent`. A later explicit step then rebuilds current authorization and requires a new consent set; neither journal absence nor old consent authorizes it.

No controller path expires a lease, declares an owner dead, adjudicates a claim, recovers quarantine, retries transport, resends a request or clears uncertainty. A `Stopped` or `Completed` journal is terminal in version 1. Any policy that resumes those states requires a new decision and protocol.

## Consequences
A scheduled Graph can progress across bounded explicit calls rather than one uninterrupted process. Its journal exposes which passive call was planned, which durable result was observed, where fresh consent is needed, which conservative reservations were consumed and why execution stopped. Exact start and event replay are idempotent, while divergent reuse fails closed.

The controller remains intentionally availability-conservative. A crash before claim can consume step and cost budget, and a claimed or uncertain request can permanently stop this controller even if later operator evidence might permit a separate lifecycle transition. That cost prevents process restart from becoming implicit effect permission.

Serial successor preparation reduces operator ceremony without broadening effect authority. A completed step can leave the next exact request ready for inspection and fresh consent, but never sends it. Existing reconcile, ready-release and one-node-step contracts remain independently meaningful and keep their wire identities.

## Validation
Domain validation must cover every event shape and legal transition, immutable profile and header digests, exact event hash chaining, ordinal and identifier bindings, journal byte and event caps, monotonic timestamps, reservation sequence and aggregate cost overflow. Terminal events must reject every later append.

SQLite validation must cover v28-to-v29 migration and rollback, one-controller-per-Graph uniqueness, atomic header-plus-start creation, exact replay, divergent conflict, canonical row reconstruction and corruption of every stored column. Two independent connections and process-level contenders must prove compare-and-append head serialization without treating it as the lifecycle send fence.

Application fault injection must cut before and after every Planned append, fallible call and Observed append. Re-entry covers existing passive results, absent lifecycle, every claimed substate, completed, quarantined, adjudicated, failed, failed-uncertain, incompatible and budget-exhausted outcomes. Provider counters must prove at most one poll per `step` and zero polls for `start`, `show`, `advance`, replay losers and every stop.

Consent tests bind the exact request, authorization, snapshot, decision and conditional predecessor-content fact, reject stale or mismatched anchors and prove journal replay never reuses a prior invocation's flags. Budget tests cover crash, preclaim failure, maximum step and maximum micro-USD boundaries and demonstrate that reservations never reset or refund implicitly.

Compiled CLI tests use repository-built pinned Core and deterministic local providers only. They cover wrong pins and handshakes, mixed versions, metadata-only output, redacted errors, poisoned credentials and endpoints, workspace and logical-Hub sentinels, process interruption and competing invocations. Fresh-context architecture and security review plus the full repository acceptance harness remain required delivery evidence; none changes this ADR from Proposed.

## Limitations
Version 1 is an explicit re-entry state machine, not a daemon or unattended provider loop. It has no schedule-v2 waves, parallel nodes, multiple attempts, retry policy, dynamic profile change, budget refund, automatic stopped-state recovery, lease expiry, quarantine repair or claim adjudication. It does not provide provider-side idempotency or remote exactly-once behavior.

Controller CAS serializes one local SQLite journal only. It does not fence non-cooperating database replacement, same-user tampering or provider effects; the lifecycle claim and Project lane remain responsible for local single consumption. An external provider may observe a request whose terminal evidence never commits.

The journal stores metadata and unkeyed integrity digests, not authenticated principals, signatures or private execution content. SQLite durability depends on the local filesystem, and digest equality does not prevent same-user rewriting. Core pinning and an empty child environment do not confine Core.

Proposed status records this architecture candidate only. It supplies no ApprovalRecord, authenticated consent, execution permission, compliance finding, lifecycle promotion or effect attestation.
