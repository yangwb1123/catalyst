# ADR-0094: Session Worktree and Local Merge Queue v1

## Context
Forge can run coding workflows against a repository, but a coding process that edits the primary worktree shares mutable files with every other process. Branches alone do not isolate working directories, and concurrent branch switching in one directory can overwrite or hide another session's edits. Allowing each coding agent to merge its own result also gives the component that authored a change authority to update the protected base branch.

The required boundary is local and session-oriented. Every coding session needs a distinct branch and worktree, while base-branch mutation must pass through one serialized controller after validation against the latest local base head. Failed validation or conflicts must retain the session worktree for repair. Git history, worktree isolation, validation and merge authority are separate concerns and must remain visibly separate in the implementation.

## Decision
Introduce the local `forge session` lifecycle with one durable `Session` record per isolated branch and worktree. `forge session start` runs only against the primary worktree, creates `session/<session-id>` from an explicit local base branch, creates a worktree outside the primary repository tree, and persists bounded control state under the Git common directory. Session identifiers use a closed lexical grammar and worktree roots that resolve inside the primary worktree or Git common directory are rejected.

`forge session ready` is the Coding Agent boundary. It accepts only the exact recorded worktree and branch when the worktree is clean, HEAD is committed, and the branch is a descendant containing work after the recorded base. It changes only the session state to `READY_TO_MERGE`; it cannot update the base branch. Failed, conflicted or merge-failed sessions may be repaired and explicitly enqueued again after they become clean.

`forge session integrate-next` is the Merge Controller boundary and must run from the primary worktree. It acquires the repository-wide local Forge mutation lock, chooses the earliest ready session by queued timestamp and session identifier, requires the primary worktree to be clean and on the declared base branch, rebases the session onto the latest local base head, and runs a controller-owned validation argv in the session worktree. After validation it rechecks the session branch, session HEAD, clean worktree, base HEAD and clean primary worktree before performing a fast-forward-only merge.

Successful integration records the merged commit, then removes the clean worktree and deletes the merged session branch unless the controller explicitly retains them. Conflicts become `CONFLICT`, validation failures become `TEST_FAILED`, and post-validation or merge failures become `MERGE_FAILED`; each failure retains the worktree and does not intentionally update the base. Session checkpoint commits are preserved in v1. Squash, remote fetch, push, pull request creation and remote CI observation are outside this local contract.

The default CLI validation command invokes the current Forge executable as `forge accept --root . --timeout 0` from the session worktree. A controller may supply an explicit program and repeated argv for a repository-specific gate. Validation programs are effectful trusted controller configuration, never session-authored state. The package retains bounded command output in memory but persists no validation output, prompt, source bytes or credentials in the Session record.

Role separation is an orchestration policy boundary, not authentication. The CLI does not prove that a caller is a Coding Agent or Merge Controller; deployments must expose `start` and `ready` to coding sandboxes while reserving `integrate-next` and the primary worktree for the controller. The local advisory lock serializes cooperating Forge processes on supported local Unix filesystems. Exact Git rechecks fail closed when an external Git process changes the base or session during validation.

## Consequences
Concurrent coding sessions can operate in independent directories without branch-switch contention, and only one cooperating controller writes the local base branch at a time. A session that fails validation or rebase remains inspectable and repairable instead of being silently deleted or merged.

The merge queue revalidates after rebasing onto the current local base, so a result tested against an older base cannot move main directly. Fast-forward-only integration keeps the final write simple and makes session checkpoint commits visible. The primary worktree must be clean, which deliberately favors safety over merging around unrelated operator edits.

The first version adds local control state and Git subprocess effects but no daemon. Automatic integration means the Harness invokes `integrate-next` when a session becomes ready; it does not mean the Coding Agent receives merge authority or that Forge continuously polls in the background.

## Validation
Use temporary real Git repositories to verify start, committed-ready admission, successful rebase-validation-fast-forward, cleanup, preserved checkpoint identity, FIFO queue order, and rebasing of a later session after main advances. Verify an empty or dirty session cannot enter the queue, a dirty primary worktree blocks without consuming the ready item, and a failing validation leaves main unchanged while persisting `TEST_FAILED` and retaining the worktree.

Run the `sessionworktree` package tests, the `forge` command tests, the complete Go suite, structural and architecture gates, governance checks and repository acceptance. Validate the new ADR as exact Proposed-only v2. Review failure paths for bounded subprocess output, no-follow private state writes, external worktree path boundaries, exact branch and commit rechecks, and absence of remote Git operations.

## Limitations
Version 1 is local-only and does not fetch or determine remote freshness, push, open a pull request, inspect remote CI, squash commits, authenticate controller identity, enforce operating-system permissions, or provide a long-running queue daemon. Harness sandbox and command policy must keep `integrate-next` and the primary worktree unavailable to Coding Agents.

The Forge run lock is an advisory single-host lock and cannot serialize non-cooperating Git clients or unreliable network filesystems. Rechecks detect many external changes but Git updates and Session state writes are not one cross-filesystem atomic transaction. A process crash can leave a state in `REBASING`, `VALIDATING`, `MERGING` or `MERGED`; automated crash reconciliation is deferred, so an operator must inspect Git and state before recovery.

Worktree isolation prevents sessions from overwriting the same checked-out files, but it is not a security sandbox. Git objects and the common directory remain shared, validation commands are trusted effectful controller input, and dependency caches or external services may still be shared unless separately isolated.
