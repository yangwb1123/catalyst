# ADR-0114: Opt-In Device Enrollment and Inventory v1

## Context
The approved cross-device Forge route needs a Coordinator-owned view of devices and reported resources. ADR-0039 is Accepted and explicitly planning-only: it does not authorize live device registration, remote access, or execution. The Rust device registry module is a pure reference model, not an authenticated registry or persistence layer. Console Agent Hub has a separate device/task domain and does not bind those tasks to Forge Conversations or Runs. Reusing its task state as Forge execution state would create two authorities.

## Decision
Propose an opt-in Forge Core device enrollment and inventory boundary. If separately authorized, a Runner generates its device key locally and proves possession during an outbound authenticated exchange. The Coordinator binds the immutable device identity to the configured personal account and tenant, issues a device-only transport credential, and leaves the device Pending until its owner explicitly approves it. Human access tokens never become Runner credentials and are never copied into a task sandbox. Enrollment and approval grant no access to Conversations, Projects, artifacts, or task execution.

A heartbeat carries device identity, process generation, strictly increasing sequence, bounded capability snapshot, and requested lease duration. Forge Core uses its own clock and one transaction to reject replay or invalid generation changes and replace the snapshot and expiry. Read APIs derive online, stale, offline, pending, approved, cordoned, and revoked views from persisted state; they never accept a caller-supplied owner. Revocation is terminal for that identity. Rotation creates an auditable binding change rather than silently changing the device key. Self-reported resources remain declared observations without hardware attestation and cannot establish trust or placement eligibility.

This proposal would permit authenticated enrollment, owner approval, heartbeat persistence, and owner-scoped inventory visibility only after an independent authorization decision. It does not permit LAN discovery, SSH automation, remote Task pull, reservations, dispatch, execution, migration, or data transfer. The feature remains disabled unless exact Coordinator configuration and applicable policy are explicitly enabled; installation or a successful heartbeat is never authorization to execute work.

## Consequences
Forge Core Go becomes the canonical owner of enrolled device identity, approval, liveness, and capability snapshots; Rust remains a pure contract reference and Runtime continues to own execution attempts. Devices can contribute resource visibility without merging Forge session state with Agent Hub task state. Clients can show pending, stale, self-reported, cordoned, and revoked state without describing it as available compute.

The design requires a device credential lifecycle, atomic replay-safe heartbeat storage, owner approval and revocation routes, tenant-isolation tests, and compatibility fixtures for the Rust reference model. It adds no authority to Snaplink, Aero-ID, Aero-IM, Aero Vault, Console, or Audit Governance. Future dispatch requires a separate decision for consent, Project grants, isolation, reservations, leases, fencing, artifact transfer, audit, cancellation, and uncertain effects.

## Validation
Before live enrollment is implemented or enabled, the governing decision must be explicitly authorized under a supported architecture/security process; this Proposed-only record and a passing structural checker are not authorization. Validate proof-of-possession challenge binding, one-time enrollment, credential expiry and revocation, exact owner and tenant binding, generation/sequence replay rejection, server-clock lease expiry, atomic snapshot replacement, restart persistence, and rollback. Verify pending, stale, offline, cordoned, and revoked devices are never represented as approved or executable; self-reported capabilities are labeled and cannot bypass trust or data-residency constraints. Exercise authenticated HTTP and persistent storage with cross-account, malformed-credential, replay, revoked-key, and disabled-feature cases. Prove the disabled default opens no Runner listener, accepts no registration, and performs no network discovery.

## Limitations
This is a Proposed-only contract candidate. It does not change ADR-0039, authorize live enrollment or heartbeat, or provide an Accepted lifecycle transition. No enrollment endpoint, device credential issuer, persistent device table, inventory API, CLI/UI resource view, placement service, scheduler, reservation, task dispatch, remote Runner execution, Vault staging, or Audit Governance integration is delivered by this document. Until a separate authorized decision exists, the runtime remains unable to register remote devices.
