# ADR-0112: Runtime Hub Read Bridge v1

## Context
Sprint 152 added a Rust-owned local Conversation change cursor, but Go App Server has no Runtime process boundary. Go must not read or write the Rust Hub database, and the Hub change cursor is local to one store rather than a tenant identity, audit sequence, or complete Run timeline. The App Server still serves only loopback health; this ADR does not open a session API or settle external client authentication.

## Decision
Add a one-request-per-process, newline-delimited JSON protocol in a private `--runtime-rpc` invocation mode of the existing Rust `forge-runtime` executable. Go invokes the explicitly configured absolute executable and Runtime database path with fixed `--runtime-rpc --database <path>` argv through `exec.CommandContext`; it never uses a shell. The configured executable must be the direct Runtime binary and must not launch child processes. The Runtime database path is outside the Go App Server state directory and remains exclusively owned by Rust. The Rust executable opens only an existing current Hub through SQLite live read-only mode, so an active WAL can be read without schema migration or logical Hub writes. SQLite may coordinate transient WAL/SHM reader locks and artifacts as documented by the live read-only store mode.

Freeze protocol version `forgeos.runtime-bridge/v1`, one JSON request followed by exactly one LF, one JSON response followed by exactly one LF, a 16 KiB request limit, a 2 MiB response limit, strict unknown-field and duplicate-key rejection, required top-level and nested response-field validation including exact Global/Project/Group tagged scope shapes for every Conversation, and no protocol bytes on stderr. Rust serializes through a capped writer; Go accepts only one exact response line and applies a bounded child wait after cancellation so inherited pipes cannot hold a request open indefinitely. That wait does not terminate descendants, which is why wrappers and child-launching executables are outside the supported configuration. The process handles exactly one request and exits. Stable request IDs only correlate that request with its response; they are not idempotency or authority tokens. The allowlist contains `snapshot_at_cursor`, bounded `conversation_changes_after` pages with limits from 1 through 128, `conversation_prompt_page` for one Conversation with a maximum 128-row page and a fixed 256 KiB aggregate Prompt-content budget, and `conversation_bootstrap_page` for bounded Conversation metadata bootstrap. Prompt pages use exclusive keyset order `(created_at_ms DESC, id DESC)`, return an explicit continuation cursor, and expose only id, conversation_id, role, content, and created_at_ms; they never expose idempotency keys. The Prompt SQL query reads bounded metadata first and loads only records that fit the fixed byte budget. Bootstrap captures a fixed journal head on its first page and binds every continuation to it. It first pages the v29 migration-baseline table by binary Conversation ID, then pages the append-only change journal by cursor, emitting metadata only for `conversation_created` events at or before that head. Each phase reads at most `limit+1` indexed rows for a maximum 128-row result; a change page containing only `prompt_appended` events may return no Conversations while advancing its cursor, and `scanned_through_cursor` explicitly reports that raw journal progress even on the final empty page. Entries include their creation cursor and observed per-Conversation aggregate version; the fixed head bounds bootstrap membership, while later Prompt appends may make metadata values newer than the head. Errors use bounded codes and messages and never include filesystem paths or raw storage errors.

The snapshot projection omits canonical project paths. Change rows remain ID-only references. Prompt hydration is limited to a requested Conversation and bounded pages; it omits idempotency keys and never falls back to a global Prompt list. Conversation bootstrap is limited to metadata and a caller-held fixed journal head; it does not disclose Prompt bodies or project paths. Its cutoff fixes membership, not an as-of value snapshot: because Prompt appends update `updated_at_ms`, continuation pages return the current row and its observed aggregate version, and replay consumers must ignore already-observed versions. Prompt text is sensitive even across this local boundary. This bridge does not add Conversation or Prompt writes, Run events, authentication, tenant ownership, HTTP routes, device state, or execution behavior. The executable is an internal same-user process boundary: filesystem permissions and the operator account remain trusted, and anyone able to invoke the binary with a readable database path can issue these read queries.

The initial Coordinator deployment assumption is private VPN/self-hosted. This decision does not bind a network listener and therefore remains safe if the deployment topology changes before remote APIs are designed. Cross-device HTTP exposure still requires a separate Snaplink resource/audience, exact owner mapping, least-privilege scopes, object authorization, session-claim policy, and ingress decision.

## Consequences
Go gains a versioned, bounded, read-only seam to the Rust-owned Hub without sharing a database connection, schema, or human CLI output format. Prompt history pages are keyset-paginated, byte-budgeted before Prompt bodies are loaded, and omit idempotency keys. Conversation bootstrap pages avoid the unbounded Global Conversation materialization and provide a fixed change-log head for replay; they do not make the separate Project/Group/member portions of `snapshot_at_cursor` bounded. The baseline phase uses a binary-ID keyset; its change-log phase scans no more than `limit+1` indexed cursor rows and can return an empty metadata page when only Prompt changes occur. The process-per-request design keeps lifecycle and crash boundaries simple for the first slice; its startup/read cost must be measured before it is used as a high-frequency event poller. A later long-lived transport may replace it only through a versioned compatibility decision.

The Runtime DB path and executable are deployment configuration, not values supplied in RPC JSON. Existing App Server and Runtime state directories are resolved through symlinks before the client rejects equal or nested paths. The Go state-directory verifier remains unchanged and does not contain Hub files. The bridge is not yet wired into App Server routes or startup, so it cannot be reached by CLI, TUI, Web, App, or Mobile clients.

## Validation
Rust tests must prove exact framing, closed operation allowlist, unknown-field rejection, bounds, path redaction, current-schema live-read-only access, and snapshot/cursor, change-page, Prompt-page, and Conversation-bootstrap semantics against a real SQLite Hub. Prompt-page tests must prove Conversation isolation, exclusive timestamp/ID ordering without duplicates or gaps, the 128-row and 256 KiB pre-load budgets, control-character response sizing, omitted idempotency keys, and generic failure for missing or corrupt oversized Prompt data. Bootstrap tests must prove each phase scans at most `limit+1` indexed rows, stable baseline-ID and change-cursor continuation without gaps, frozen-head membership across concurrent creation, Prompt-update idempotence through aggregate versions, v29 baseline coverage, invalid/future cursor rejection, and unchanged Hub state. Go tests must prove fixed argv without a shell, context cancellation including descendants that inherit output pipes, bounded stdout, exact response framing, duplicate-key and required-field rejection including exact tagged Conversation scopes, Prompt DTOs, bootstrap DTOs, and scanned journal-cursor advancement for empty Prompt-only pages; they must also prove generic failures, symlink-resolved state separation, and correct projection decoding with fake executables. The Hub must remain unchanged after bridge reads, and a missing or old-schema Hub must fail without creation or migration. Run targeted Rust and Go checks, repository architecture/governance gates, and same-tree acceptance before marking this bridge slice complete.

## Limitations
This ADR does not provide authenticated or network APIs, route scopes, tenant/session ownership, Conversation creation, Prompt submission, Run begin/execute, ordered Run timeline events, client surfaces, session import, device inventory, scheduling, remote execution, Vault/IM/Audit integration, or HA. The new Conversation bootstrap page bounds per-query Conversation metadata preloading and indexed range work for that operation only; head validation still counts the full change journal and does not provide a hard CPU bound; `snapshot_at_cursor` still materializes Global projects, groups, members, and conversations before the RPC byte cap is applied, so that operation must not be used as a remote bootstrap API until every returned collection is paginated or given a pre-load size gate. Prompt pages have a separate SQL metadata scan and content pre-load budget, but still rely on the trusted same-user Hub file and same-user process boundary. The proposed private VPN/self-hosted topology is a deployment assumption for the roadmap and not a firewall, VPN, TLS, or authorization implementation. The Hub cursor is store-local and must not be presented as an audit log or cross-store order.
