# ADR-0096: Scheduled Graph Progress Snapshot and Core Reconcile v1

## Context
The scheduled Graph path persists an exact schedule, per-node passive candidates, prepared provider requests, dispatch lifecycles and Core terminal receipts. Each object is inspectable, but callers cannot atomically determine the whole schedule's current disposition. The existing ready-nodes command consumes caller-supplied completed receipts and cannot observe claimed, quarantined, adjudicated, failed or uncertain durable state.

A direct automatic loop would cross unresolved authority and recovery boundaries. Consent is granted to one exact provider request, while a claimed dispatch may already have produced an off-machine effect and cannot be resent automatically. Schedule version 1 also fixes serial execution, one in-flight node and completed-contiguous-prefix progression even though a separate wave-ready surface can materialize topology-parallel candidates.

## Decision
Adopt a version-1 content-free `ScheduledGraphProgressSnapshot` produced by Rust inside one deferred SQLite transaction. It binds the exact validated Graph Run, Graph and schedule, then projects every schedule ordinal with optional candidate identity and contract digest, optional provider request identity and `prepared_request_sha256`, optional lifecycle status and, only for a Core-terminalized lifecycle, terminal outcome and receipt digest. It excludes Prompts, provider request bodies and body digests, model output, artifacts, credentials, authorization bodies, pricing bodies and workspace content.

The runtime fully revalidates each present candidate, request, lifecycle and receipt against already loaded source objects, rejects rows outside the exact schedule and checks observed row counts. Loaders reuse the Run, Graph, schedule, candidate and request within the same snapshot rather than recursively reconstructing the whole Run per node. The snapshot is compact canonical JSON bounded to 64 KiB and content-addressed under a dedicated digest domain.

`forge-runtime group graph run reconcile GRAPH_RUN_ID --core-bin ABSOLUTE_PATH --core-bin-sha256 SHA256` opens an existing exact-current Hub through the live read-only path. It invokes only a canonical regular executable whose bytes match the explicit lowercase SHA-256 and are copied to a sealed Linux executable. The empty-environment child performs a version-1 handshake and receives the exact snapshot through bounded, deadline-limited I/O.

That executable is an operator-trusted, same-user TCB component. The digest proves only which bytes Rust copied and executed, while the handshake proves only protocol compatibility. Neither authenticates the publisher or function of those bytes. Empty environment, sealed executable bytes and bounded standard I/O are not a sandbox: the child retains ambient same-user filesystem and network capabilities, and Runtime applies no syscall, mount, namespace or egress confinement to Core.

Go Core strictly validates the snapshot and returns one digest-bound canonical decision: `ready`, `claimed_unknown`, `manual_recovery_required`, `failed`, `failed_uncertain`, `completed` or `incompatible_progress`. Only `ready` carries the exact next ordinal and node ID. Core reports `incompatible_progress` when any candidate, request, lifecycle or terminal evidence appears beyond the first non-completed ordinal; structural corruption or invalid identity remains a hard error. Rust revalidates the exact decision encoding, digest, snapshot bindings and field shape without recomputing the scheduling policy.

Forge Runtime itself performs no logical Hub write or migration and does not read credentials or workspace files, access a network, construct a provider, materialize a candidate, prepare a request, claim or release a lane, adjudicate, retry, resend or grant successor authority. The official Core command is designed and tested as a pure snapshot-to-decision transform, but Runtime neither confines nor attests arbitrary operator-selected Core bytes. Therefore the combined no-effect claim is conditional on trusting the pinned official Core implementation. CLI JSON makes that scope explicit with `effect_facts_scope="forge_runtime"`, a separate all-false `runtime_effect_facts` object, and a `core_trust_boundary` object that reports same-user/operator trust, binary identity, protocol handshake and empty environment as present while reporting filesystem/network isolation, effect containment and effect attestation as absent. Human output repeats the trusted same-user TCB warning. These disclosures are not syscall observations. SQLite may still coordinate live readers through SHM locks or transient empty sidecars. A `ready` result is an observation only.

## Consequences
The runtime gains one atomic whole-schedule progress view and Core-owned stop decision that can serve as the validated input to a later single-node step when the operator trusts the exact official Core bytes. Claimed work stops as unknown; quarantined and adjudicated work requires a future explicit recovery contract; deterministic and uncertain terminal failures remain distinct. Full completion requires a trusted completed receipt at every exact ordinal.

Under the trusted official Core assumption, Forge Runtime leaves existing Graph Run events pristine because scheduled progress remains in sidecar tables and Runtime writes nothing. Schedule-v1 serial semantics stay honest: wave-parallel durable evidence is visible but cannot be silently accepted as a contiguous serial prefix.

The next effectful slice may advance at most one Core-selected node and must obtain fresh consent for that exact provider request. A durable automatic controller and schedule-v2 concurrent wave execution remain separate later decisions.

## Validation
Go tests exercise all seven dispositions, ready-field shape, canonical decision encoding and stale-digest rejection. Rust domain and application tests exercise strict canonical decoding, digest and presence-chain validation, source-bound decision checking and storage/Core error mapping. A compiled-Go bridge golden binds one exact Rust snapshot to the exact Go decision bytes and digests.

Current SQLite tests cover a schedule-only content-free snapshot, candidate and prepared-request projection, preservation of non-contiguous evidence, missing-schedule rejection and an out-of-schedule candidate row. Process-level CLI tests exercise the repository-built official Core and wrong-pin failure, compare logical Hub table snapshots, preserve workspace sentinels, poison credential/endpoint inputs, reject private-output leakage and observe no loopback connection. Those observations do not prove filesystem/network confinement for an arbitrary pinned binary. Concurrent terminalization, the full 32-node bound and a complete stored-corruption matrix remain required validation before an effectful one-node step or automatic controller can rely on this boundary.

## Limitations
Version 1 does not execute a node, recover or retry a dispatch, persist controller state, consume a consent grant, run a whole Graph, propagate concurrent wave failure, or provide remote exactly-once semantics. It accepts only the fixed schedule-v1 serial policy. `incompatible_progress` is a stop disposition, not a repair instruction.

Snapshot and decision SHA-256 values are unkeyed local integrity identities, not signatures, provider attestations or protection against a same-user database rewrite. The Core pin is likewise not publisher identity, code-function attestation, sandbox evidence or effect containment. The CLI explicitly scopes `runtime_effect_facts` to Forge Runtime and separately reports that Core filesystem/network isolation, effect containment and effect attestation are absent. Those structured negative facts disclose a trust gap; they neither attest confinement nor observe the syscalls of an arbitrary child. Accepting an untrusted Core requires a separate confinement contract; it is not enabled by this version. Live read-only SQLite coordination is not a promise of a physically side-effect-free filesystem.
