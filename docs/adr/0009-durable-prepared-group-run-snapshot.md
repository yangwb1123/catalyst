# ADR-0009: Durable prepared Group Run snapshot

- Status: Accepted; local preparation implemented
- Date: 2026-07-28

## Context

ADR 0007 introduced a bounded, deterministic Group context dossier spanning a
Group discussion and the persisted Prompt history of member Projects. The
initial `group context` command was deliberately an on-demand preview.

An Agent must not retry against whatever happens to be “latest.” A retry after
uncertain output needs the exact same cross-project input bytes. At the same
time, the existing Project `RunStore` cannot represent that state honestly: a
Project Run requires one Project Conversation, one user Prompt, an execution
configuration, and an append-only event journal. An empty Project journal is
classified as incomplete execution, not as a prepared Group input.

## Decision

Forge adds a separate version-1 `GroupRunStore`. A Group Run in this phase has
one state only: `prepared`. It means that a bounded context has been frozen
locally. It does not mean that a model, provider, tool, workspace, discussion,
or analysis has started.

The management commands are:

```text
forge-runtime group run prepare GROUP_ID [--max-bytes N]
              [--include-content] [--idempotency-key KEY]
forge-runtime group run show RUN_ID [--include-content]
forge-runtime group run list [GROUP_ID] [--limit N]
```

These commands use the Hub management path. They never construct a model
provider, Agent Runtime, tool catalog, or workspace capability. Project and
Group space selectors are rejected because the target is already explicit.

### Durable representation

SQLite schema version 3 adds one `group_runs` table. Each row contains:

- an opaque Group Run ID and a foreign-keyed Group ID;
- fixed Run and Group-context format versions;
- the fixed `prepared` status;
- the Group-context digest as a raw 32-byte BLOB;
- the complete canonical `GroupContextSlice` JSON as a BLOB;
- an outer snapshot digest as a raw 32-byte BLOB;
- one unique local idempotency key and the original creation time.

The exact byte length is derived with `length(context_blob)` rather than stored
twice. IDs, keys, versions, status, digest types and sizes, creation time, and
the 8 MiB snapshot limit are enforced by SQLite checks and verified again on a
full snapshot read. The 8 MiB limit accommodates worst-case JSON escaping of a
legal bounded 512 KiB Prompt excerpt budget.

The two content contracts are:

```text
context_slice_sha256 =
  SHA256("forge.group-context.v1\0" || canonical(context.payload))

snapshot_sha256 =
  SHA256("forge.group-run-snapshot.v1\0" || exact context_blob bytes)
```

Canonical JSON is compact UTF-8 with recursively lexicographically sorted
object keys and preserved array order. One generated byte vector is used for
hashing, insertion, and the returned snapshot. `show` verifies length, outer
digest, JSON decoding, canonical encoding, inner digest, Group/policy/source
structure, statistics, and the context version/Group/digest bindings before
returning it; other record metadata is validated against its fixed bounds.

`list` is deliberately a bounded inventory query: it reads and validates only
fixed metadata, including versions, status, IDs, digest shapes, byte count, and
creation time. It does not load or audit snapshot bodies. Callers that need
full integrity validation use `show`; idempotent replay also performs the same
full validation before returning stored bytes.

Both SHA-256 values are unkeyed content-integrity identities, not a MAC,
signature, or authentication boundary. They detect accidental corruption under
the supported API, but cannot stop the same OS user from rewriting SQLite and
recomputing matching hashes. The outer digest identifies the canonical frozen
slice bytes; it does not authenticate mutable row metadata such as the local
idempotency key or creation time.

### Atomic preparation and replay

`prepare` validates the complete request and context policy, then performs one
SQLite `BEGIN IMMEDIATE` transaction:

1. Look up the idempotency key first.
2. If it exists, validate the stored snapshot. The same Group, policy, and
   format return the original ID, creation time, bytes, and hashes. The retry's
   candidate ID and clock are ignored.
3. A reused key with a different Group or any policy field conflicts.
4. A new key with an already used Group Run ID conflicts.
5. Read the Group, members, Conversations, and Prompts inside that same
   transaction.
6. Canonicalize and hash once, insert one row, and commit.

Replay never queries current Group history. A new idempotency key is required
to freeze newer members or Prompts. Immediate locking prevents membership and
Prompt writes from interleaving with snapshot construction. Lock contention
uses the Hub's bounded five-second availability window.

Any validation, encoding, insertion, or commit failure leaves no prepared row.
Preparation does not create Project `runs`, `run_events`, Run cursors,
Run-assistant associations, or assistant Prompts.

### Output and confidentiality

The database snapshot always includes the complete bounded excerpts and
per-Prompt hashes. It is plaintext local state, not encrypted memory.

Default human and JSON output omits excerpts, per-Prompt hashes, raw canonical
JSON, idempotency keys, and canonical project paths. `--include-content`
explicitly returns the bounded excerpts and per-Prompt hashes. Only the
structured `--json --include-content` projection contains every public field
needed to independently recompute both digest layers after canonicalization;
human output is a readable summary. Neither mode is an anonymized or
safe-to-share export.

Human output explicitly says that the snapshot is prepared/frozen and that
model/provider execution has not started.

## Rejected alternatives

- Reusing Project `runs` would require a fabricated Project Conversation,
  Prompt, provider, or empty execution journal and would misstate recovery.
- Writing the dossier in application code before a second storage transaction
  would allow torn membership/Prompt views.
- Rebuilding a missing or corrupt replay from current history would destroy
  idempotency and conceal corruption.
- A separate snapshot table adds orphan and cross-binding failure modes while
  every prepared Group Run owns exactly one immutable snapshot.
- Loading snapshot bodies for `list` can amplify 100 legal records into
  hundreds of MiB; list therefore reads and validates metadata only.

## Consequences and deferred work

The local system now has a durable, inspectable boundary between Group history
and future execution. At adoption, this ADR itself added no Group model request,
planning loop, multi-Agent discussion, automatic task creation, approval flow,
remote account, sync, shared ACL, or provider consent.

ADR 0010 now introduces the first explicit transition from a verified prepared
snapshot to a versioned execution record, but only as a local integrity
receipt. ADR 0011 adds a distinct, consent-gated single-model request over the
same frozen bytes. Multi-Agent execution remains separate and must not query
current Group history in place of its immutable input.
