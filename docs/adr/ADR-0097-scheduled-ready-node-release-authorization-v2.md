# ADR-0097: Scheduled Ready-Node Release Authorization v2

## Context
ADR-0096 provides one atomically observed, content-free scheduled Graph progress snapshot and a Core-owned reconcile decision. Its `ready` disposition identifies one next serial ordinal and node, but is deliberately an observation rather than permission to admit a lifecycle, release execution, claim a Project lane or send a provider request.

The existing scheduled release-control and authorization v1 path is not the missing bridge. Go v1 rebuilds only the initial candidate, requires ordinal zero and an empty predecessor receipt set. Rust can represent successor candidates, but widening only one side or silently accepting successor evidence under the v1 command would preserve neither independent scheduling ownership nor cross-language compatibility. A later effectful one-node step therefore needs a separate, successor-capable, zero-effect release policy first.

That policy must remain current across multiple related Hub objects. A progress snapshot, candidate, prepared request, direct predecessor receipts and optional predecessor result artifact loaded by separate connections could describe different database instants. Conversely, holding a SQLite transaction while running operator-selected Core would create an unbounded external-process lock and an unsafe availability boundary.

## Decision
Define independent canonical `ReadyReleaseControl` version 2 and `ReadyAuthorization` version 2 wires. Their digest domains are respectively `forge.group-agent-scheduled-ready-node-dispatch-release-control.v2\x00` and `forge.group-agent-scheduled-ready-node-dispatch-authorization.v2\x00`. They do not supersede, decode as or fall back to the existing scheduled release v1 types, command, versions or digest domains.

The dedicated Core command is `forge graph-scheduled-ready-node-dispatch-authorize --control FILE|-`. Its private-data preflight is `forge graph-scheduled-ready-node-dispatch-authorize --protocol-version`, which must produce exactly `2` on stdout, no stderr and exit zero. Runtime must complete that handshake before writing any control bytes. The public Runtime surface is `forge-runtime group graph run ready-release GRAPH_RUN_ID --core-bin ABSOLUTE_PATH --core-bin-sha256 SHA256` on the existing exact-current Hub only.

### Atomic discovery, A to authorization Core to B composition
Runtime first obtains a validated version-1 progress snapshot S0 through the existing atomic progress reader, releases that read transaction and invokes the existing pinned Core reconcile path. Runtime validates the exact source-bound reconcile decision and requires `ready` before reading release source A. Using S0's digest and the selected ordinal and node, Runtime then opens one deferred read transaction and loads atomic bundle A. The loader rebuilds the progress snapshot and requires the expected S0 digest and selection before it revalidates the exact Graph Run, Graph, schedule, selected candidate record and canonical candidate, prepared provider-request record, logical request and exact provider body, ordered direct predecessor receipt closure and any permitted content artifact. Every durable source, identity, count, ordinal, digest and presence relation is checked inside that transaction. After A closes, Runtime combines it with the exact reconcile decision to construct and validate control A. Neither the reconcile child nor the later authorization child runs while a SQLite transaction or lock is held.

The authorization Core strictly decodes the v2 control, independently reruns the ADR-0096 reconcile algorithm from the embedded snapshot and requires byte-for-byte equality with the embedded exact decision. Only `ready` is eligible. The ready ordinal and node must select the same candidate and request carried by the control. Core independently rebuilds their source contract and emits one authorization only if every reconstructed canonical byte and digest matches.

After the authorization Core returns, Runtime opens a new deferred read transaction and loads atomic bundle B through the same complete loader and expected S0 binding. B must be byte-for-byte identical to A, including its canonical digest and every optional closure member. Runtime constructs control B with the same exact decision, requires control A and B equality, then validates the authorization against B. Any intervening claim, terminalization, row replacement, extra or missing row, decision drift, Core error or non-ready disposition returns no authorization. Repeating an unchanged call may deterministically reproduce the same artifact, but every call reruns discovery, both Core validations and both source transactions; hashes are not freshness, consumption or idempotency authority. State can change immediately after B, so a later effectful step still requires an atomic snapshot-to-claim compare-and-swap.

### Initial and successor parity
Ordinal 0 uses only the initial-node candidate scope, an empty direct-receipt closure and `predecessor_content_included=false`. Ordinals 1 through 31 use only the successor scope. Their direct receipt IDs are exactly the schedule's canonical ordered direct-predecessor set; a same-wave successor may legitimately have an empty direct set, while ADR-0096 serial progression must still show every earlier ordinal completed.

Every present direct receipt is the exact canonical version-1 receipt for the same Graph Run, schedule, predecessor node, attempt, provider request, dispatch, Project lane and completed result-class terminal lifecycle. Its retry and successor-advance flags remain false, and its digest must equal both the durable source and the selected candidate binding. Ordering edges, transitive ancestors, unrelated completed nodes and caller-reordered receipts cannot satisfy the closure.

Predecessor content follows ADR-0033 and the scheduled-successor protocol. It is optional, never synthesized by this slice and legal only with a nonempty direct closure. When `predecessor_content_included=true`, exactly one content artifact is included: the durable terminalized result artifact bound by the first receipt in canonical direct-predecessor order. Its exact nonempty valid UTF-8 output has an independent 1-through-1,048,576-byte field bound and must equal the candidate user Prompt's `predecessor_output`; unlike task and acceptance prose, that already accepted output contract does not reject whitespace, control or bidirectional-control scalars. The complete artifact must separately fit its 1 MiB canonical bound, so these independent maxima do not necessarily compose. Prompt bytes and digest, candidate bytes and digest, receipt, provider-request identity and artifact all bind the same content. When the flag is false, both `predecessor_output` and the content artifact closure are absent. Uncertainty artifacts, non-result artifacts and content from any other predecessor fail closed.

The selected prepared-request envelope digest and the exact provider body digest remain separate bindings. Initial candidate storage remains capped at 4 MiB, successor candidate encoding at 8 MiB and provider body encoding at 16 MiB. No release policy may substitute one digest for another or materialize a missing candidate, request, receipt or artifact.

### Authorization, privacy and effects
The authorization binds the outer-control digest, snapshot, exact ready decision, Run, Graph, schedule, selected candidate, prepared envelope, exact request body, ordinal, node, attempt, Project lane, provider destination, budgets and failure policy. For successors, that outer-control digest transitively binds the ordered receipt closure, content-presence flag and optional artifact without echoing their private bytes or individual receipt digests in output. It fixes `maximum_future_node_releases=1`. Its future admission/execution/dispatch policy booleans are prerequisites for a separately reviewed step; all current admitted, released, claimed, sent, observed and terminal facts remain false. It is not a persistent counter, consumed grant or current lifecycle, execution or dispatch authority.

Core output and public Runtime JSON or Human output are metadata-only. They must not contain the outer control, progress snapshot, reconcile decision, control snapshot, Graph manifest, candidate JSON, Prompt, provider-request envelope or body, receipt JSON, artifact JSON or predecessor output. Errors are similarly redacted. The private Core input does contain Prompts, provider details, request bytes and possibly predecessor output, so the command uses a canonical absolute regular executable, explicit lowercase SHA-256, copied sealed executable bytes, empty environment, bounded stdin/stdout/stderr and deadlines. A v1 handshake, wrong pin, changed path, symlink, nonregular file, extra stdout, any stderr, timeout, signal or nonzero exit fails with no fallback.

The pin identifies bytes and handshake 2 identifies only this wire. Neither authenticates a publisher or function nor confines filesystem, network or syscalls. Only the repository-built official implementation may support the tested zero-effect claim; arbitrary operator-selected bytes remain a trusted same-user TCB. Runtime performs no logical Hub write or migration and does not read credentials or workspace files, construct a provider or transport, access a network, collect or consume consent, admit a lifecycle, release current authority, claim or release a lane, send, terminalize, persist a receipt, retry, resend, recover or advance a successor. SQLite may still perform ordinary live-reader SHM or sidecar coordination.

Neither `ready`, content presence nor this authorization implies consent. A later effectful step must independently obtain fresh `--confirm-off-machine` for the exact request and, exactly when predecessor content is present, separate fresh `--confirm-predecessor-content`. Neither consent is inferred from the other, a prior invocation, a receipt, a decision or an authorization.

### Closed bounds
The schedule remains at most 32 nodes with selected ordinal 0 through 31. The ordered direct closure contains 0 through 31 receipts, each at most 64 KiB, and at most one optional result artifact of 1 MiB. Progress snapshot and reconcile decision are each at most 64 KiB. Candidate and provider-body component bounds remain 8 MiB and 16 MiB, with the stricter existing 4 MiB storage boundary retained for an initial candidate. The exact request-v2 user Prompt ceiling is 6,553,926 bytes: identifier, task and acceptance retain their existing prose grammar and at-most-two-times JSON expansion, while the 1 MiB exact valid UTF-8 predecessor output permits ASCII controls with six-times inner JSON expansion.

The complete canonical v2 outer control has one supported aggregate cap of 64 MiB, and the metadata-only authorization is capped at 1 MiB. Component maxima are independent rejection limits, not a promise that snapshot, decision, successor candidate, provider body, all 31 receipts, optional artifact and longest wrapper metadata can be saturated simultaneously inside the aggregate cap. Decoders reject zero length or max-plus-one before typed decoding and require exact canonical JSON and EOF; programmatic encoders validate component objects and reject canonical output above the aggregate cap. Canonical serialization constructs its bounded result before the encoder's final aggregate-length check, so the 64 MiB limit is an ingress ceiling rather than a streaming or pre-allocation checked-arithmetic claim. Duplicate, unknown, reordered and trailing input fail closed. Boundary tests cover supported largest count and escaping shapes and reject top-level max-plus-one input; they do not claim an exact-fill valid object, arbitrary overflow compositions or simultaneous saturation of independent component maxima.

## Consequences
The next pre-effect slice can establish one source-complete future-release policy for either the initial node or an exact successor, including ordinal 31 and optional first-direct-predecessor content, while Core remains the sole owner of reconcile and candidate reconstruction. Runtime owns durable source validation and currentness rather than reimplementing the scheduling decision.

Version 1 remains stable and initial-only. Version 2 has a distinct command, handshake, wire and digest identity, so incompatibility fails explicitly instead of becoming an ordinal-zero fallback. The A-to-Core-to-B shape detects changes during Core evaluation without keeping an external process inside a database transaction.

The result still cannot be executed. `maximum_future_node_releases=1` narrows a future consumer but does not serialize concurrent callers, persist consumption or close the race after B. Two zero-effect callers may both receive the same deterministic metadata policy for unchanged state; this is safe only because neither call has an effect.

## Validation
Independent Go and Rust implementations must share compiled exact goldens for five positive shapes: ordinal-zero initial; successor with an empty direct set; receipt-bearing content-free successor; content-bearing successor with exact first-receipt result artifact; and ordinal 31. Each fixture must assert meaningful nonempty candidate and request bindings and independently reconstructed expected bytes, rather than only round-tripping one shared fixture.

The negative matrix mutates representative security-relevant bindings across the snapshot, decision, Run, Graph, schedule, ordinal, node, attempt, candidate, prepared envelope, body, Project lane, direct-receipt order and source, content flag, Prompt, artifact and digest chain. It also covers every non-ready disposition class, stale decisions, transitive or extra receipts, absent required rows, uncertainty artifacts and unchanged-but-noncanonical encodings. Every enumerated case returns no policy; this is a closed fixture matrix, not a claim to enumerate every possible byte mutation.

A real Application service over SQLite pauses its authorization Core port after A, commits a legal scheduled claim while that Core is paused, resumes it and requires B to reject the changed source; the successful intervening write also proves that no read transaction is held across the child. Separate lower-level SQLite snapshot tests cover concurrent-claim snapshot coherence and stale-snapshot rejection after terminalization. The inherited stored-progress corruption suite covers candidate, request, lifecycle, orphan, count, terminal receipt and artifact source drift, while mock Application tests cover selected candidate and aggregate source changes plus deterministic unchanged repetition. These are distinct evidence layers, not a claim that every durable row class is independently replaced between A and B.

Process validation combines v2-specific dual-handshake-before-private-input and wrong-pin cases with the shared pinned-Core process suite for malformed output, executable replacement, bounded stdout/stderr, timeout, signal and nonzero exit. Privacy and effect sentinels snapshot logical Hub tables, workspace files and loopback activity under poisoned credentials and endpoints, and assert metadata-only stdout/stderr. These observations support only the official tested Core path and are not syscall confinement evidence.

Both v2 top-level decoders reject zero length and max-plus-one input, and the authorization encoder and process bridge enforce the same 1 MiB output ceiling. Existing component codecs retain their own independently tested field and canonical-byte bounds. Positive boundary evidence covers the largest supported count shape of 32 nodes, 31 receipts and ordinal 31, the candidate's 1 MiB worst-control-escape predecessor Prompt, optional artifact presence, and a compiled Rust-to-Go whole-control case containing raw U+2028/U+2029 in both candidate and artifact. Numeric caps are rejection ceilings rather than a claim that every exact byte value is reachable by a semantically valid aggregate, so tests do not synthesize invalid padding or claim that mutually incompatible maxima compose. Full repository format, lint, architecture, tests and `forge accept` remain required delivery evidence, but a structural pass or this Proposed ADR is not acceptance, implementation completion or authority.

## Limitations
Version 2 does not admit or persist a lifecycle contract, release current execution or dispatch authority, acquire credentials, validate live destination or pricing state, construct a provider, access a network, claim a Project lane, send a request, produce or terminalize an artifact, persist a receipt, advance progress, retry, resend, adjudicate, recover quarantine or resolve hard-crash and uncertain-commit outcomes. It neither collects nor consumes off-machine or predecessor-content consent.

The remaining B-to-claim race, policy consumption, concurrent claim winner, PID-sidecar ownership and post-claim no-resend behavior belong to the later effectful one-node step. A durable whole-Graph controller, a second automatic node, failure propagation, concurrent schedule-v2 waves and remote exactly-once semantics remain later decisions. Untrusted-Core sandboxing, publisher authentication and function or effect attestation are also deferred.

All digests are unkeyed local integrity identities rather than signatures, freshness proofs or protection from same-user database rewriting. Metadata-only output does not make the private Core input public-safe, and empty environment plus sealed executable bytes do not isolate the child. Proposed status records this design candidate only; it supplies no ApprovalRecord, acceptance, compliance, implementation or effect authority.
