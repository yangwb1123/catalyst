# ADR-0081: Authenticated Architecture Decision Approval Authorization Service v1

## Context
ADR-0079 freezes exact v1 structures, digests, signature domains, proposal bindings, approval profiles, revocation relations and complete-ledger relations. Its Python core is deliberately structural: it neither consumes an external root pin nor verifies Ed25519, current time, revocation high-water, CAS or persistence. The proof-shaped golden signatures are not production credentials.

ADR-0057 and ADR-0058 contain useful mechanical patterns for strict canonical decoding, external pins, domain-separated signatures, key-last signing, idempotency, CAS and durable publication. Their roots, key usages, grants, repo.read permission and effect meanings are closed and cannot be imported or reinterpreted here. The existing grant state also has repo.read-specific layouts and a sixteen-megabyte ceiling, while the frozen approval ledger permits sixty-four megabytes.

The missing narrow slice is an in-process authorization-prerequisite service. It must take root identity, epoch, observation time and revocation high-water from an authenticated caller boundary; authenticate every signed input; preserve exact proposal bytes; and return no result until a newly signed complete ledger is atomically published, synchronized and reopened. It still cannot perform an ADR lifecycle transition.

## Decision
Propose two isolated stdlib-only Go packages: authenticatedadrapprovalcontract for exact ADR-0079 structural parity and authenticatedadrapprovalauthority for external trust, Ed25519 verification, currentness, state signing and durable CAS.

The contract package uses immutable validated documents and the exact ADR-0079 constants, bounds, digest preimages and seven signature domains. It reuses only the authority-neutral adrv2 and approvalrecordcontract semantic validators. It exposes strict bundle, input, standalone receipt and ledger decoding, canonical encoding, signature-check projections, replay facts and two-phase receipt and ledger drafts whose signatures must be supplied by the authority package. A structural golden success remains explicitly non-authoritative.

VerifyBundle accepts exact canonical bundle bytes plus an explicit external trust root SHA-256, trust epoch, trusted observation time and exact revocation high-water sequence and digest. It rejects the known ADR-0079 fixture root, every fixture public key, fixture namespaces and key identifiers. It verifies policy, revocation, request, ApprovalRecord authority, ApprovalRecord separation-of-duty, receipt and ledger signatures over their distinct NUL-terminated domains and raw thirty-two-byte artifact digests. It validates current authorization against the latest externally pinned revocation snapshot. Verification authenticates the supplied bytes relative to those external inputs; it does not prove that a supplied stored label or ledger was persisted.

AuthorizeAndStore loads the exact externally pinned root and state-signing seed from protected repository-external authority leaves. It structurally decodes the proposal, policy, complete revocation chain and request, authenticates every external signature, then acquires a nonblocking exclusive state lock and strictly authenticates the current ledger. Exact idempotent replay returns the same signed receipt without signing or writing. A reused idempotency key with different canonical policy, proposal or request fails. A new request must bind the exact current ledger digest and next sequence. All authenticated records are evaluated before applying policy_denied, authenticated_reject and insufficient_authenticated_approvals precedence. Its distinct opaque StoredAuthorization return is privately constructed only after fresh strict authenticated reopen or locked exact replay against the exact current state. Generic VerifyBundle continues to return only a VerifiedBundle and has no conversion to StoredAuthorization.

For a new decision the trusted observation time must not regress below the ledger clock high-water and must lie within every applicable half-open validity window. The request must bind the exact externally supplied revocation high-water, and the complete signed revocation chain must extend the stored chain by an exact prefix. Only after every rejection check does the service read a thirty-two-byte seed matching the independent approval_authorization_state_sign key. It signs the receipt and complete ledger under their distinct v1 domains.

The state root and every state component are bound by file identity. Authority and state directories are exact mode 0700 and owned by the effective UID. Root, seed, lock, ledger and temporary files are exact mode 0600, effective-UID-owned regular files with one link. Symlinked ancestors or leaves, special files, aliases, traversal and overlapping repository roots fail closed and are not repaired. Publication uses an exclusive same-directory temporary file, complete write, file synchronization, close and readback, a second CAS and binding check, atomic rename, directory synchronization and a fresh strict byte and signature reopen. Failure after rename is persistence-uncertain and returns no StoredAuthorization.

StoredAuthorization exposes a deep-copied VerifiedBundle view and, only for a current authorized receipt, a deep-copied AcceptancePrerequisiteSource. That source carries the exact signed receipt, its semantic and physical digests, exact ProposalBinding, approval root identity and epoch, complete-ledger digest, signature, last sequence and clock high-water, observation time and revocation high-water, plus exact profile, root and proposal bytes needed by a future builder. It carries no bundle digest, result, delivery disposition or stored boolean. The source is caller-mutable data and is not itself a capability: any future lifecycle mutation boundary must consume StoredAuthorization and compare the exact projection, never accept the source alone.

The full canonical bundle remains available only as the detached VerifiedBundle view. The ArchitectureDecisionApprovalAuthorizationResult remains the frozen unsigned five-field delivery envelope carrying the signed receipt. Its delivery_disposition neither establishes persistence nor participates in the prerequisite source, and changing it cannot create StoredAuthorization. A zero value, denied stored outcome, failed or uncertain publication, stale currentness, generic VerifiedBundle or caller-forged projection cannot produce an acceptance prerequisite.

The authority hard-excludes ADR-0079, the structural Go parity decision ADR-0080 and ADR-0081 from authorizing their own bootstrap. It imports no ADR-0057 or ADR-0058 package, root, key usage, signature domain, Grant, repo.read scope, permission or effect. It exposes no command, socket, route, registry, scaffold, repository write, accept, reject or supersede operation.

## Consequences
An authenticated in-process caller can obtain deterministic cryptographic verification and a crash-conscious stored-authorization capability without granting the service broader lifecycle or repository authority. A newly stored capability is withheld until the exact signed ledger reopens and revalidates; exact replay does not extend a receipt's expiry or bypass later revocation.

Policy denial, an authenticated reject and insufficient authenticated approvals are signed and stored audit outcomes, not transport failures, but none can project an acceptance prerequisite. Invalid signatures, stale external trust, revoked inputs, time regression, CAS mismatch, idempotency conflict, capacity exhaustion and unsafe state are failures that produce no result.

The implementation is Unix-only in this slice and depends only on the Go standard library plus the two authority-neutral internal contract packages. A future transport can wrap the internal API only after it defines peer authentication, framing, resource limits and trusted currentness sourcing.

## Validation
Require structural golden parity for the frozen Schema, golden and proposal pins, with exactly one physical LF and no instance LF. Mutate duplicate and unknown keys, JSON form, UTF-8, controls, bidi, depth, width, integer, base64url and every exact byte bound. Mutate every digest preimage, proposal byte and identity, role mapping, ApprovalRecord constraint, threshold, decision precedence, revocation link, receipt relation and ledger chain.

Generate fresh Ed25519 keys only inside tests. Verify every signature category independently, swap domains and usages, alter pins and epochs and require the proof-shaped golden authority and each fixture key to fail production verification. Exercise exact half-open time boundaries, clock regression, stale and mismatched revocation high-water, later approval and key revocation, self-excluded proposals, authorized proposal uniqueness and every replay and CAS branch.

Inject faults before and after temporary creation, write, file synchronization, close, CAS recheck, rename, directory synchronization, reopen, signature validation and bundle construction. Require no output for every failure and persistence-uncertain after any ambiguous publication. Require fresh and replay projections to match, every returned byte slice to be detached, unsigned delivery disposition to be irrelevant, and zero, forged, denied or noncurrent values to fail projection. Race identical and conflicting requests and require at most one append. Attack every path component, mode, owner, link count and file type. Run focused tests, the race detector, vet, formatting, strict ADR validation, export and line caps, and assert that no command, socket, route, registry, scaffold or repository mutation is introduced.

## Limitations
ADR-0081 remains Proposed and supplies no production root, key custody, HSM, signer process isolation, trusted clock, revocation publisher or authenticated caller transport. Exact file ownership and mode checks, seed clearing and same-UID tests are hygiene evidence; they do not prove private-key isolation or secure erasure.

The unsigned v1 delivery result cannot be described as independently signed. A direct result signature requires a versioned wire. VerifiedBundle and AcceptancePrerequisiteSource do not prove durable storage; only the in-process opaque StoredAuthorization preserves this operation-local boundary. Local lock, CAS, synchronization and reopen do not prevent a same-UID or privileged administrator from restoring an older valid signed snapshot. Administrator rollback resistance requires an external monotonic ledger checkpoint or protected hardware state.

One root epoch has one state-signing key and no rotation wire. Revoking that key prevents a valid new ledger from containing the revocation snapshot; recovery requires a newly pinned epoch and state namespace. The complete ledger stops at sixty-four entries and two hundred fifty-six revocation snapshots and has no rollover or compaction contract.

An authenticated authorization receipt is only a prerequisite. This service does not accept, reject, supersede, rewrite or persist an ADR document; set acceptance_id or accepted_at_unix_ms; create an acceptance lifecycle receipt, ledger or materialized view; register a capability, Grant, permission, effect, command, route or socket; write repository content; or close G0.
