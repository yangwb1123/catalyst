# ADR-0113: Authenticated Shared Conversation Coordinator v1

## Context
The approved personal multi-device product route needs one authenticated Coordinator through which CLI, TUI, Web, desktop App, and Mobile can view and continue the same Forge Conversation. The current Rust Hub remains the only canonical owner of Conversation, Prompt, and Run state under ADR-0007. ADR-0111 adds a local change journal and ADR-0112 adds a same-user read-only Go-to-Rust process bridge, but neither is an authenticated network API or authorizes a caller to read a Conversation. The old Hub records have no account owner; assigning every old Conversation to whoever logs in first would disclose private history and create an unaudited claim.

On 2026-09-13 the user approved implementation of the staged personal session and device route. That product approval does not transition this proposed ADR through the repository lifecycle. This document is a Proposed-only decision candidate; the formal v2 status and acceptance fields remain `proposed`, null, and null.

## Decision
Use Snaplink as the human identity authority and the Go Forge Coordinator as the only public API boundary. Before accessing any product route, Go must validate the bearer access token with a configured Snaplink resource-server verifier: exact allowed issuer, the configured Forge Coordinator audience, signature, expiry, and required route scope. Require nonempty `sub` and `tenant_id`; the authenticated Forge owner key is the exact `(issuer, subject, tenant_id)` tuple from verified claims. Do not normalize it, derive it from `client_id`, or accept any owner/tenant/issuer field from request JSON, query parameters, or headers. Use separate least-privilege scopes `forge:conversations:read` and `forge:conversations:write`. Health remains the only unauthenticated route. JWKS retrieval must use bounded HTTPS, reject redirects, and cap response bytes. Tokens are never persisted in the Hub or written to logs.

Persist the exact owner tuple in Rust Hub data keyed by Conversation ID. Owner binding is created in the same Rust Hub transaction as Conversation creation; every remote Conversation metadata, Prompt-history, and change query filters by that owner in SQL, and every Prompt/Run-seed write rechecks that same owner inside the Hub write transaction. The Go App Server enforces authentication and route scopes, while Rust is the final object-owner guard; Go must not create a second canonical session store or authorize from an untrusted caller-supplied ID. Store legacy Conversations with no inferred owner and do not return or mutate them through the network API. Login never claims or uploads local history; a later explicit claim/import flow must show the source, destination, selected Conversations, associated Projects, and content size and obtain consent.

Expose only bounded, versioned API operations for owned Conversation bootstrap, one-Conversation Prompt pages, and owner-scoped change replay, plus idempotent owned Conversation creation and Prompt submission. Do not use the existing full `snapshot_at_cursor` projection as a remote bootstrap. Read pages retain the existing 128-row and 256 KiB Prompt-content ceilings; change replay must not reveal another owner's IDs or content. Mutating requests require an idempotency key and expected Conversation aggregate version. A Prompt that starts a Run must use a server-authorized Project and server-owned execution profile, and Rust must atomically persist the owner check, user Prompt, and pending Run intent; the API reports only the durable pending intent, never execution success. The caller cannot select an arbitrary workspace path, provider credential, tool capability, or Runner.

The initial deployment is one self-hosted logical Coordinator reachable only through private-network/VPN HTTPS. Bind only an explicit private interface or loopback behind an operator-managed private HTTPS ingress; reject wildcard/public listener addresses and remote plaintext HTTP. Browser access uses an explicit origin allowlist. Public-internet SaaS exposure, multi-user team ACLs, multi-Coordinator federation, HA, Runner enrollment, and remote execution are later stages with separate decisions. Runner credentials remain distinct from human access tokens.

## Consequences
The verified Snaplink principal has one canonical mapping to each remotely visible Conversation, and owner checks remain in the Rust Hub transaction boundary instead of relying on a Go-side precheck or a second database. Pre-existing local Conversations remain private and unclaimed until an explicit import flow exists. The authenticated API can reuse bounded Hub query pages and the store-local change cursor only after owner-filtered access is implemented; the cursor remains neither an account ID nor an audit sequence.

This decision adds requirements to the existing read-only Runtime bridge: a versioned owner-aware query/write operation, current-schema migration, exact principal validation, and transaction-level access checks. The bridge's local process trust is not sufficient for network callers. The intended first reachability model avoids public ingress but still requires TLS, validated tokens, route scopes, object checks, and safe client-origin policy. API operations that only seed a Run do not imply that an Agent or device has executed it.

## Validation
Before any route is exposed, verify the exact Proposed-only ADR v2 document contract and keep `accepted_at_unix_ms` and `acceptance_id` null. Against a real Hub, prove the additive ownership migration preserves existing rows as unowned, exact tuple ownership survives reopen, ownership creation is atomic with Conversation creation, and injected failures roll back both ownership and Prompt/Run intent. Prove owner-filtered SQL denies an absent owner, a different issuer, subject, or tenant, and never returns another owner's IDs, metadata, Prompt bodies, or change records. Prove legacy unowned records are not implicitly claimed.

At the Go HTTP boundary, prove missing, malformed, expired, wrong-issuer, wrong-audience, missing-scope, missing-subject, and missing-tenant tokens fail closed; JWKS redirects, oversized responses, and insecure remote URLs are rejected. Prove verified claims, rather than request fields, determine the Hub owner. Exercise two independently authenticated client instances against the same server for bounded bootstrap, page continuation, Prompt retry, expected-version conflict, and cross-owner denial. Verify private HTTPS deployment configuration rejects wildcard/public and remote plaintext listeners and that disallowed browser origins cannot read authenticated responses.

Run focused Go authentication/route/runtimebridge tests (including race tests and vet), Rust Hub migration/owner/transaction tests, real Go-to-Rust process E2E, repository architecture and governance checks, independent security review, strict Clippy, and final same-tree `node harness/acceptance.mjs`. None of these results is claimed by this Proposed ADR itself.

## Limitations
This candidate does not provision an OAuth client, implement Snaplink login/device authorization UX, complete CLI/TUI/Web/App/Mobile clients, or establish external production keys. It does not provide a complete Run timeline, Agent execution dispatch, Runner identity/inventory, resource placement, lease/fencing, Vault staging, Audit Governance outbox, Aero IM notifications, Aero-ID profile integration, team ACLs, multi-tenant collaboration, HA, public service deployment, or federation. Those remain staged requirements in the approved implementation plan. Proposed metadata and a passing structural checker do not constitute ADR acceptance, security review, product completion, or permission to expose a route; the API remains unavailable until implementation and same-tree acceptance prove these boundaries.
