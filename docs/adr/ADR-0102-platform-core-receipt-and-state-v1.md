# ADR-0102: Platform Core Receipt and State v1

## Context
Platform Core Envelope v1 gives Go control, Rust runtime, and Harness one bounded identity, scope, command, event, and ArtifactRef vocabulary, but deliberately leaves execution outcome, verification input/result, product state edges, and machine-readable rejection classes undefined. Building a journal or Objective-to-Outcome controller before these records agree across languages would force storage and transport choices to become accidental protocol semantics. Reusing the existing Kernel operational ExecutionReceipt or completion-evidence shapes would also conflate specialized governance closure with product Attempt and Harness ownership.

The next safe increment is therefore a pure supplied-bytes boundary. It must say what Runtime claims to have observed for one Attempt, what Harness is asked to check against one immutable Artifact, what Harness claims it observed, and which state edges are in vocabulary. It must also prevent `not_applicable`, `not_executed`, or a structurally valid Approval reference from being interpreted as pass, authority, transition, persistence, or completion.

## Decision
Adopt Platform Core Receipt and State v1 as three exact canonical JSON families plus pure state-edge functions. ExecutionReceipt binds an exact session-level ScopeRef, Attempt/Session/ProjectSnapshot references, executor actor and adapter version, nullable unresolved Grant/Approval RecordRefs, bounded observed usage, terminal Attempt state, sorted input/output ArtifactRefs, optional event range, timestamps, and reason codes. Input Artifacts cannot postdate start; output Artifacts must bind the receipt Attempt/Snapshot and execution interval. Only interrupted, completed, failed, and uncertain are receipt terminals; completed alone has no reason codes.

VerificationRequest binds one `ver_` ID, requester declaration, request time, Attempt/Snapshot scope, one immutable input ArtifactRef, and 1–64 sorted check declarations. `declared_required` remains an inert declaration for a future completion-policy consumer. VerificationReceipt binds one `rcp_` ID, exact request digest and verification ID, the same scope and input, a Harness actor declaration, timing, and exact sorted result coverage. Results distinguish applicable from not-applicable, require a reason for N/A, and use pass/fail/inconclusive/not_executed. Overall status is derived over applicable results with fail above inconclusive above not_executed above pass; all-N/A derives not_executed.

Freeze explicit WorkItem, Attempt, and Action directed edges. Terminal Attempt and Action states cannot reopen; retries use new Attempt identity. WorkItem failed, blocked, or uncertain may return only through the documented remediation edges. Edge membership is a pure vocabulary check, not current-state or transition authority. The planned-to-ready and requested-to-approved shortcuts merely permit a later authenticated policy decision; they do not supply one.

Expose seven broad stable rejection classes: document invalid, identifier invalid, value invalid, reference mismatch, state invalid, transition invalid, and relation mismatch. Human diagnostics remain unstable. Go, Rust, and Python independently reconstruct one shared golden and consume one JSON-pointer mutation corpus. Keep the Schema a non-load-bearing structural shadow and keep all App Server, database, CAS, journal, transport, execution, policy, and completion paths disconnected.

## Consequences
The three component languages can now exchange the next Platform Core shapes without inventing transport-specific terminal, applicability, N/A, or error semantics. A future Runtime journal and Harness bridge can bind their durable records to exact request/receipt bytes, and a future controller can distinguish valid edge vocabulary from the separate authority to apply an edge.

The wire is intentionally redundant: receipt references repeat scope identities, verification receipts repeat the immutable input, and request digest plus verification ID both bind a pair. Those equalities turn substitution into a deterministic rejection before persistence. Sorted sets and fixed limits also make canonical reconstruction and resource bounds explicit.

This candidate does not complete PC-03 through PC-08 or Platform Core v1 by itself. It closes the pure ExecutionReceipt, VerificationRequest/Receipt, state-vocabulary, and broad rejection-code portions, while durable sequence/idempotency consumers, current/previous compatibility, legacy mapping, live Harness production, Runtime replay, App Server APIs, and Objective-to-Outcome completion remain separate work.

## Validation
Pin one golden in which a completed Runtime receipt exposes an output Artifact that becomes the immutable verification input. Include both one applicable passing check and one explicit not-applicable/not-executed check with a reason, then bind the receipt to the exact request digest. Go, Rust, and Python must reproduce all three domain-separated SHA-256 values and exact round trips.

Consume the same mutation corpus in all three languages. It covers unknown fields, nonterminal execution receipts, valid-but-foreign Attempt refs, duplicate check IDs, missing N/A reasons, overall-status elevation, request-digest substitution, and terminal-state reopen attempts. Add language-specific tests for noncanonical framing, boolean/integer confusion, exact 32/33 Artifact, 64/65 check, and 16/17 reason boundaries, event/timing drift, output producer substitution, all-N/A derivation, and incomplete result coverage. Existing Envelope v1 tests must remain unchanged and pass with the new coded error carrier.

Run focused and full Go tests including race and vet, all Rust workspace targets with formatting and strict Clippy, isolated Python conformance suites and checker modes, optional JSON Schema shadow validation, ADR v2 validation, file/function/architecture/governance gates, fresh-context architecture and security review, and full repository acceptance. Formal completion markers may be retained only if acceptance passes on that exact tree.

## Limitations
All IDs, actor types, usage, timestamps, states, events, Artifact metadata, evidence, Grant refs, and Approval refs are caller-supplied. Validators do not authenticate a producer, resolve a digest, inspect Artifact bytes, verify metering, check revocation/expiry, observe current state, reserve idempotency, guarantee event continuity, or write durable state. A valid event range is not a journal receipt; a valid evidence ref is not truth; a valid Approval ref is not effective approval.

The broad error class identifies a stable failure family, not a complete list of all defects in one document. Validation is fail-fast and callers must not depend on diagnostic wording or assume later fields were examined. The v1 bindings preserve unknown state and status text through typed decoding and classify it during semantic state validation as state invalid; wrong JSON scalar types remain document invalid.

Verification overall status summarizes supplied applicable results, not project policy. `declared_required` has no effect until a future authenticated completion consumer resolves the request, evidence, applicability, waiver, freshness, and policy context. Neither ExecutionReceipt completion nor VerificationReceipt pass can alone complete a WorkItem or Change. ADR-0102 remains Proposed; structural parity and repository acceptance are implementation evidence for this narrow candidate, not an authenticated ADR lifecycle transition or product-readiness claim.
