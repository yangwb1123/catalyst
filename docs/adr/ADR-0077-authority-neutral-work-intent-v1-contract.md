# ADR-0077: Authority Neutral WorkIntent v1 Contract

## Context
ForgeOS has versioned records for source snapshots, evidence, claims, approvals, grants, transitions and journals, but those records do not define one bounded declaration of what a requester says should be investigated or changed. Reusing an authority-bearing record would collapse lexical intent, authenticated identity, ownership, materiality, approval and execution into one ambiguous object. Reusing Run or RunJournal would also imply lifecycle or persistence that a declaration cannot establish.

This candidate needs a deterministic cross-language wire before any route, policy or runtime integration can be considered. It must carry exact caller-supplied bindings, narrative intent, origin labels and reference declarations while keeping every semantic attestation false. The contract can validate canonical bytes and self-identity; it cannot authenticate an origin, resolve references, determine materiality or scope, create ownership or permission, close G0, choose a route, prove a Run or RunJournal exists, or authorize work.

ADR-0056 supplies the exact three-field principal shape for `requester` and the non-null branch of `declared_owner`. ADR-0059 supplies the exact local artifact declaration triple. ADR-0045 supplies the exact optional source snapshot declaration triple. Those shape reuses do not import the authority, approval, evidence, freshness or runtime semantics of the source contracts.

## Decision
Propose the authority-neutral `forgeos.work-intent/v1` candidate wire with exactly sixteen top-level fields: `api_version`, `attestations`, `binding`, `canonicalization`, `declared_at_unix_ms`, `declared_owner`, `freshness`, `intent`, `kind`, `materiality`, `origin`, `references`, `requester`, `status`, `work_intent_id` and `work_intent_sha256`. There is no top-level `ownership` field. Constants are `kind=WorkIntent`, `canonicalization=forgeos.canonical-json/v1`, `status=declared_unassessed` and `freshness=not_evaluated`.

`requester` is one exact ADR-0056 principal containing `authority_domain`, `principal_id` and `principal_type`; `declared_owner` is null or that same exact shape. Principal type is only `agent`, `human`, `operator` or `service`. These values are lexical caller declarations and do not authenticate identity, authority or ownership. `binding` contains exact lexical `change_id`, `project_id` and nullable `run_id` fields; it does not prove any referenced object exists.

`intent` contains nullable `deadline_unix_ms`, `external_constraints`, `goal`, `non_goals`, `open_questions`, `scope`, `success_signals` and `work_type`. A deadline may precede `declared_at_unix_ms`; no clock or scheduling assertion is made. Scope and success-signals arrays contain one through 64 entries, the other narrative arrays contain zero through 64, and all five arrays contain at most 256 entries in total. Every narrative array preserves authored order, is unique by exact string and is not sorted. Work type is one of `question`, `defect`, `small_change`, `feature`, `refactor`, `migration`, `incident_response` or `architecture_evolution`.

`materiality` contains `basis=caller_declaration_only` and a level of `materiality_not_bound` or `L0` through `L4`. It is not a materiality assessment. `origin` contains an `origin_kind` of `user_request`, `runtime_signal`, `incident`, `technical_debt`, `reflection_proposal`, `operator_request` or `other`, plus nullable `origin_ref`. It is not origin authentication.

`references` contains claim and evidence record-reference arrays, local artifact declarations and a nullable local source snapshot declaration. Each record reference is exactly `record_id` plus `canonical_sha256`; `record_id` uses the ADR-0045 lowercase identifier grammar. Each record array has at most 64 entries, the two arrays have at most 128 entries in total, each array is strictly sorted and unique by `record_id` UTF-8 bytes, and claim and evidence record IDs are mutually disjoint. Each local artifact declaration is the exact ADR-0059 `artifact_kind`, `artifact_ref`, `artifact_sha256` triple; the array has at most 32 entries, is strictly sorted and unique by complete canonical member bytes, and an artifact kind/reference pair may occur only once even with a different hash. The snapshot is null or the exact ADR-0045 `snapshot_id`, `snapshot_sha256`, `snapshot_type` triple. Validation neither loads nor resolves a reference.

`attestations` contains exactly fourteen boolean fields, all exactly false: approval, authentication, authority, completion, effect, execution, freshness, materiality, ownership, permission, persistence, reference-resolution, scope and truth, each with the `_attestation` suffix. No other attestation field is admitted.

Instances are exact compact canonical UTF-8 JSON without a trailing LF. JSON is bounded to depth eight, 32 fields per object, 256 items per generic array, 16,384 UTF-8 bytes per string, 160 bytes per short value, 4,096 bytes per reference and signed-int64 integers. Both the sealed instance and its blank-identity preimage are at most 262,144 bytes. Floating and non-finite numbers, duplicate keys, forbidden control or bidirectional Unicode scalars and noncanonical encodings are rejected.

The self digest is SHA-256 over ASCII `forgeos.work-intent.v1` followed by NUL and the complete canonical record with only `work_intent_id` and `work_intent_sha256` replaced by empty strings. `work_intent_sha256` is the lowercase digest and `work_intent_id` is `work-intent-` followed by that digest. The golden physical file is the exact canonical sealed record followed by one LF; the LF is fixture framing and is not valid instance framing.

Record the Python, Go and Rust semantic validators, JSON Schema, deterministic golden fixture and focused checks as candidate implementation evidence. All three implementations bind the same Schema, golden physical bytes and record digest. This Proposed decision does not adopt a route, registry entry, governance activation, scaffold distribution, persistence model or runtime consumer.

## Consequences
Callers and the three candidate language implementations gain one precise byte-level candidate for expressing declared intent without promoting it to authority. Exact digest identity makes fixture and implementation comparisons deterministic, and explicit shape reuse avoids subtly different principal, artifact and snapshot members.

The record is intentionally incomplete as operational state. A structurally valid result says only that the caller-supplied bytes satisfy this candidate contract. It says nothing about whether the requester or owner is authenticated, references exist or are current, a scope or materiality level is correct, a deadline is feasible, work is permitted, G0 is closed, a route selected, a Run created, a journal persisted, or an effect executed.

This candidate adds another bounded record type and requires later implementations to preserve exact UTF-8 ordering, canonical JSON, cross-array identity constraints, authored narrative order and domain-separated self hashing. JSON Schema alone cannot enforce every ordering, aggregate-count, cross-array or digest rule, so the semantic validator remains necessary.

## Validation
Validate the JSON Schema and require it to accept the exact deterministic golden structure. Require the fixture physical SHA-256, exact one-LF framing, deterministic reconstructed bytes, record digest and ID to match. The instance decoder must accept the fixture with its one LF removed and reject the physical fixture itself.

Exercise exact and missing fields, unknown fields, constants, all fourteen false attestations, ADR-0056 principals including rejection of `tool`, nullable owner and run binding, an early deadline, work and origin enums, materiality basis, nonempty scope and success signals, per-array and aggregate narrative limits, exact duplicate rejection and preservation of unsorted authored narrative order.

Exercise record-reference UTF-8 ordering, uniqueness and claim/evidence ID disjointness; artifact canonical ordering, uniqueness and same-pair/different-hash rejection; and the nullable exact ADR-0045 snapshot shape. Exercise strict canonical bytes, no-LF instance framing, duplicate JSON keys, floats, non-finite values, invalid UTF-8, forbidden scalars, depth, signed-int64, string UTF-8 limits, exact 262,144-byte acceptance, 262,145-byte rejection and mutations of each self-identity field.

Require Python, Go and Rust to accept the same canonical golden record, reproduce the same domain-separated record digest, preserve identity-neutral digest calculation while keeping decode, seal and validate strict, and fail closed on the same structural, semantic and exact-boundary mutations. Go and Rust remain repository-local candidate implementations with no route, consumer, persistence or runtime adoption.

The focused CLI has mutually exclusive golden and file modes. Success emits exactly the frozen structural marker plus LF. Failures emit no success stdout. The marker explicitly denies origin authentication, reference resolution, G0, routing, Run or RunJournal existence, lifecycle, approval, authentication, authority, completion, effect, execution, freshness, materiality, ownership, permission, persistence, scope and truth attestation.

## Limitations
This candidate does not acquire, infer, author, repair, default, merge, route, persist, refresh or execute intent. It does not inspect a repository, request channel, clock, identity provider, policy, evidence store, claim store, graph, journal, runtime, network, credential or effect system. Origin and binding values remain unverified lexical labels.

Digest validity is data integrity under a public algorithm, not authentication, signature, provenance, freshness, truth or authorization. Reference hashes are caller declarations and are never dereferenced. A declared owner is not verified ownership; a requester is not an authenticated principal; a materiality level is not a materiality verdict; declared scope is not complete or accepted scope.

ADR-0077 remains Proposed. It grants no semantic authority, closes no gate or roadmap package item, creates no authenticated route, Run, RunJournal or lifecycle transition, and changes no production behavior. Acceptance, governance activation, portable packaging, scaffold distribution, persistence and runtime use each require separate evidence and decisions.
