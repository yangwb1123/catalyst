# ADR-0080: Authenticated Architecture Decision Approval v1 Proposed Candidate Governance and Source Distribution

## Context
ADR-0079 freezes the prospective wires for Authenticated Architecture Decision Approval v1 and an isolated dependency-free Python structural core. Its golden includes proof-shaped keys, signatures, policy, request, receipt, revocation and ledger data, but the checker deliberately performs no Ed25519 verification and consumes no external trust root, trusted time, revocation high-water or durable state. An exact structural success therefore cannot authenticate or authorize anything.

The standalone candidate needs a separate governance decision before shared Registry and Agent Engineering metadata can refer to it or generated projects can receive its validation sources. That integration must preserve ADR-0079's negative boundary: caller-supplied root, time, revocation and ledger relations are declarations, not current or trusted facts, and an authorization-shaped receipt is not an issued receipt or ADR lifecycle event.

The narrow distribution target is the existing Python structural source set and its exact artifacts. A future authenticated verifier, Go service, production keys, isolated signer, durable ledger or lifecycle controller has not been designed and cannot be implied by source presence.

## Decision
Propose Registry v33 candidate-only metadata for the unchanged ADR-0079 structural prerequisite. Bind the Schema physical SHA-256 `9882e45816f3c3a6e2d84ba09d942848dcc1eae90d3d5193b9cf18b6ebe27198`, golden physical SHA-256 `936b989856ff733e2de848ba9907c10f9f626aa188648fc60372775e44dbc7b5`, proposal physical SHA-256 `6beabf33656998b942036b63c90db99c6a5f9b138cf2e5bd4a5372ec8e1ad1f2`, proposal body SHA-256 `9a798ab129919d51d8b2a3c842d281b19c1d1667a180ef8cbd4f690465730a63` and proposal self SHA-256 `1d2579dafcf152c302e22cfa4d6932e248f1171eef812297f601b60ce7ed208f`.

The complete Registry `scope` mapping remains byte-semantically unchanged with canonical SHA-256 `8ba82b638e8031f0d1be2b9ea6d522a4b9cf064a4ed532e1f0d3281f2dfe874c`. The v33 runtime-binding text is descriptive policy metadata only. It adds no kind, route, runtime profile, evaluator, producer, service, lifecycle controller, persistence or effect.

Record one Python reference implementation: the isolated structural core and strict golden checker. Source-only fresh and legacy generated-project distribution may copy the exact thirteen-file Python package, checker, focused core test, Schema, golden, proposal, ADR-0079, ADR-0080 and governance module and test. It must not copy a future Go service, production keys or state; install a Skill or adapter; or add a route or runtime consumer.

Add one checker-only, non-load-bearing shadow detector that runs `python3 harness/authenticated_adr_approval_contract_check.py --golden repo_root`. Activation references point only to the Schema, golden, proposal, checker, ADR-0079 and ADR-0080. The contract discipline lists only the Schema and checker as candidate assets. All six references remain absent from authenticated context routes.

The Registry authority fields are all false. The candidate does not verify Ed25519 or separation-of-duty proofs; authenticate a root, key, principal, proposal or publisher; authorize acceptance; sign, mint or issue a receipt; consume an external root pin; establish trusted time or current revocation; provide CAS, durability or rollback resistance; accept or transition an ADR; close G0; or persist, execute or effect anything.

Documentation may mark only the Wave 0 Proposed structural prerequisite evidence bullet complete. Full authenticated approval, authenticated ADR lifecycle, G0 and every package implementation item remain open.

## Consequences
The shared Registry and Agent Engineering checks gain an exact mutation-tested description of the Proposed structural prerequisite. Artifact and decision pins expose deterministic identity while the unchanged scope mapping prevents administrative versioning from appearing as runtime adoption.

Generated projects can reproduce the exact Python structural checks without receiving a verifier service or deployment trust material. Copy parity is only source-distribution evidence; it authenticates neither the source nor the interpreter and provides no check-to-use atomicity.

Any future authenticated validity, authorization, receipt issuance, durable ledger or lifecycle transition requires a separate decision and external authority inputs. ADR-0079 and ADR-0080 remain Proposed and cannot bootstrap or accept themselves.

## Validation
Validate ADR-0079 and ADR-0080 with the strict ArchitectureDecisionRecord v2 checker and compare body, self and physical pins. Re-run the unchanged Python candidate suite and golden CLI with site packages disabled.

Mutation-test Registry v33 candidate metadata, canonical references, Schema, golden and proposal pins, Python implementation placement, non-capability text and the complete unchanged `scope` mapping. Reject any enabled authority semantic or insertion into a scope array.

Run Agent Engineering checks for the exact activation references, Schema and checker discipline assets, one checker-only shadow and complete authenticated-route absence. Require the exact structural-only success marker.

Run source-only fresh and legacy generated-tree checks with exact bytes, regular mode `0644`, closed copy inventory and no future Go service, production key, durable state, Skill, adapter, route or runtime consumer. A generated tree that omits Catalyst-only documentation must still run Registry, artifact, CLI, wiring, detector and strict ADR checks.

Run focused governance, agent, repository check, gate and architecture checks without the long suite. Verify documentation closes only Proposed structural prerequisite evidence while full authenticated approval, authenticated ADR lifecycle, G0 and package work remain open.

## Limitations
This decision does not verify Ed25519 or any proof byte. It does not authenticate a root, key, principal, requester, approver, owner, implementer, subject, proposal, repository, publisher, host or interpreter. It consumes no external root or epoch pin and proves no trusted time, freshness or current revocation.

It does not sign, mint or issue a receipt; provision or isolate a key; provide a service, socket or HSM; persist a ledger; perform durable CAS, fsync, atomic replacement, crash recovery, replay, reopen, retention or rollback resistance; or attest that the caller-supplied stored label represents storage.

It does not accept, reject, supersede or transition an ADR; create an acceptance receipt or lifecycle ledger; register a capability, Grant, permission, route, evaluator, producer or runtime profile; close G0; install a Skill or adapter; execute an effect; or claim semantic authority. Full authenticated approval and ADR lifecycle remain unavailable.
