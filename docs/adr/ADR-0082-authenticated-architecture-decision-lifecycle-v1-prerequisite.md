# ADR-0082: Authenticated Architecture Decision Lifecycle v1 Prerequisite

## Context
ArchitectureDecisionRecord v2 deliberately freezes every new source document at status proposed, null acceptance_id and accepted_at_unix_ms, and empty superseded_by. ADR-0079 freezes an approval-prerequisite wire; ADR-0081 adds an internal authenticated authorization service but explicitly cannot accept, reject, supersede or rewrite an ADR. A durable authorization receipt is necessary but is not an ADR lifecycle event and does not establish architecture compliance.

A lifecycle transition must preserve exact Proposed bytes while recording derived Accepted and Superseded state elsewhere. It must atomically relate one new acceptance to every intended supersession target, reject stale or partial target sets, and make a complete materialized view reproducible from an append-only ledger. The first deliverable remains structural because no lifecycle key provisioning, live authority API, repository mutation protocol or durable state path has been adopted.

## Decision
Propose Authenticated Architecture Decision Lifecycle v1 as an independent structural prerequisite and implement only its dependency-free Python candidate validator, Schema, deterministic golden and adversarial fixtures.

The top bundle contains the generic SignatureProfile, exact ADR-0079 approval trust root, an independent lifecycle trust root, one signed-shaped lifecycle state image and one unsigned delivery result. Lifecycle and approval roots have different domains, root identities, key identifiers, public keys and principals. The lifecycle root has exactly one request-authentication key and one state-signing key. Every signature remains proof-shaped data: the candidate checks profile, root usage, domains, self-digests and relations but never verifies Ed25519 or consumes an external root pin.

Each ArchitectureDecisionAcceptancePrerequisite embeds the exact ADR-0081 authorization receipt and ProposalBinding, binds approval root and epoch, exact receipt canonical bytes including signature bytes, signed-ledger digest/signature/sequence and clock high-water, revocation high-water and one observation time. The projected approval ledger retains ADR-0081's exact maxima of sixty-four entries and two hundred fifty-six revocation snapshots; its clock high-water lies from the embedded receipt evaluation time through the observation time, and the receipt prior link is null exactly at approval-ledger sequence one. It deliberately contains no stored boolean or unsigned authorization delivery disposition. Serialized structure cannot distinguish generic VerifyBundle output from the live AuthorizeAndStore fresh-reopen or locked exact-replay provenance required by a future lifecycle authority. A future effectful API must accept the raw transition request plus a nonforgeable StoredAuthorization handoff, compare every embedded prerequisite byte and use the same trusted observation instant; a structural decoder alone can never grant transition authority.

A transition request embeds exact strict Proposed ADR v2 bytes, the prerequisite, a 16 through 128 byte idempotency key, half-open validity, lifecycle root binding and signature, and CAS expectations for the next lifecycle sequence, prior complete logical ledger digest and prior structural current-head-set digest. It binds sorted target refs containing each target ADR ID, ProposalBinding digest, acceptance ID and acceptance digest. The target IDs must exactly equal the immutable proposal frontmatter supersedes array. Genesis has sequence one, null prior ledger and prior entry, and the domain digest of the empty structural head set.

One versioned ledger entry contains exactly one acceptance receipt and zero through sixty-four supersession receipts sorted by target ADR ID. All target refs are checked against the same prior rebuilt view before any update. Each target must exist as a current derived Accepted row, and the new ADR must be absent. The entry either derives the new acceptance and every target supersession together or is invalid; missing, legacy, already-superseded, stale, partial, extra, duplicate or reordered targets fail. Every target receives exactly one direct superseded_by edge. Self, forward, dangling, fork and cycle relations fail.

The digest dependency order is prerequisite, request, acceptance, supersession receipts, entry, ledger, materialized view, then state. Acceptance and supersession receipts do not hash a resulting head, avoiding a digest cycle. The structural head-set domain covers only sorted ADR ID and ProposalBinding pairs for unsuperseded rows. Approval-ledger sequence and lifecycle-ledger sequence are independent and are never compared or ordered across ledgers.

The complete logical ledger has contiguous lifecycle sequences, exact prior-entry links, unique idempotency record keys and unique embedded authorization receipt physical identities. Each non-genesis request binds the exact reconstructed prior ledger and head set. The exact view is rebuilt from the complete ledger, sorted by ADR ID, and contains source identities, proposed/expiry times, acceptance evidence, forward supersedes edges, at most one reverse superseded_by edge and status accepted or superseded. Head means structurally unsuperseded, not time-current or effective. Ledger and view live inside one signed-shaped state image so a future service can publish one file rather than independently rename two snapshots.

The golden has three lifecycle entries. Sequence one derives ADR-9003 Accepted; sequence two derives ADR-9004 Accepted; sequence three derives ADR-9005 Accepted while exactly two sorted receipts supersede ADR-9003 and ADR-9004 in that same entry. All three source documents remain byte-for-byte strict Proposed v2 with null acceptance fields and empty superseded_by. Their approval receipt sequences intentionally appear as two, one and seven to prove approval and lifecycle ledgers are independent.

New transitions require a future live durable StoredAuthorization capability. Exact idempotent replay is a historical no-effect read: it must run before stale CAS or capacity checks, return the original receipt and state without signing or writing, and remain readable after the upstream authorization window closes or its keys are later revoked. A conflicting use of the same key fails. The current unsigned stored or exact_replay result labels attest neither persistence nor provenance.

Canonical JSON is exact compact forgeos.canonical-json/v1 with duplicate and unknown rejection, raw UTF-8 key ordering, signed-int64 integers, no floats, maximum depth sixteen, object width sixty-four and array width two hundred fifty-six. Controls, DEL, bidi controls, surrogates, U+2028 and U+2029 are forbidden. Bounds are 16 KiB profile, 64 KiB lifecycle root, 256 KiB proposal and each receipt, 1 MiB request, 4 MiB entry, 64 MiB ledger, 8 MiB view, 80 MiB state and 96 MiB bundle/golden. A maximum of 256 entries/decisions and sixty-four supersessions applies; enclosing ceilings still win when child maxima cannot coexist. The physical golden is canonical instance bytes plus exactly one LF; instance mode rejects that LF.

## Consequences
The exact proposal identity, authenticated-authorization-shaped prerequisite, target set, lifecycle receipts, append-only CAS relations, atomic-entry grouping and materialized state become deterministic mutation targets. A later authority implementation can consume one closed wire without changing source ADR bytes or conflating authorization with acceptance.

The source ADR remains Proposed forever in this contract. Accepted and Superseded are derived lifecycle-view statuses, not frontmatter edits. Acceptance proves a recorded decision only after a future authority and durable repository transition exist; it never proves implementation compliance, fitness, completion, permission or effect.

The single state image removes a future two-file ledger/view publication ambiguity, but structural validation of supplied bytes does not prove the image was atomically written, synchronized, reopened, retained or protected from rollback. Current-head labels are clock-free structural graph state; source expiry remains in each row for a trusted reader to evaluate.

## Validation
Require deterministic reconstruction of the Schema, golden, three proposal fixtures and every domain digest. Validate the Schema offline with explicit registration of the pinned ADR-0079 approval Schema; missing external resolution fails closed. Validate ADR-0082 and ADR-9003 through ADR-9005 as strict Proposed v2 documents.

Mutate duplicate and unknown keys, JSON form, UTF-8, controls, bidi, depth, width, integers, base64url tails and every byte/count bound. Mutate each source byte, Proposed constant, body/self/physical identity, embedded authorization receipt including signature bytes, prerequisite, root relationship, time relation, idempotency key, CAS expectation, target ref, acceptance, supersession, entry, ledger, view, state and result relation.

Exercise genesis and non-genesis, empty and multi-head sets, stale ledger/head CAS, prefix rewrite, entry reorder, missing/legacy/already-superseded targets, partial/extra/reordered receipts, duplicate ADR, reused and conflicting idempotency, fork, cycle, dangling edge, source proposed/expiry boundaries and nondecreasing observation time. Require the approval receipt sequence order two then one to validate, proving no accidental lifecycle coupling. Mutate proof-shaped signatures and reseal every structural digest to demonstrate that structural success still does not authenticate Ed25519.

Run with Python site packages disabled and require the dependency-free suite to pass with exactly one optional offline jsonschema skip. Check regular files, mode 0644, one link, line/function caps and absence of cache. Run focused tests, checker, strict ADR validation and an independent semantic review before recording pins.

## Limitations
ADR-0082 remains Proposed. It provisions no lifecycle or approval root, private key, signer, HSM, trusted clock, revocation publisher, nonforgeable StoredAuthorization capability, state directory, lock, CAS service, filesystem protocol, repository writer, command, socket, route, registry, scaffold, Skill, Grant, permission or effect.

The proof-shaped fixture approval root is rejected by ADR-0081 production verification. Neither an offline VerifiedBundle nor a caller-declared ledger signature/digest is consumable lifecycle authority. Because the lifecycle ledger stores only the signed receipt and state bindings rather than the complete approval bundle/ledger, it cannot independently replay ADR-0081 verification or prove durable provenance; a future live service must compare the serialized prerequisite against an in-memory capability obtained from AuthorizeAndStore.

This structural candidate never mutates status, acceptance_id, accepted_at_unix_ms or superseded_by in an ADR source document and creates no Accepted repository artifact. It does not establish atomicity, persistence, durability, rollback resistance, administrator resistance, currentness, lifecycle authority, architecture fitness, ADR compliance, implementation truth, completion, permission or effect. Production lifecycle service, repository mutation and G0 closure remain open.
