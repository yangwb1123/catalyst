# ADR-0108: First-party Dev Agent v1

## Context
ForgeOS already has an authoritative Rust `AgentRuntime`, an OpenAI Responses adapter, workspace tool capabilities, SQLite-backed Conversation and Run records, a durable event journal, assistant-message reconciliation, and explicit recovery through `run resume`. The implemented CLI can assemble these existing parts into one finite model-and-tool loop for a user-selected local Project. Treating the product path as merely a wrapper around Claude Code, Codex, or another external agent executable would make external software a runtime prerequisite even though ForgeOS owns the necessary execution boundary.

The intended slice is deliberately smaller than product orchestration. One prompt selects one Conversation and creates one Run; it is not a Sprint, an Attempt aggregate, a scheduled node, a Group Agent Graph, or an automatic traversal of any Work Graph. Those contracts have different ownership, state, authority, persistence and recovery requirements and must not be inferred from a convenient direct CLI.

Local developer effects also need a visible trust boundary. Reading the selected workspace is useful by default. Editing files and launching a local program are materially stronger same-user effects. Workspace-relative validation, bounded arguments, output limits and timeouts reduce accidental scope, but they do not isolate the process from the operating system or make arbitrary commands safe.

## Decision
Provide `forge-runtime -C PATH agent [--dev] PROMPT` as a first-party, finite, single-task Agent CLI. The command requires an explicitly selected Project, resolves or creates its ordinary Conversation, appends the user Prompt, persists one ordinary Run configuration, and drives it through the existing `AgentRuntime` and OpenAI Responses provider. Model and tool events are committed through the existing durable SQLite Run journal; existing Conversation-history loading, terminal assistant reconciliation and explicit `run resume` behavior remain the state and recovery owners.

Default execution registers the versioned read-only workspace toolset (`list_files`, `search_text` and `read_file`) and grants only `WorkspaceRead`. Explicit `--dev` additionally registers the workspace edit tool and the local process tool and grants workspace-write and process capabilities. The process tool launches one program with an explicit argument vector under the selected workspace and the same operating-system user; a shell exists only if the model explicitly selects one as the program. This mode is trusted local execution, not an OS sandbox or a general shell sandbox.

Require a non-empty explicit provider credential before a real model execution begins. Automated tests use scripted providers or assert missing-credential refusal and do not call a paid model. Claude Code, Codex and other external agents may continue to interoperate with ForgeOS files and workflows, but none is a runtime prerequisite for this first-party command.

Do not route the command through Sprint, Attempt, Group or Graph execution. Do not claim remote deployment, multi-agent coordination, automatic whole-graph execution, production safety, tenant isolation, process containment or a general-purpose shell sandbox.

## Consequences
Developers gain one direct ForgeOS command for a bounded local task without installing a separate agent runtime. The command reuses established Conversation history, Run configuration, model protocol, journal sequencing and recovery behavior rather than introducing parallel execution or persistence ownership.

Read-only remains the ambient behavior. File mutation and process execution become visible opt-in capabilities selected with `--dev`; once selected, the model acts with the invoking user's local authority and can cause consequential or destructive effects. The selected workspace and tool bounds are operational constraints, not a security boundary.

Prompts, prior Conversation history, Run configuration, provider events, tool arguments, tool results and model responses remain locally journaled in plaintext under the existing store contract. A completed Run reconciles its assistant answer through the existing Conversation path, while an incomplete safe prefix still requires the existing explicit resume command.

The direct CLI neither completes the Forge Workspace execution architecture nor changes external agent compatibility. Sprint, Attempt, scheduling, Group Graph, remote execution and production hardening remain separate work with separate decisions and evidence.

## Validation
Parser and CLI tests must cover the exact command shape, the required `-C` Project, prompt and option bounds, duplicate and unknown options, the read-only default, the explicit `--dev` warning, human and JSON start output, and refusal when the credential is missing. Credential refusal must happen before agent Hub state is created.

Application and infrastructure tests must drive `AgentRuntime` with a scripted provider through read, edit, local verification and terminal completion, proving that the dev capability set is sufficient without a real model call. Tool tests must cover workspace binding, path traversal and link behavior, argument bounds, environment filtering, output truncation, timeout, cancellation and child reaping. Read-only tests must prove that edit and process tools are absent.

Run and storage tests must prove that the new provider mode round-trips through SQLite, derives the exact capability set, durably commits the normal event sequence, uses Conversation history and assistant reconciliation, and remains compatible with validated explicit resume. Strict ADR v2 validation, focused Rust tests, formatting, Clippy, workspace tests and architecture/security review must pass before any acceptance or broader capability claim.

No automated validation may require a paid provider call. Live conformance is operator-invoked only with an explicit credential and must not be treated as evidence for isolation, production safety, remote deployment, multi-agent behavior or automatic graph execution.

## Limitations
ADR-0108 remains Proposed. It records an implemented candidate and its still-required validation; it is not authenticated acceptance, production readiness or permission to expand the effect boundary.

The read and edit tools constrain workspace paths, and the process tool constrains its working directory and execution inputs, but `--dev` does not provide an OS sandbox. A same-user subprocess may access authority available to that user, spawn descendants, invoke a shell explicitly, use ambient network access, and affect resources outside the workspace through operating-system interfaces. No claim is made that arbitrary shell execution is sandboxed or safe.

The command has one active model loop for one task. It does not create or advance an Attempt, schedule nodes, coordinate multiple agents, traverse a Work Graph, run a Group Graph, deploy remotely, authenticate a remote principal, enforce a tenant boundary, prove reproducibility, verify a production change or provide a production rollback controller.

The OpenAI Responses path requires explicit credentials and sends selected model context off-machine under the existing provider behavior. Tests that pass with scripted events prove local wiring and boundaries only; they do not prove live-provider availability, model quality, confidentiality, safety or cost. External Claude Code, Codex and similar tools remain optional interoperable peers and are outside this command's required runtime contract.
