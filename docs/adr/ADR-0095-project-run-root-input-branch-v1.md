# ADR-0095: Project Run Root-Input Branch v1

## Context
Project Run recovery supports explicit continuation of a validated durable prefix, while independent restart creates a new resume-ready Run from a terminal source. Product workflows also need a new Run whose direct source remains queryable without copying the source answer, result, tool activity or journal suffix.

The safe reusable boundary is the parent's root input. A terminal parent already binds its Project, Conversation, user Prompt and complete execution configuration, and its first event is a validated `run_started`. Later event boundaries can include model output, partial messages and tool effects whose inherited meaning is not captured by a complete context or workspace snapshot. The branch contract therefore needs a closed root-input mode, atomic persistence and explicit execution release.

## Decision
Adopt Project Run branch version 1 with `branch_mode=root_input` and `source_event_seq=1`. `forge-runtime --idempotency-key KEY -C PATH run branch PARENT_RUN_ID` accepts only a fully validated terminal parent whose Project matches the selected canonical workspace.

One SQLite v28 `BEGIN IMMEDIATE` transaction creates or exactly replays the child Run, one immutable `run_lineages` direct-parent row and exactly one fresh child `run_started` event at sequence 1. The child reuses the parent Project ID, Conversation ID, bound user Prompt and complete execution configuration. It copies no parent journal suffix, result, answer, tool call, tool output or external-effect claim.

The child identity uses a dedicated digest domain and reserved `run-branch-` namespace. Exact parent and key replay returns the same child; a different parent or another Run creation operation cannot reuse that key. `source_event_sha256` binds the exact parent Run envelope and root event. `lineage_sha256` binds the child, parent, root-input mode, source sequence, source digest and child creation time.

`forge-runtime run lineage RUN_ID` opens the existing current Hub through the immutable read-only path and returns only direct-parent metadata. Reads revalidate the lineage digests, terminal parent and root event, and the child's inherited Project, Conversation, Prompt, execution configuration, creation time and root Prompt. The query returns no Prompt, event body, answer, result or tool output.

Branch preparation reads no credential or workspace content, constructs no provider, tool or transport, and accesses no network. It releases no model or tool execution authority. The caller starts child execution only through a later explicit `run resume CHILD_RUN_ID`. If the child journal has terminal outcome `RunOutcome::Completed`, that command validates the Project binding and performs only idempotent assistant Conversation writeback reconciliation before credential, provider, tool, history or workspace-content setup. A terminal child with `RunOutcome::Failed`, `RunOutcome::Cancelled` or `RunOutcome::LimitExceeded` remains ineligible for `run resume`.

## Consequences
Terminal Run workflows gain a deterministic, queryable fork point whose stored provenance and fresh child seed commit together. Late exact replay reports the child's current validated journal state without resetting or truncating later child events. `RunOutcome::Completed` child resume remains a writeback-only recovery operation and never re-enters provider or tool execution; other terminal outcomes remain non-resumable.

Independent `run restart` retains its no-lineage rerun semantics. Ordinary starts and existing Runs also remain valid without a lineage row. The additive v28 schema preserves the v27 governance semantic view and all earlier Hub records.

The branch view is intentionally content-free and direct-parent-only. It declares `context_snapshot_bound=false` and `workspace_snapshot_bound=false`, so a lineage relation cannot be read as a historical context or filesystem snapshot.

## Validation
Validation covers terminal-parent admission, Project binding, exact inherited configuration, one-event child creation, explicit resume, content-free lineage output, ordinary Run no-lineage output and nonterminal refusal. Idempotency tests cover exact replay, different-parent conflict, reserved child namespace and key ownership conflicts with start and restart.

SQLite validation covers exact v27-to-v28 migration, current-schema ownership, transaction rollback, child-lineage-seed atomicity, source and lineage digest reconstruction, child/parent binding drift and corrupted record rejection. Read paths must fail closed on any unsupported mode, sequence, digest, parent state or inherited-input mismatch.

Effect-boundary CLI tests remove `OPENAI_API_KEY` and delete the selected workspace file before branch preparation and completed-terminal writeback recovery; lineage query remains read-only. Static path review confirms that branch and completed-terminal recovery paths construct no provider, tool or transport. A valid result must require only local Hub state.

## Limitations
Version 1 supports only the root input and one direct parent. It does not provide arbitrary event-prefix branching, transitive ancestor expansion, inherited tool-effect replay, automatic child execution, whole-Graph branching or remote exactly-once behavior.

Conversation context before the bound user Prompt and workspace bytes are not snapshot-bound. The two SHA-256 values are unkeyed local integrity identities, not signatures, authenticated provenance or protection against a same-user database rewrite. Any future event-prefix mode, snapshot binding or bounded ancestor traversal requires a separately versioned decision and migration contract.
