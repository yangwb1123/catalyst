# ADR-0083: Authenticated ADR Approval Authority Evidence and Lifecycle v1 Proposed Candidate Governance and Source Distribution

## Context
ADR-0081 now provides independently reviewed Catalyst-repository-only Go evidence for authenticated approval relative to explicit external root, epoch, trusted time and revocation high-water inputs. Its opaque `StoredAuthorization` boundary, signature verification, authorization decision, durable CAS publication and authenticated reopen are real internal authority behavior. ADR-0081 remains Proposed, provisions no production trust material or transport, exposes no route or command, and cannot accept or mutate an ADR.

ADR-0082 separately freezes an exact dependency-free Python structural prerequisite for immutable-source ADR lifecycle relations. It reconstructs proposal bindings, authorization-shaped prerequisites, transition requests, acceptance and supersession receipts, append-only ledger state, a materialized view and one enclosing state image. It intentionally performs no Ed25519 verification, live `StoredAuthorization` authentication, repository mutation, currentness decision, persistence or architecture-compliance enforcement.

The shared governance layer must record both facts honestly without collapsing them. Catalyst has narrow Go approval authority evidence; generated projects receive only Python lifecycle structural source. Neither fact puts lifecycle or approval authority into Registry scope, a context route or a runtime profile.

## Decision
Adopt Registry v34 with two additional exact metadata blocks. `authenticated_adr_approval_v1_go_authority_evidence` records ADR-0081 as Catalyst-repository-only Proposed evidence, including its external-trust authentication, signing, durable CAS, authenticated reopen, exact replay and `StoredAuthorization` boundary. It also records that no production root, key, state, clock, revocation publisher or transport is provisioned and that the implementation is not scaffolded.

`authenticated_adr_lifecycle_v1_candidate_contract` records ADR-0082 only as a source-distributed dependency-free Python structural candidate. Its authority fields remain false: structural validation does not verify signatures, authenticate current external trust or `StoredAuthorization`, authorize a transition, mutate source, publish Accepted state, enforce compliance or supply persistence, atomicity, CAS, durability, permission or effect.

Preserve the complete Registry `scope` mapping byte-semantically, with canonical compact sorted SHA-256 `8ba82b638e8031f0d1be2b9ea6d522a4b9cf064a4ed532e1f0d3281f2dfe874c`. Add only one `governance.authenticated_adr_lifecycle_v1_candidate` checker-only shadow. It invokes the frozen Python golden checker, is non-load-bearing and adds no Skill, adapter, kind, evaluator, producer, route or runtime profile. No Go detector is added.

Source distribution uses a closed exact lifecycle inventory: the ADR-0082 decision, lifecycle Schema and golden, three strict Proposed fixtures, twelve Python package files, checker and focused structural test, plus this ADR, the lifecycle governance module and governance test, and the canonical ADR-0081 prerequisite authority decision as audit documentation. Existing ADR v2 and authenticated-approval Python fragments supply the shared dependency closure and must own their already-distributed paths; the lifecycle fragment must not duplicate ownership.

The distribution must not copy `forge-core/internal/authenticatedadrapprovalcontract`, `forge-core/internal/authenticatedadrapprovalauthority`, any future lifecycle Go authority, a production root, private or signing key, seed, authority state, lock or ledger directory. It must not copy any route, runtime registration or scope entry. Fresh and legacy generation must produce the same exact bytes and modes, reject partial or additional closure, fail on mutation and remain executable without a `forge-core` directory.

The source ADR documents remain immutable and strict Proposed. Derived `Accepted` and `Superseded` labels inside a structural fixture are not source frontmatter, live lifecycle state or architecture compliance. An ADR-0081 authorization receipt is only a prerequisite, and even a live opaque `StoredAuthorization` cannot itself perform a lifecycle transition. `forge accept` remains completion authority only and is not ADR approval, lifecycle acceptance or execution authority.

## Consequences
The Registry can state the strongest reviewed truth about ADR-0081 without pretending that its Go authority is installed, routed, provisioned or distributed. At the same time, generated projects can reproduce every ADR-0082 structural relation using source-only Python artifacts with no Go or production trust dependency.

One shared governance checker now rejects scope expansion, authority-field promotion, source-distribution confusion, Go implementation projection drift, pin drift, route insertion, detector promotion, missing contract assets, exact-inventory drift and strict ADR drift. The protected policy hash makes any later metadata change require an explicit version and reseal.

The checker success marker remains negative and exact. It proves only caller-supplied structural consistency. It does not convert a proof-shaped signature, receipt, ledger, state, source status or completion result into authority.

## Validation
Validate the frozen exact twenty-file ADR-0082 core inventory as regular mode `0644`, link count one, exact SHA-256 and no scoped cache. Run its eighteen normal and dependency-free tests, CLI golden marker, Schema registry and strict ADR checks. Validate ADR-0081, ADR-0082 and ADR-0083 physical, body and self digests as strict Proposed v2 documents.

Mutation-test both Registry blocks, the complete unchanged scope mapping and scope hash, every canonical reference, every lifecycle pin, all three reference implementations, both non-capability declarations and the existing approval Python block. Turning on lifecycle authority or Go distribution, inserting any candidate into scope or route, reclassifying a Go implementation as source-distributed, or adding Go detector/runtime wiring must fail closed.

Run focused shared governance tests, the protected Agent Engineering integration, gate and architecture checks. Then run fresh and legacy scaffold acceptance and mutation cases against the exact final source manifest. Generated trees must pass the lifecycle checker and governance test without `forge-core`, a Go authority package, a key or authority state.

## Limitations
Rollback removes the Registry v34 Go-evidence and lifecycle-candidate blocks, lifecycle refs, pins, implementations, non-capabilities and single shadow detector, removes ADR-0083 and lifecycle scaffold ownership, and restores a separately sealed Registry v33 policy and active test expectations. It does not delete or alter ADR-0081, its Catalyst-only Go packages, or the independent ADR-0082 core.

ADR-0083 remains Proposed. It provides no production provisioning, authenticated caller transport, lifecycle root or key custody, trusted clock, revocation publisher, repository mutation transaction, persistent lifecycle state, administrator rollback resistance, architecture-compliance engine or Accepted-document generator.

Full authority-bearing lifecycle promotion remains open. So do authenticated Approval revocation, usage and reservation integration; immutable Accepted ADR publication and supersession enforcement; per-package `implementation_wave` rollout; change-intake orchestration; G0 closure; and a full Governance Kernel. This candidate cannot close any of them.

Generated projects contain signed-shaped fixture bytes and structural state fields for deterministic tests. Those are not production keys or authority state, and they must never be promoted into a trust root, signer seed, current ledger or permission boundary.
