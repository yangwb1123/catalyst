# ADR-0087: Legacy Governance Read Import Governance and Source Distribution

## Context
ADR-0086 freezes a bounded pure projection for explicitly supplied historical Memory JSONL and legacy ADR Markdown bytes. It preserves raw rows and documents, binds them to a caller-declared project snapshot, and emits only sealed `unverified_legacy` candidates. It neither reads an ambient repository nor interprets legacy confidence or status as truth, currentness, instruction eligibility or authority.

The isolated core now has one dependency-free Python implementation, one zero-argument stdin checker and an exact Go parity package. A shared Registry entry must describe those facts without turning a byte projector into a product migration, detector service, repository scanner or authority-bearing knowledge import. Generated projects need the Python source and evidence fixtures; they do not need the Catalyst Go parity implementation.

The detector registry can express executable argv, cwd and shell mode, but it has no stdin-source field. Adding a fake request path, `repo_root`, `--golden` flag or shell-redirection token to argv would contradict the checker and create an invocation that cannot consume the frozen wire honestly.

## Decision
Adopt Registry v36 with one scope-neutral `legacy_governance_read_import_v1_candidate_contract` block. It records the exact ADR-0086 decision, Schema, five fixtures, six-file Python package, stdin checker and focused test as a frozen fifteen-file source core. It separately records the ten-file Go package as Catalyst-repository-only cross-language parity evidence. The complete Registry scope mapping and its canonical digest remain unchanged.

Update the existing `legacy` policy block to state precisely what is implemented: Memory import is an explicit-supplied-bytes unverified read-only projection, and ADR import is the same projection with parsing deliberately not performed. This does not change Proposed-only ADR v2 validation and does not make old Markdown a v2 document. Missing confidence is never defaulted, and legacy status remains non-authoritative.

Register exactly one non-load-bearing shadow, `governance.legacy_governance_read_import_v1_candidate`. Its argv is exactly `python3 harness/legacy_governance_read_import_contract_check.py`; the script receives no arguments. An operator or future separately governed adapter must pipe one exact request to stdin and close EOF. The registry does not claim to supply that data plane, and shell mode remains false. No `--golden`, `repo_root`, request path, `<` token, route, Skill, evaluator, producer or runtime profile is added.

Source distribution is an exact eighteen-file closure: the fifteen-file core, this governance decision, the v36 governance module and its focused test. The Python implementation, checker, Schema and evidence fixtures are copied byte-for-byte. `forge-core/internal/legacygovernanceimportcontract`, runtime binaries, ambient path readers, databases, state, ledgers, caches, keys, receipts and authority artifacts are not copied.

The Registry positive result remains a structural unverified read-only projection. Acceptance, authority, confidence interpretation, conflict resolution, currentness, instruction eligibility, persistence, runtime effect, source authentication, source completeness, status interpretation, truth and winner selection are all false. The supplied binding remains caller-declared and is not authenticated by governance or scaffold checks.

## Consequences
Catalyst and generated projects can reproduce the same explicit-byte Python projection and its negative authority boundary. Catalyst additionally retains Go parity evidence without presenting that implementation as installed capability in generated projects.

Registry v36 closes only the roadmap item for designing a read-only legacy Memory/ADR import whose default state is `unverified_legacy`. It does not merge `.agent/DECISIONS` with ADRs, authenticate source provenance or completeness, adjudicate conflicts, select a current record, migrate persisted data, accept an ADR or create a Claim, Atom, instruction, Grant, transition, receipt or effect.

The exact argv is executable when the caller provides stdin and EOF. Invoking it with inherited open stdin is an operator error, not an automatic detector claim; invoking it with EOF and no request fails closed with no stdout.

## Validation
Pin and independently recompute the ADR-0086 physical, body and self digests, the exact fifteen-file source aggregate and exact ten-file Go aggregate. Run all twenty-five Python tests, the exact stdin golden, all Go tests, race detection, vet and cross-language output comparison. Reconstruct the thirteen false attestations from the golden view.

Mutation-test Registry v36 version, unchanged scope and scope digest, the `legacy` block, candidate metadata, refs, pins, Python and Go projection classifications, non-capability declaration and detector wiring. Reject every route or scope insertion, load-bearing promotion, data-bearing pseudo argv, Go source distribution, ambient repository input or authority-bearing attestation.

After independent shared review, validate exact eighteen-file fresh generation and a real Registry v35-like legacy projection. Require regular mode `0644`, link count one, no-follow source and target reads, fixed hashes, exact ledger ownership, no Go or runtime artifacts, a clean second upgrade and compatibility of all older source-slice verifiers under active Registry v36.

## Limitations
ADR-0087 remains Proposed. It does not authenticate the caller, project ID, revision, source-tree digest, Memory file or ADR file. It does not prove the supplied source set is complete or current and provides no protected check-to-use handoff.

The checker is not invoked by `forge accept`, receives no automatically discovered input and has no path-reading fallback. Registry shadow wiring is descriptive and non-load-bearing. No service, route, socket, product command, database adapter, repository crawler, watcher or migration transaction is delivered.

Generated projects receive no Go implementation. Neither Python nor Go establishes truth, authority, status meaning, confidence meaning, conflict resolution, winner selection, persistence, runtime effect, lifecycle acceptance, compliance or G0 closure. Any operational or authority-bearing promotion requires a separate authenticated input, authorization, transition, persistence, recovery and audit decision.
