# ADR-0111: Hub Conversation Change Journal v1

## Context
The Rust Hub owns canonical Conversations and Prompts under ADR-0007, but its current API exposes only point-in-time reads. A future Coordinator cannot reliably replicate committed session changes across CLI, TUI, Web, App, and Mobile without a durable cursor. The Hub is currently schema v29; creation and Prompt append already use immediate SQLite transactions and exact idempotency replay.

The cross-device plan proposes one logical Coordinator and keeps Snaplink identity, Go transport, Rust Runtime ownership, and Runner identity separate. This slice establishes only a Rust-owned local change feed. It does not resolve remote authentication, tenant mapping, deployment reachability, or transport ownership. Existing v29 records remain available from the normal snapshot query; the v30 event journal begins empty and records changes committed after migration. The migration needs a non-event baseline marker for each existing Conversation so it can distinguish expected legacy history from a missing v30 creation event.

## Decision
Add Hub schema v30 with a `conversation_changes` table, baseline markers, a singleton global cursor head, and per-Conversation version heads. The journal uses a store-global, contiguous positive cursor. The closed event kinds are `conversation_created` and `prompt_appended`. Each event row contains the Conversation ID, immutable entity ID, per-Conversation journal version, event kind, schema version 1, and creation time. It carries no Prompt body; consumers use the entity reference to query canonical Hub state. The migration inserts one baseline marker and a zero version head for each Conversation that exists in v29, plus a zero global cursor head; these metadata rows are not events and consume no cursor.

Append exactly one change row and advance both durable heads in the same existing immediate transaction as each newly committed Conversation or Prompt. The per-Conversation journal version begins at 1 for the first recorded change and increments by one for each later recorded change. A new Conversation therefore starts with `conversation_created` at version 1; an existing v29 Conversation has a baseline marker but no synthesized creation row, so its first post-migration Prompt is `prompt_appended` at version 1. A non-baseline Conversation with no valid creation event is corrupt and cannot accept a Prompt. This journal version does not represent unrecorded pre-v30 history. Before writes, compare journal counts and maxima to the durable heads and validate the whole Conversation head set; readers verify the global/per-Conversation heads, require each zero-version head to have its migration baseline marker, and check that a positive head's first event kind agrees with baseline status. This detects interior gaps, deleted final events, and missing baseline metadata without reusing a consumed cursor/version. Exact idempotent replays return the stored entity and append no row; conflicting key reuse remains a conflict. Cursor assignment occurs inside the write transaction, so committed rows are gap-free and visible in commit order. Do not backfill historical v29 events or claim the new cursor represents pre-migration history.

Expose an application query for bounded store-global cursor pages and a Global snapshot-with-head-cursor read performed in one deferred transaction. A client can bootstrap from the canonical Global snapshot at cursor N, then request changes after N; page responses include the snapshot head and next cursor. Project and Group snapshots remain point queries and are not paired with a scoped feed. Reject a cursor beyond the observed head, invalid limits, malformed rows, and any gap in the returned contiguous range. The journal has no retention or deletion API in this version.

## Consequences
Rust remains the sole canonical owner for Conversation and Prompt records. Existing Hub v29 data and query behavior are preserved through the additive migration; every new write after migration has an atomic durable change reference suitable for a later authenticated Coordinator adapter. Existing v29 Conversations remain writable without fabricated event history: baseline markers identify them, and their first post-migration Prompt starts the journal version at 1. Snapshot and cursor are read from one SQLite snapshot, avoiding a bootstrap race.

Cursor values are local to one Hub database and are not global account IDs or portable across stores. Change rows expose IDs and references, not authenticated actors, tenant ownership, prompt bodies, authorization, delivery, or effect evidence. Journal rows and head metadata grow with new Conversation and Prompt writes; retention, compaction, protocol, and cross-store replication require later decisions.

## Validation
Verify v29-to-v30 migration preserves populated Conversations, Prompts, and Runs, creates baseline markers and zero-valued durable heads without journal events, and that an existing v29 Conversation accepts a new Prompt whose first journal version is 1. Verify a new Conversation whose creation event is missing cannot accept a Prompt. Verify new creation and Prompt append each add one atomic row and advance both heads; exact replay adds none, while conflicting replay fails without advancing either sequence. Remove baseline metadata before and after the first legacy event, plus interior/final journal rows, in corruption fixtures and prove readers and later writes fail closed without committing another Prompt or reusing a cursor/version.

Verify the Global snapshot and its store-global head cursor share one read transaction, pages are ordered and bounded, `next_cursor` advances only over returned rows, and cursor-ahead, gaps, malformed rows, and schema drift fail closed. Do not expose a Project or Group snapshot as if it had a scoped change feed. Run focused Rust tests, formatting, strict lint/build checks, schema migration tests, architecture/governance checks, and repository acceptance on the final tree before claiming this slice complete.

## Limitations
This is not an authenticated remote sessions API, Snaplink integration, Go↔Rust service adapter, session import/claim, Web/TUI/CLI/App/Mobile client, Runner enrollment, resource inventory, placement, lease, remote execution, or Aero ecosystem integration. The local event cursor is not an authorization boundary or tamper-evident ledger. Historical v29 Conversations and Prompts are visible through snapshot reads and receive baseline markers, but no synthesized change rows. `HubSnapshot` does not contain Prompt history; a later authenticated API must hydrate canonical Prompt queries as well as consume change references. The ADR and this repository slice remain Proposed until their applicable review and governance lifecycle is complete.
