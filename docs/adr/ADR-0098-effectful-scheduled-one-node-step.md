# ADR-0098: Effectful Scheduled One-Node Step

## Context
ADR-0096 can atomically observe scheduled Graph progress and ask Core which one serial node is ready. ADR-0097 can independently rebuild the selected initial or successor source, run the ready decision again in Core, and bracket that private authorization with complete atomic bundles A and B. Both protocols deliberately stop before consent, a lifecycle write, a Project-lane claim or a provider effect. Their result can become stale immediately after B, so it cannot itself be execution authority.

The existing scheduled effect path already has exact request, pricing, registered destination, one-shot provider collection and terminal receipt machinery. Its persisted lifecycle version 1, however, embeds the older release and authorization types. Silently putting ready-release v2 bytes into that family would make reconstruction ambiguous, while adding a second physical active-lane index would permit a legacy claim and a ready claim to own the same Project simultaneously.

A process can also fail after a local claim commits but before it sends, or after a send but before terminal evidence commits. A timeout, missing process or database error does not reveal whether the provider observed the request. Any automatic retry, lease expiry or replacement executor would therefore risk a duplicate external effect. Recovery needs durable exact-owner evidence and an explicit operator transition, not elapsed time.

## Decision
Add one explicit effectful scheduled step. Its input names one Graph Run, the expected ready authorization digest and exact provider request ID, one exact pricing artifact, an operator-pinned Core binary, fresh off-machine consent and conditional fresh predecessor-content consent. The application reruns the full ADR-0097 A/Core/B service internally for every prospective effect and compares both expected identities before reading a credential or constructing a provider. An unchanged prior lifecycle is returned as already claimed without rebuilding a provider or sending.

### Versioned lifecycle reconstruction
Ready-node claims use lifecycle version 2 while retaining the existing physical SQLite lifecycle table. The stored release-control and authorization JSON versions jointly identify the family: exactly `(1,1)` reconstructs the legacy inspection and exactly `(2,2)` reconstructs the ready-node inspection. Mixed or unknown pairs are corruption. Family-specific public readers reject the other family rather than falling back, while the progress reader and explicit adjudication reader use a tagged union and validate the selected family completely.

The v2 inspection stores and revalidates the complete ready release control, authorization, pricing snapshot, prepared request and exact body together with the existing claim, active lane, claim event and optional terminal artifact, control and receipt. Every graph, request, authorization, pricing, lane, source snapshot, event head, ordinal, node, attempt, body and digest relation is checked again on read. Terminal artifact, control and receipt remain version 1 because their existing claim-bound fields are sufficient and their bytes do not encode the release family.

No schema migration is needed. Existing rows, indexes and caps remain unchanged. Reusing one table also keeps the existing per-request and per-node constraints, but the protocol family must never be inferred from a failed decode or from whichever decoder happens to succeed.

### Snapshot-to-claim CAS and authority
After consent and the internal ready-release preflight, Runtime creates unpredictable claim metadata and an exact local executor owner. It constructs a provider with an invocation-scoped credential but does not poll it. The sidecar is made durable before the claim reaches its commit-uncertain boundary.

The lifecycle store starts `BEGIN IMMEDIATE`. Inside that transaction it validates the full v2 request, reconstructs the complete current ready source using the expected progress snapshot, ordinal and node, and requires exact equality with the release control and prepared body. It then checks both scheduled lifecycle and legacy lifecycle ownership for the same Project lane, inserts the claim, lane and immutable source evidence, reconstructs the stored row and constructs a non-`Clone` request authority. Only a successful commit returns that authority. A stale source, occupied lane, corrupt row or failed commit returns no send capability.

Both the legacy and ready claim paths perform the opposite-family active-lane check while holding their immediate writer transaction. Thus the Project lane is one global exclusion domain even though the lifecycle protocols and physical tables differ. Two ready contenders can prepare independently, but only the transaction winner receives request authority; an exact-source loser returns the durable winner and discards its unopened provider and losing sidecar.

Exact replay compares immutable release, authorization, pricing, request metadata and body. It deliberately does not require equality with the contender's fresh lane owner or timestamp. The contender request is still fully validated before replay classification. Reusing the provider request identity with different immutable evidence is a conflict.

### Exact executor ownership and adjudication
On Linux, the owner directory must be an exact non-symlink directory with mode `0700`. A sidecar is created with `create_new`, mode `0600`, link count one and an owner-hash filename derived from the provider request ID and lane ownership ID. Its compact canonical JSON is capped at 4 KiB and binds version, request, lane, PID, Linux machine ID, boot ID, PID namespace identity, time namespace identity and `/proc` process start ticks. Creation and adjudication additionally require `/proc/self`'s exact positive-decimal target to equal the process `getpid()`, so a procfs mount exposing an ancestor PID namespace cannot be used for liveness. File, directory and newly created parent entries are synchronized before claim.

Created handles normally remove their own exact device-and-inode path on drop. Immediately before the commit-uncertain claim, the application switches the handle to preserve-on-drop. After terminal or quarantine commit releases the lane, it removes only the still-present path with the same device and inode and synchronizes the directory. A replacement path is left untouched.

Hard-crash adjudication first reads the durable lifecycle through the explicit any-family reader, requires `claimed`, an active lane and exact request-and-lane owner, then opens that exact hashed sidecar. The local machine must match. A different boot proves that the old executor is dead; on the same boot, the exact PID namespace, time namespace and verified procfs PID view must match before liveness may be classified as `dead` or `pid_reused`. A live process, foreign or mismatched namespace/view, missing or malformed document, unsafe permissions, symlink, hardlink or changed file identity is rejected. The immediate adjudication transaction repeats status, evidence absence, lane-active and exact-owner checks and guards the update with those fields. Exactly one updated row releases the lane. Sidecar cleanup occurs only after commit; cleanup failure cannot erase the committed adjudication facts and is reported separately with post-cleanup presence unknown.

### One-shot send and terminal outcomes
The committed authority is consumed into the exact prepared body once. The registered provider is polled once with the inherited event, byte, token, result and timeout bounds; there is no transport retry or application resend. The collector produces completed or uncertainty evidence only after its existing terminal and true-EOF rules. Runtime re-inspects the exact durable claim and lane before building the terminal artifact.

The existing pinned terminal Core validates a claim-bound terminal control and returns a receipt. One immediate terminal transaction stores artifact, control and receipt and releases the lane. If Core refuses or fails, Runtime instead attempts artifact-only quarantine and releases the lane; that status also forbids resend. A catchable cancellation becomes bounded uncertainty evidence. A hard process crash can leave `claimed` with an active lane and preserved owner evidence.

Claim commit failure is treated as unknown: no authority is returned, the provider is not polled, and the owner is retained whenever inspection cannot prove that the exact lane was not committed. Terminal commit failure is also no-resend: Runtime cleans the owner only when a fresh exact inspection proves that the same claim is durably lane-released; otherwise the owner remains for adjudication. Every later invocation inspects the lifecycle before provider construction and returns the existing claimed, terminalized, quarantined or adjudicated evidence without sending.

The command performs at most this one node. It does not materialize a successor, invoke itself recursively, advance a controller cursor or treat a completed receipt as permission to execute another node. A caller must make a separate explicit invocation with fresh consent and newly validated current release evidence.

## Consequences
One local call now closes the race from Core-selected ready observation to durable single-winner authority. The exact current source and global Project lane are compared and claimed together, while provider polling remains outside the database transaction and can start only for the commit winner.

Version 1 remains byte-compatible and version 2 is explicit. Progress can consume terminal receipts from either family without confusing their private release evidence. Adjudication can release a stranded lane from either family only through the same exact owner protocol.

The design intentionally preserves uncertain states. A retained claimed lane can require operator action and reduce availability, but it never turns missing evidence into permission to resend. Local single-consumption does not imply remote exactly-once because the provider may observe a request whose local terminal transaction never commits.

## Validation
Domain and SQLite tests must mutate each family version, release-to-authorization pair, claim binding and terminal evidence presence. Real two-connection races must cover ready versus ready and both legacy-versus-ready directions, proving one winner, one active owner and zero authority for every loser. A stale progress or selected source changed between ADR-0097 B and `BEGIN IMMEDIATE` must fail before provider polling.

Application tests use a deterministic in-memory provider and real SQLite. They cover one completed ready step, exact repeat with no second credential or provider use, concurrent contenders with one provider poll, missing off-machine consent, conditional predecessor-content consent, provider uncertainty, Core quarantine, claim commit uncertainty and terminal commit uncertainty. Tests count owner creation, preservation and cleanup independently from provider and Core calls.

Sidecar tests cover canonical bounds, `0700` and `0600` modes, create-new collision, symlink and hardlink rejection, unsafe directories, malformed and foreign documents, PID-namespace, time-namespace and procfs-view mismatch, device/inode replacement, live/dead/PID-reused classification and cleanup ordering. Adjudication tests require the wrong lane owner and a live exact owner to fail while reboot-proven-dead or same-boot dead/reused exact owners in the exact namespaces and view can update exactly one claimed row from either lifecycle family.

The public CLI suite must use only repository-built local Core and deterministic or refusing provider fixtures. It checks argument duplication and bounds, both Core handshakes and pin failure before private input, fresh consent before credential/owner/provider effects, metadata-only default output, explicit result disclosure, no second node, no resend on re-entry and redacted error output. Workspace, logical Hub state and loopback sentinels remain part of the process-level privacy boundary.

Strict format, Clippy, full Rust tests, architecture limits and the repository acceptance harness remain required. A fresh-context security reviewer must independently trace the source-to-claim transaction, authority lifetime, owner creation and cleanup, every post-claim error path, cross-family lane race, adjudication guard and CLI effect ordering. These observations can support delivery of the repository slice, but this ADR remains Proposed and does not become accepted through tests or review.

## Limitations
The step does not provide remote exactly-once, provider-side idempotency, automatic retry, lease expiry, resume, quarantine recovery, automatic successor admission, failure propagation or a durable whole-Graph controller. It does not execute a second node or schedule-v2 parallel wave. Every later external request still needs its own fresh exact consent.

The sidecar is local Linux evidence for one exact machine and boot-bound executor, not an authenticated distributed executor identity or fencing token. A different boot proves the old process dead; on the same boot, the PID namespace, time namespace and procfs PID view must match exactly before process start ticks distinguish ordinary PID reuse. These checks do not protect against a hostile privileged or same-UID process. Standard-library pathname operations do not retain a verified directory descriptor or provide atomic create, open, sync or unlink relative to one. The implementation repeatedly cross-checks directory and file identities, permissions, link counts and held device/inode values and leaves replacements it observes untouched, but a malicious same-UID process can replace a parent after validation or race a later path operation. That attacker is outside this local trust model; eliminating these races requires a separately reviewed persistent dir-fd plus Linux `openat2`/`unlinkat` protocol.

SQLite `BEGIN IMMEDIATE` and local unique constraints provide one-Hub serialization only. Database replacement, same-user tampering, storage loss or an untrusted custom store remain outside the claim. Digests are integrity identities rather than signatures, freshness proofs or authenticated principals.

The pinned Core is still a trusted same-user TCB. Its binary digest and handshake identify bytes and protocol, not publisher, function, filesystem or network confinement, or effect attestation. The pricing artifact is operator asserted and does not prove live vendor billing. Proposed status records this candidate decision only and provides no ApprovalRecord, compliance, permission or effect authority.
