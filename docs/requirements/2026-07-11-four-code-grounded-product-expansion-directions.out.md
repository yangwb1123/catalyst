## 来自资深架构师视角的更深层观察

### 1. 这里有一个“元缺口”在蔓延

所有四个方向都共享一个共同的根源：**管道缺失**。当前的状态机（oracle → observe → converge → loop）将每个阶段的输出视为不透明的 blob。它有一个清晰的执行模型，但缺少的是**投影层**——能够说“从规划器的输出中，取任务列表并以结构化形式呈现给实现者”。

这在 DDD 术语中是“仓库”与“投影”问题：当前状态是将事件（阶段输出）转储到文本存储中，而不是将其投影到可供下游使用的具体化读取模型。

### 2. 方向三的最大风险是误报（尤其是在并行模式下）

你注意到了这一点，但值得强调：当两个阶段并行运行，其中一个声明了 `readonly: true`，另一个则没有，且后者修改了一个文件——对 readonly 阶段的 `git diff` 验证会提示违规，但实际上是另一个阶段造成的。你需要**文件级变更归因**（通过 `git diff` 中的文件模式，可能通过查看变更的代码行是否在另一个阶段的“所有权”范围内），才能让 readonly 验证在并行场景可靠。

### 3. 方向一和方向二应该被统一为一个单一模式，而不是分别推进

输出约定（方向一）和结构化数据管道（方向二）本质上是同一枚硬币的两面：一个阶段产生结构化数据，该数据通过管道传输到下一个阶段。如果你引入了一个 `Contract` 接口，该接口生成一个带类型的 `Result`，那么这个 `Result` 自然就是应该通过管道传输的结构——方向二的 `FeedsForward struct { As string; Schema string }` 变成了“方向一契约的结果流经方向二管道”。如果分别构建，你最终会得到两个相互引用的模式。

### 4. 方向四有两个未提及的依赖项

**依赖关系 A：** Run identity 需要 `forge trace --run <id>` 和 `forge status --run <id>` 等 CLI 子命令——这意味着 CLI 表面积的增长超出了你当前的范围。确保这能与现有的 `forge status`（它只关心当前运行）合理地组合。

**依赖关系 B：** `.forge/manifests/` 目录需要生命周期管理——gc 策略、磁盘大小上限，以及可能集成到 `forge doctor` 中。否则，经过 100 次运行后，你就会有像检查点一样堆积的 100 个清单文件。

### 5. 我不同意方向三中 P0 的分类

你将其标记为 P1，但基于代码库自身的 TODO 注释（“已在此处添加：... 但尚无任何东西强制执行”）以及 `Emits` / `Readonly` / `RequiresTools` 当前作为无操作字段存在的事实，我会说：
- **方向三已在路线图上**（代码库内的 TODO 注释）
- 它的成本是三者中最低的（验证框架大约 200 行 Go 代码 + 三个验证器各约 50 行）
- 它直接与文档声称的强制语义相关
- **建议：将其提升为 P0，如果不是实际 P0，至少在 sprint 顺序上优先于方向一和方向二。** 用户看到 `readonly: true` 并期望只读语义——默认 fail-open 行为与直观预期不符。

### 6. 关于新颖性验证的一个方法论提示

你在 126+ 篇分析文档中进行的“零命中”关键词搜索验证了方向作为**独立系统性论证**是新颖的。但是，我应该指出，方向一和方向三实际上已经作为代码库自身 TODO 注释中承认的缺口而存在（`asset.go:126, 152, 160` 等中的“已在此处添加”）。这在代码中留下了追溯路径——对新读者的影响与“团队知道这一点但尚未修复”相同。你的新颖性主张是安全的（没有现有的分析系统地论证过这一点），但值得指出的是，在实现层面已经有认知存在。
